下面给出一份可以作为 **OntoPlatform v0.1 总体架构设计基线** 的完整版本，并把它与已经收敛的 **Ontology Runtime Kernel v0.1** 的关系一次性定义清楚。

---

# OntoPlatform v0.1 总体设计

## 1. 产品定位

**OntoPlatform** 是一个面向业务人员、领域专家、开发者和 AI Agent 的本体智能应用平台。

它以 **Ontology（本体）** 为业务语义中心，把：

```text
业务知识
+
现实数据
+
业务能力
+
AI / Agent
+
应用
```

统一到一个可设计、可发布、可运行的业务世界中。

核心价值链：

```text
定义业务世界
        ↓
     Ontology
        ↓
连接现实数据
        ↓
       Data
        ↓
赋予业务能力
        ↓
    Capability
        ↓
形成领域应用
        ↓
   Application
        ↓
AI / Agent 智能使用
        ↓
 Runtime Kernel
```

一句话：

> **OntoPlatform 负责“构建、治理和使用业务世界”，Ontology Runtime Kernel 负责“让业务世界真正运行起来”。**

---

# 2. 整体定位：Design Time + Run Time

OntoPlatform 和 Kernel 最核心的关系，是：

```text
                  Design Time
                       │
                 OntoPlatform
                       │
           设计 / 配置 / 编排 / 发布
                       │
                       ▼
                    Publish
                       │
                       ▼
                   Run Time
                       │
             Ontology Runtime Kernel
                       │
             Object / Relation / State
                       │
                Function / Execution
```

所以两者不是简单的：

```text
Platform = Kernel 的超集
```

而是：

```text
OntoPlatform
    = Design + Compose + Govern + Intelligence

Runtime Kernel
    = Semantic Execution + Runtime State
```

---

# 3. 用户视角：只暴露 4 个核心概念

虽然后端内部很复杂，但前端产品必须简单。

用户真正需要理解：

```text

数据
能力
应用
```

加一个平台容器：

```text

```

因此一级产品结构建议：

```text
工作空间

├── 本体
├── 数据
├── 能力
└── 应用

AI 助手
设置
```

不要让用户直接接触：

```text

Projection
Function
Workflow
Executor
Runtime
Semantic Context
MCP
```

这些属于内部实现概念。

---

# 4. 工作空间 Workspace

Workspace 是平台级隔离与组织容器。

```text
Workspace
├── Ontology
├── Data
├── Capability
└── Application
```

Workspace 负责：

```text
资源组织
权限隔离
生命周期
发布范围
```

第一版不要引入：

```text
Workspace
  ↓
Solution
  ↓
Project
```

这种多级容器。

---

# 5. Ontology：平台核心领域

Ontology 是整个 Platform 的中心语义模型。

用户通过 Ontology 定义：

> **这个业务世界里有什么东西，以及它们之间是什么关系。**

Ontology 只负责描述业务世界结构，不吞并 Data、Capability、Workflow、Application。

---

## 5.1 Ontology 核心模型

```text
Ontology
├── ObjectType
│   └── Property
├── Relation
└── Vocabulary
```

例如高速领域：

```text
Vehicle
TollStation
Road
Transaction
Account
```

以及：

```text
Vehicle --passes--> TollStation
TollStation --belongs_to--> Road
Transaction --belongs_to--> Vehicle
```

---

# 6. ObjectType

定义业务对象类型：

```yaml
Vehicle:
  description: 车辆

  properties:
    plate:
      type: string

    type:
      type: string

    balance:
      type: number
```

平台中的 ObjectType 最终会编译成 Kernel 的：

```text
ObjectType
```

但二者不是同一个领域对象。

---

# 7. Relation

定义对象之间的语义关系：

```yaml
passes:
  source: Vehicle
  target: TollStation
```

平台定义的是：

```text
Relation Definition
```

Kernel 运行的是：

```text
Relation Instance
```

即：

```text
Platform:
Vehicle --passes--> TollStation

Kernel:
Vehicle/V001 --passes--> TollStation/ST001
```

---

# 8. Vocabulary

Vocabulary 是为了让业务语言和 Ontology 对齐。

例如：

```text
收费站
收费场站
站点
Toll Station
```

可以映射到：

```text
TollStation
```

Vocabulary 是后续 LLM 理解业务语义的重要基础。

它属于 Platform，不进入 Kernel 的核心 Runtime 模型。

---

# 9. Ontology 生命周期

Ontology 是设计时资产：

```text
Draft
  ↓
Validate
  ↓
Review
  ↓
Publish
  ↓
Runtime Schema
```

平台内部：

```text
Ontology
```

发布后生成：

```text
OntologySchema
```

然后进入 Kernel。

---

# 10. Ontology Compiler

这是 Platform 和 Kernel 之间非常关键的防腐层。

```text
Platform Ontology
        ↓
Ontology Compiler
        ↓
Kernel OntologySchema
```

Compiler 负责：

```text
解析
引用解析
语义校验
类型转换
裁剪平台属性
生成 Runtime Schema
```

因此：

> Kernel 不认识 Platform 内部复杂的 Ontology Model。

---

# 11. Data：连接现实世界

Data Domain 负责：

> **如何把现实世界的数据映射到 Ontology 世界。**

核心模型：

```text
Data
├── DataSource
├── DataAsset
├── Mapping
└── Projection
```

---

# 12. DataSource

支持：

```text
Database
API
ES
File
Object Storage
MQ
```

例如：

```text
MySQL
ES
Kafka
REST API
```

它们属于 Infrastructure 的具体实现。

Domain 只认识：

```text
DataSource
```

---

# 13. Mapping

Mapping 解决：

> 数据字段与业务语义怎么对应？

例如：

```text
vehicle_plate
      ↓
Vehicle.plate
```

或：

```text
station_code
      ↓
TollStation.code
```

Mapping 是：

> **语义映射规则。**

---

# 14. Projection

Projection 解决：

> 如何从数据源得到运行时对象和关系？

例如：

```text
transaction table
vehicle table
station table
       ↓
    Projection
       ↓
Vehicle
Transaction
passes Relation
```

所以：

```text
Mapping
= 字段/语义对应

Projection
= 从源数据构造语义状态
```

这是两个不同层次。

---

# 15. Data → Kernel

Data 不直接操作 Kernel Store。

统一：

```text
DataSource
    ↓
Mapping
    ↓
Projection
    ↓
RuntimeGateway
    ↓
Kernel
```

最终形成：

```text
Source State
     ↓
Semantic State
```

其中：

> **Kernel 是 Semantic State 的唯一运行时事实来源。**

Platform 不复制一份 PlatformObject。

---

# 16. State 的最终归属

系统存在三种状态：

```text
Source State
Semantic State
Application State
```

分别属于：

```text
Data
Kernel
Application
```

关系：

```text
External Data
     ↓
Source State

Mapping / Projection
     ↓

Kernel
     ↓
Semantic State

Application
     ↓
Application State
```

特别重要：

> Platform 不维护第二套 Semantic Object State。

否则最终会变成：

```text
Platform Object
     ↕
Kernel Object
```

导致同步地狱。

---

# 17. Capability：平台的“动词世界”

如果说：

```text
Ontology = 世界有什么
```

那么：

```text
Capability = 世界可以做什么
```

Capability 是 Platform 的第二核心领域。

例如：

```text
车辆充值
收费站开启
拥堵分析
异常车辆处置
交易异常分析
```

---

# 18. Function / Workflow / Tool 的层级

平台内部统一采用：

```text
Function
   ↓
Capability
   ↓
Application
```

其中：

```text
Function
```

来自 Kernel，是最小执行能力。

```text
Workflow
```

是 Platform 中组合 Function 的实现方式。

```text
Capability
```

是面向业务的能力抽象。

```text
Tool
```

只是向 Agent 暴露 Capability 的协议形式。

因此：

```text
Function
= 原子执行

Workflow
= 能力编排

Capability
= 业务能力

Tool
= Agent 接口
```

---

# 19. Capability 的实现方式

一个 Capability 可以由：

```text
Single Function
Workflow
Agent
AI + Function
```

实现。

例如：

```text
Capability:
异常车辆处置
```

内部：

```text
查询车辆
   ↓
查询通行记录
   ↓
分析异常
   ↓
调用处置函数
   ↓
发送通知
```

用户看到的只有：

```text
异常车辆处置
```

而不是 Workflow DAG。

# 21. Application：面向最终用户的产品

Application 是 Platform 最上层的产品抽象。

它负责：


```text

```

用户创建的是：

> **应用**

而不是：

> Workflow / Function / Tool。


# 24. Intelligence：AI 不作为独立用户世界

AI 是横向能力。

而不是：

```text

数据
能力
应用
AI
```

五个并列业务模块。

AI 应该贯穿：

```text

  ↓

  ↓
Capability
  ↓
Application
```

具体：

```text

```

```text

```

# 26. Semantic：连接 Ontology 与 LLM

Semantic Layer 负责：

```text
Ontology → AI Context
User Language → Ontology Concept
```

例如：

用户：

> “帮我找出拥堵收费站附近的异常车辆。”

Semantic Layer 识别：

```text
拥堵
→ TollStation.status

附近
→ Spatial / Relation semantics

异常车辆
→ Vehicle + Anomaly capability
```

这一步不应该全部依赖 Prompt。

---

# 27. LLM Layer

LLM 负责：

```text
理解
结构化生成
推理
规划
判断
```

通过：

```python
LLMProvider
```

连接：

```text
OpenAI
Qwen
GLM
llama.cpp
vLLM
Ollama
```

Domain 不依赖具体模型。

```text

 ↓
```



# 30. Platform 与 Kernel 的核心关系

这是整套设计最关键的接口：

```text
                 OntoPlatform
                      │
              RuntimeGateway
                      │
                      ▼
          Ontology Runtime Kernel
```

Platform 不能直接：

```text
Platform → SQLite
Platform → Kernel Store
```

而统一：

```text
Platform
   ↓
RuntimeGateway
   ↓
Kernel
```

---

# 31. RuntimeGateway

RuntimeGateway 是 Platform 的 Anti-Corruption Layer。

负责：

```text
Platform Model
      ↕
Kernel Model
```

主要 API：

```text
publish_schema()
get_object()
find_objects()
related()
invoke()
observe_changes()
```

并负责：

```text
ObjectRef 转换
FunctionCall 转换
Schema 转换
Change 转换
错误转换
```

---

# 32. Platform 与 Kernel 的“所有权关系”

这是最终必须明确的。

| 对象                        | 所属         |
| ------------------------- | ---------- |
| Ontology                  | Platform   |
| ObjectType Definition     | Platform   |
| Relation Definition       | Platform   |
| Vocabulary                | Platform   |
| DataSource                | Platform   |
| Mapping                   | Platform   |
| Projection                | Platform   |
| Capability                | Platform   |
| Workflow                  | Platform   |
| Application               | Platform   |
| Agent                     | Platform   |
| Object Runtime Instance   | **Kernel** |
| Relation Runtime Instance | **Kernel** |
| Runtime State             | **Kernel** |
| Runtime Function          | **Kernel** |
| Function Execution        | **Kernel** |
| Change                    | **Kernel** |

Platform 负责定义与管理。

Kernel 负责运行与保存语义状态。

---

# 33. Function 归属需要特别说明

这里容易产生误解：

```text
Platform Capability
      ↓
Kernel Function
```

不是说 Platform 拥有 Kernel Function 的实例。

而是：

```text
Platform
定义 Capability
       ↓
编排 / 绑定
       ↓
Kernel Function
```

Kernel Function 是：

> 最小运行时能力。

Capability 是：

> 面向业务的完整能力。

# 42. 前端设计原则

### 第一原则

> **用户看到的是业务语言，不是技术语言。**

例如：

```text
对象
关系
能力
应用
```

而不是：

```text
ObjectType
RelationDef
Function
Workflow
Runtime
```

---

### 第二原则

> **复杂性默认隐藏，按需展开。**

例如 Capability 页面：

```text
异常车辆处置
```

点击“实现详情”后才看到：

```text
Workflow
Functions
Agent
```

---

### 第三原则

> **AI 是平台的自然语言入口。**

每个页面都应该能表达：

```text
“帮我完成这个事情”
```

而不是要求用户学习完整配置流程。

Ontology 不依赖高速行业。

例如：

### 高速

```text
Vehicle
TollStation
Transaction
Road
```

### 制造

```text
Equipment
ProductionLine
WorkOrder
Material
```

### 政务

```text
Person
Organization
Application
Event
```

### 企业经营

```text
Customer
Contract
Product
Order
Account
```

底层全部归约为：

```text
Object
Property
Relation
Capability
Application
```

所以普适性来自：

> **稳定的语义抽象，而不是支持大量行业专用功能。**

传统方式：

```text
LLM
 ↓
一堆 API
 ↓
业务系统
```

OntoPlatform：

```text
LLM
 ↓
```

# 47. 最关键的边界原则

## 原则一

**Platform 不拥有第二份 Semantic State。**

Kernel 是 Runtime State 的唯一事实来源。

## 原则二

**Kernel 不知道 Platform。**

Kernel 甚至可以脱离 OntoPlatform 独立运行。

## 原则三

**Platform 不直接调用 Kernel 内部组件。**

## 原则四

**Application 不直接操作 Function。**

```text
 ↓
Runtime
```

---

## 原则五

**Agent 不直接操作数据库。**

统一：

```text

 ↓

 ↓
Runtime
```

# 51. 最终用一句话定义两个产品

### Ontology Runtime Kernel

> **让一个语义世界可以被读取、导航、操作和持续运行。**

### OntoPlatform

> **让用户可以创建、连接、赋能、治理并通过 AI 使用这个语义世界。**

最终形成：

```text
             OntoPlatform
                  │
     ┌────────────┼────────────┐
     │            │            │
  Ontology      Data       Capability
     │            │            │
     └────────────┼────────────┘
                  ↓
             Application
                  ↑
                  │
                 AI
                  │
                  ↓
          RuntimeGateway
                  ↓
      Ontology Runtime Kernel
                  ↓
       Object / Relation / State
                  ↓
              Change
                  ↑
                  │
              Application
```

这版可以作为 **OntoPlatform + Ontology Runtime Kernel 的总体架构基线**。后续详细设计应该围绕几个稳定契约展开：**Ontology 发布协议、Data Mapping/Projection 协议、Capability→Function 协议、RuntimeGateway 协议、Semantic Context 协议，以及 Application 的统一模型**。这些才是下一层真正需要冻结的架构接口。
