# 落地路线图

本页面向准备把本体引入组织的人：如何判断从哪一阶段开始、90 天能做什么、需要哪些角色、怎么选试点和验收、如何避免“立项即高潮、验收即终止”。结论先给：**从一个受限业务域、一个明确消费方、一条可自动校验的链路开始，用 90 天做出可验收的最小闭环，再谈平台化。**

## 成熟度模型

组织在本体上的能力通常经过四个阶段。先定位自己，再决定下一步，不要跳级。

| 阶段 | 特征 | 关键产出 | 退出条件 |
|---|---|---|---|
| 探索 | 有零散尝试，概念验证为主 | 术语表、小样例本体、技术选型报告 | 找到一个真实痛点与可行技术路线 |
| 试点 | 单域、单消费方、有明确验收指标 | 可运行的本体 + 映射 + 校验 + 一个应用 | 消费方实际使用并给出量化收益 |
| 规模化 | 多域并行，有治理流程与 CI | 模块化本体库、共享词表、角色分工 | 变更可控、多团队复用同一模型 |
| 平台化 | 语义层作为公共基础设施 | 本体注册表、语义 API 网关、SLA | 有稳定运营指标与预算保障 |

常见错误是“探索阶段直接按平台化设计”：还没人用，就先买商业图数据库、设计多租户语义网关。结果预算花完，产出物没人接。**每一阶段的投入应匹配上一阶段验证过的需求**。

## 90 天启动计划

以周为单位，可执行、可交付：

**第 1–2 周：定义问题与范围**

- 访谈 3–5 位业务/技术相关方，收集“因为语义不一致而返工”的具体案例；
- 写出 10 条能力问题（CQ），按价值与可行性排序，选 5 条作为本期验收，写法见 [能力问题（CQ）](/modeling/method/competency-questions)；
- 确定范围：1 个业务域、不超过 3 个源系统、明确不做什么。

**第 3–4 周：复用调研与模型初稿**

- 盘点可复用标准（schema.org、DCAT、行业标准），列取舍理由；
- 建仓库、定命名空间与 IRI 规则，写第一批类与属性，配 `rdfs:label`、`skos:definition`；
- 搭最小技术栈：三元组库（或轻量 oxigraph/RDFLib 起步）+ Git + CI 骨架，见 [技术栈与平台总览](/impl/tech/)。

**第 5–7 周：数据接入与映射**

- 从优先级最高的源系统开始，写映射（R2RML 或程序映射），导入样例数据；
- 用 CQ 查询验证数据可用性，暴露缺失字段与口径问题；
- 记录每条问题的处理方式，形成“语义决策日志”。

**第 8–10 周：校验与消费方对接**

- 写 SHACL 形状，覆盖必填、类型、范围、关键跨实体规则，见 [SHACL 形状约束](/spec/shacl)；
- 上线第一个消费接口：查询 API、检索服务或校验流水线，择一，不要全做；
- 与消费方联调，收集错例。

**第 11–13 周：验收与复盘**

- 对照 5 条 CQ 验收；统计使用量、数据质量、查询延迟；
- 写复盘：哪些决策被证明错误、哪些标准复用有效、下一阶段优先级；
- 决定继续、调整或停止。**允许停止也是成功**，及时止损比硬撑更有价值。

## 团队能力与角色

最小可运行配置是三个人兼职：

- **语义/知识工程师**：建模与形式化、约束设计、CI 配置；
- **数据工程师**：源系统接入、映射实现、数据质量；
- **领域专家**：语义判定与评审，按需参与。

再加一名有决策权的 Owner 负责终审。规模扩大后才需要专职的语义平台团队。

能力建设建议：

- 先用一个真实小项目把“建模 → 映射 → 校验 → 查询”走通，比看教程有效；
- 团队至少有一人熟悉 OWL 与 SHACL 的语义差异（开放世界 vs 封闭世界），这是最常见的知识缺口；
- 不要指望外部顾问交付后就撤场，必须做知识转移，把 CI 与仓库留在自己手里。

## 工具与预算

工具分四类，按需配置：

| 类别 | 起步选择 | 何时升级 |
|---|---|---|
| 建模编辑 | Protégé / WebProtégé | 多团队协作时引入注册表与评审流 |
| 存储与查询 | 单机三元组库（如 Apache Jena TDB2 + Fuseki、Oxigraph） | 数据量与并发上来后评估商业库 |
| 校验与推理 | pyshacl、Jena SHACL、ELK/HermiT | 需要增量推理或规则引擎时评估商业产品 |
| 工程协作 | Git + CI | 规模化后加本体注册表与发布流程 |

预算上要区分三类成本：**软件许可**（开源可零许可费，但需要人力运维）、**人力**（建模与映射通常是主要成本）、**集成与培训**（容易被低估）。商业产品在集群、权限、推理性能、技术支持上有优势，是否值得取决于数据规模与运维能力，不要用“开源一定便宜”做决定——运维成本常常超过许可费。

## 与 DDD 团队、数据团队协作

- **与 DDD 团队**：分工是“业务边界与行为 vs 共享语义与数据互操作”。本体团队不重写领域模型，而是把跨上下文共享的部分抽出来。协作方式：领域模型评审时同步语义决策；防腐层可作为映射入口。参见 [领域驱动设计（DDD）是什么](https://ddd-fans.github.io/ddd-guideline/main) 与 [分层与六边形架构](/impl/arch-pattern/layered)。
- **与数据团队**：数据团队提供源系统与质量基线，本体团队提供术语与映射。最容易冲突的是“谁是主数据权威源”，这件事必须在启动前书面明确。
- **与业务方**：业务方提能力问题、判定语义、验收结果。不要让他们参与 IRI 命名这类技术细节，会消耗耐心。

## 试点选择与验收

选试点的五个标准，满足四条以上再启动：

1. 痛点有基线数据（返工工时、对账差异、查询耗时）；
2. 范围能在 90 天内收敛；
3. 有明确的消费方与使用流程；
4. 源数据可得且质量可接受；
5. 有业务方愿意投入评审时间。

验收标准写成可核对的条目，而不是“完成知识图谱建设”这种描述：

- 5 条 CQ 全部可查询且结果正确；
- 核心实体覆盖率、关键属性填充率达到约定值；
- SHACL 规则全部自动化运行，违规可定位；
- 消费方在生产或准生产环境实际使用，并给出满意度反馈；
- 运营机制就位：Owner、评审节奏、CI、监控指标。

## 推广与组织保障

试点成功后，推广失败仍然是常态。三个保障动作：

- **复用优先**：第二个域优先复用已有模块与词表，避免团队各自建本体。模块化做法见 [模块化与复用](/modeling/elements/module)；
- **流程固化**：变更分级、评审规则、发布说明写进团队规范，见 [运营与生命周期](/application/lifecycle)；
- **价值可视化**：定期展示使用量、质量提升与节省的工时，让投入可见。没有可见价值的项目，预算会最先被砍。

## 常见问题

**必须买商业图数据库吗？** 不必。试点阶段单机开源方案足够，规模与并发上来再评估。

**必须用 OWL 吗？** 从 SKOS 词表起步完全可以，需要推理时再升级。

**没有领域专家怎么办？** 那就先不做语义严谨度要求高的场景，从检索/术语治理起步，等专家可用再推进。

**和现有数据中台冲突吗？** 不冲突。中台管数据加工与服务，本体管语义定义与互操作，通过 ID 与元数据对接。

**怎么衡量成功？** 用消费方使用量、CQ 通过率、质量违规下降、返工工时减少四项组合，不要只看模型规模。

## 启动 Checklist

| 检查项 | 验收证据 |
|---|---|
| 已定位成熟度阶段，并明确本阶段目标 | 一页纸的阶段说明与目标 |
| 已有 10 条 CQ，选定 5 条作为验收 | CQ 清单与查询草稿 |
| 范围限定：业务域、源系统、时间窗口 | 范围声明，含“不做什么” |
| 复用标准已盘点并给出取舍理由 | 标准对照表 |
| 仓库、命名空间、IRI 规则已定 | 仓库 README 与命名规范 |
| 映射方案与责任人已确认 | 映射清单与负责人 |
| SHACL 校验已进入 CI | CI 流水线与最近一次报告 |
| 消费方已确认并参与联调 | 联调记录与反馈 |
| Owner 与评审节奏已书面确认 | 职责说明与例会安排 |
| 验收指标有基线值与目标值 | 指标基线表 |

这十项里，最容易漏的是最后一项与“消费方参与联调”。缺少前者无法证明价值，缺少后者交付即闲置。
