# 知识中台定位与落地

本页回答一个问题：**当"本体建模"被包装成"知识中台"立项后，为什么目标会漂移、领导会误解、业务方会推脱，以及平台如何把这些抽象概念落成可执行、可验收的工程交付。** 配套的两份操作件是 [责任矩阵 + 验收基线模板](./knowledge-midplatform-template) 和 [领导 10 页对齐提纲](./knowledge-midplatform-pitch)。

## 一句话定位

> **知识中台 = 把"业务共识"编译成"机器可执行、人可验证"的语义世界，并让每个业务方同时成为这个世界的定义者和受益者。**

它不是"建一张大图谱"，也不是"又一个数据大屏"。它是一个**语义服务层**：上游接业务共识与源数据，下游向消费方（查询、检索、校验、应用、Agent）提供**可被程序读取、可被门禁验证**的语义状态与能力。

## 为什么"知识中台"这个名字会漂移

三个落地症状，其实是同一个根因：

> "知识中台"被当成一个**技术建设目标**或**一次性文档项目**，而不是一个**有明确消费方、可验收产出、责任到人的工程交付**。

| 症状 | 根因 | 后果 |
|---|---|---|
| 目标不清晰 | 目标写成"建一个中台/图谱"，这是**不可验收**的描述 | 怎么做都对，怎么都不算完 |
| 领导理解不到位 | 交付物是类/属性/关系/公理，看不到业务关联 | 认为是"技术项目、花钱的大屏" |
| 业务方推脱 | "业务方是语义权威来源与验收方"没写进流程和审计 | 责任落不到具体的人和可核对的证据 |

对策不是再做一页"重要性与意义"的 PPT，而是把定位、目标、责任、验收**全部落成平台里可执行、可追溯、可重放的工作对象**。

## 四个边界：用"是/不是"逼出共识

立项会上把这张表贴在墙上，凡写不进"是"这一列的，都不是本期目标：

| 维度 | 知识中台**是** | 知识中台**不是** |
|---|---|---|
| 本质 | 一套共享业务语义（术语表 + 对象/关系模型 + 标准） | 一堆 PPT / 文档 / 没被任何系统读取的模型文件 |
| 产出 | 可被消费方调用的语义状态与能力 | "建完了放在那儿"的图谱 |
| 成功标准 | 消费方使用量 + CQ 通过率 + 质量违规下降 + 返工工时减少 | 模型规模、类/属性数量 |
| 治理方式 | 标准流程 + 硬门禁 + 审计 + 版本 | 靠某个人的自觉或热情 |

## 三个症状 → 平台机制 → 具象动作

| 症状 | 平台机制 | 具象动作 |
|---|---|---|
| 目标不清晰 | CQ（能力问题）+ 范围卡 + 门禁阈值 | 用 5–10 条 CQ 定义"什么算成功"，每条填来源、期望、判定方式、优先级，否则不计入通过率 |
| 领导理解不到位 | 关系图 + 追踪矩阵 + 智能视图 + 验收报告 | 让领导看到一条可点击的线：`CQ → 模型引用 → 样例 → 查询 → 结果 → 证据`，再配一个从真实本体编译出的业务视图做演示 |
| 业务方推脱 | 干系人字段 + 评审记录 + 审计日志 | 每条 CQ 标注来源方；评审结论独立填写；`round.created / round.submitted / cq.created / acceptance.run / review.recorded / round.published` 全部留痕 |

关键：**推进不再靠领导催，而是靠"下一个可发布版本"这个明确的交付节奏**——平台把发布做成硬门禁，推不动 = 门禁红灯，红灯有名有姓、有据可查。

## 平台里的标准流程：八步工程流

本体页第三个页签 `工程流`，把"抽象知识"编译成"具体工作对象"。每一步的产出物和退出条件都是平台里真实存储的字段：

| # | 步骤 | 落成的工作对象 | 退出条件 |
|---|---|---|---|
| 1 | 范围 | 范围卡：一句话目的 + 范围内/外 + 干系人 + 明确不做什么 | 一句话目的 + 至少一个目标应用 |
| 2 | 能力问题 | CQ 清单（5–10 条，每条有来源/判定/优先级） | 不足 5 条标"风险" |
| 3 | 复用调研 | 复用台账：复用/扩展/自建/不复用 + 理由 | 每个候选有决策和理由 |
| 4 | 概念草图 | 术语表 + 类/关系草图 | 领域专家认可术语和主要关系 |
| 5 | 形式化 | 可加载模型 + 语义检查（绑定本体指纹） | 语法通过、每个 CQ 至少有模型引用 |
| 6 | 样例实例 | 样例集（与生产运行态隔离） | 覆盖 P0 CQ 所需对象/关系 |
| 7 | CQ 验证 | 验收运行 + 通过率 + 证据快照 | P0 100%、总体 ≥ 80% |
| 8 | 评审发布 | 检查表 + 版本 + 审计 | 评审通过 + 全部硬检查 |

只有**发布**是硬门禁，其余步骤可自由跳转、回退。改任何一步都会让旧证据自动过期，迫使团队回到真实状态而不是自说自话。

## 可视可验证的三件套

**可视**，给三类人各看一样：

- **关系图**（力导向 / 分层卡片 / 2.5D / 3D + 聚类）：给业务方看"你嘴里的收费站、车辆、门架长什么样、什么关系"；
- **追踪矩阵**（`CQ × 模型 × 样例 × 结果 × 证据`）：给 PM 看"哪条 CQ 断了、断在哪一环"；
- **智能视图**（从真实本体与实例编译出的业务界面）：给领导看"这不是 PPT，是跑在真实语义状态上的界面"。

**可验证**，把"可验证"做成硬门禁而不是事后补材料：

- 验收运行两种引擎：`fixture`（隔离样例上跑）与 `runtime`（已发布真实状态上回归），都给出通过/失败/阻断与错误摘要；
- 每次运行记录**证据包**：查询哈希 + 样例哈希 + 本体指纹 + 结果快照，可重放、可复核；
- 发布前 `publish-check` 给出 blockers / warnings，P0 CQ 全通过 + 总体达标 + 评审通过 + 证据新鲜，缺一不可发布。

## 责任落地：把"推脱"变成"有据可查"

1. **责任前置到范围卡**：第 1 步写干系人，每条 CQ 标来源方与来源类型，不写来源的 CQ 不计入通过率；
2. **评审结论独立记录（maker-checker）**：MVP 允许同一人准备并评审，但自评审只记 warning；团队模式建议强制"评审人 ≠ 最后一位模型编辑者"；
3. **审计全留痕**：领导要的"谁在什么时间做了什么、还差什么"，就是一条自动生成的审计时间线，不需要任何人写周报。

## 90 天路线

| 周 | 动作 | 平台落点 | 验收证据 |
|---|---|---|---|
| 1–2 | 定义问题与范围，选 5 条 CQ | 范围卡 + CQ 清单 | 5 条 CQ 有来源、判定、优先级 |
| 3–4 | 复用调研 + 模型初稿 | 复用台账 + 草图/词表 | 每个候选有决策和理由 |
| 5–7 | 数据接入与映射 | 数据源 + 投影 | CQ 在样例上可查 |
| 8–10 | 校验 + 消费方对接 | 形式化 + 样例 + 验证 | P0 CQ 通过，消费方联调 |
| 11–13 | 验收 + 复盘 | 评审发布 + 报告 | 评审通过、发布新版本、写复盘 |
