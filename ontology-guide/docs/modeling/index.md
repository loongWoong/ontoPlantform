# 建模总览

本体建模不是“画一张概念图”，而是把团队共享的概念体系从文档、表格和人脑里提取出来，写成语义明确、机器可处理、能被多个系统复用的形式化模型。判断一次建模是否真的成立，只看三条：概念被显式定义、定义能被机器解释、模型确实驱动了数据或应用。

这和 DDD 的建模目标一致——用模型解决业务问题——但本体建模多了两个约束：模型必须用标准语言表达，且要能跨系统共享。

## 建模的两个产物：模式与数据

本体建模同时产出两类东西，理解这个划分是后续所有工作的前提：

- **模式（TBox）**：类、对象属性、数据属性、公理。回答“这个领域里有哪些概念、它们如何关联、有什么逻辑规律”。例如“订单至少包含一个订单行”“已取消订单不能发货”。
- **数据（ABox）**：个体与断言。回答“具体有哪些对象、它们之间是什么关系”。例如“订单 ORD-20250301 由客户 C-1001 在 2025-03-01 下单，含两个订单行”。

TBox 与 ABox 的边界不是绝对的。一个“订单状态”集合，既可以建成类层次，也可以建成一组个体，取决于你打算用它做分类推理还是做取值校验。做这个选择时，先问“谁会用它、怎么用”，而不是先问“哪种更标准”。

## 推荐流程：能力问题先行

本指南推荐的轻量流程如下，每一步都有可验收的产物，不追求一次到位：

| 步骤 | 产物 | 完成标志 |
|---|---|---|
| 1. 定范围 | 一页范围说明 | 明确“覆盖什么、不覆盖什么” |
| 2. 写能力问题（CQ） | 5–10 条可判定问题 | 每条都能翻译成查询或校验 |
| 3. 定复用策略 | 复用清单 | 决定哪些用标准词表、哪些自建 |
| 4. 概念草图 | 术语表 + 类与关系清单 | 领域专家能读懂并纠正 |
| 5. 形式化 | Turtle/OWL 文件 | 能加载、能通过一致性检查 |
| 6. 样例实例 | 小规模 ABox | CQ 能跑出预期结果 |
| 7. 验证与评审 | CQ 通过率、问题清单 | 关键 CQ 全部通过 |
| 8. 发布与迭代 | 版本化本体 + 变更记录 | 有维护人、有变更流程 |

关键在于第 2 步和第 6 步：没有 CQ，建模就没有验收标准，最后只能靠“看起来对不对”来评审；没有样例实例，模型就永远停留在纸面，无法证明可用。详细操作见[从零到一本体：建模流程与规范](/modeling/method/process)与[能力问题（CQ）](/modeling/method/competency-questions)。

## 建模与 DDD 建模是什么关系

两者互补，不互相替代：

| 维度 | DDD 建模 | 本体建模 |
|---|---|---|
| 解决的问题 | 边界内的行为、聚合不变量 | 跨边界的共享语义、数据互操作 |
| 核心产物 | 领域模型 + 代码 | 形式化模式（TBox）+ 数据（ABox） |
| 一致性手段 | 聚合内不变量、事务 | 推理器一致性检查 + SHACL 校验 |
| 验证方式 | 用例、测试 | 能力问题、SPARQL 查询、样例数据 |
| 迭代节奏 | 随需求迭代 | 随需求与数据源变化迭代 |

实践中的常见做法是：DDD 负责“业务怎么变、流程怎么走”，本体负责“概念是什么、数据怎么换算”。同类概念可以对齐，例如类与实体/值对象类型、个体与实例、模块与限界上下文、约束与聚合不变量，但不要在一个聚合内部引入 OWL 推理来维护不变量——那是过度设计，见[本体模型是什么、不是什么](/ontology-model)。

## 建模到什么程度算够

从最小可用本体开始，而不是从全量公理开始。一个能支撑 3–5 条 CQ 的本体，通常只需 5–20 个类、10–30 个属性。先让这条链路跑通：模式 → 样例数据 → 查询/校验 → 服务或报表。之后再按需增加类、公理和 SHACL 形状。

需要回答“模型质量如何评估”时，见[质量评估与反模式](/modeling/method/quality)；需要决定用 SKOS、OWL 还是 SHACL 时，见[标准与语言总览](/spec/)。

## 建模最常犯的四个错误

1. **把 ER 图或类图当本体**。图形本身没有共享 IRI、没有形式语义、不能被推理，也无法跨系统复用。它们可以是建模过程中的草图，但不是交付物。
2. **只画图不落地**。没有样例数据、没有查询、没有接入任何系统，模型无法被验证，也无法证明价值。
3. **过度公理化**。一上来写大量等价类、不相交、属性链和基数限制，推理变慢且难以维护；开放世界假设下模型“永远不完整”，靠公理补完整性是错误方向。
4. **无人维护**。本体是长期资产，一次性交付后无人评审、无版本记录，半年后连原建模者都说不清某个类为什么存在。

## FAQ

### 不写代码、只画概念图可以吗？

不可以作为交付形态。概念图可以作为评审材料，但本体必须有可加载的形式化文件，并且至少有一组样例数据和查询能证明它可用。否则无法区分“模型”和“幻灯片”。

### 必须用 OWL 吗？

不一定。只做词表与分类，用 SKOS 更简单；只做数据校验，SHACL 就足够；需要类层次与推理才上 OWL。选型判断见[标准与语言总览](/spec/)，不要为了“标准”而堆标准。

### 必须一次建全整个领域吗？

不需要，也不可能。领域本体会长期演进，第一版覆盖核心场景即可。预留扩展点（模块划分、命名空间）比提前建全更重要，见[模块化与复用](/modeling/elements/module)。

### 没有领域专家怎么建模？

领域专家不一定是“行业专家”，可以是产品经理、资深业务人员，甚至是熟悉业务的工程师。关键是有人能确认术语含义和业务规则。若确实找不到人，用现有系统数据、单据和报表反推，并把假设写进注释，待评审时确认。

### 怎么判断模型够好了？

首要是能力问题通过率，其次是一致性检查通过、术语可理解、复用方愿意用。不要追求公理数量或类图美观，见[质量评估与反模式](/modeling/method/quality)。

### 建模要用什么工具？

编辑器用 Protégé 或 WebProtégé；校验与查询用 Apache Jena、RDF4J 或 pyshacl；存库选三元组库或文件。工具只影响效率，不影响建模是否成立。平台选型见[技术栈与平台总览](/impl/tech/)。
