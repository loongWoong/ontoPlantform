# 模块化与复用

一个本体从小到大必然经历“一个文件写不下”的阶段。模块化不是洁癖，而是让本体可持续演进、可分工、可复用的工程手段。与之相伴的是复用决策：哪些概念应该复用标准词表，哪些必须自建。

## 为什么必须模块化

- **变更隔离**：改订单模块不牵动商品、客户模块，回归范围可控。
- **职责清晰**：每个模块有明确的主题与负责人，评审时知道该找谁。
- **按需加载**：不同应用只需加载自己依赖的模块，减少推理与校验负担。
- **复用与替换**：标准词表可以整体替换或升级，不必动业务模块。
- **发布节奏**：上层本体稳定、领域本体频繁迭代，分开才能各自发版。

反面教材是单体本体：一个上万行的 Turtle 文件，所有人都往里加，没人敢删，推理越来越慢，最后没人能说清某个类为什么存在。

## 三种切分手段

| 手段 | 作用 | 注意 |
|---|---|---|
| 命名空间/IRI | 标识概念归属，避免重名 | 命名空间一旦发布就要稳定 |
| 文件/目录 | 物理组织，便于评审与版本管理 | 一个模块一个文件或一个目录 |
| `owl:imports` | 逻辑依赖，加载时合并公理 | 无“部分导入”，导入即全量生效 |

```turtle
@prefix owl:  <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

<https://example.com/shop/ontology> a owl:Ontology ;
  owl:imports <https://example.com/commons/party> ;
  owl:imports <https://example.com/commons/product> ;
  owl:versionInfo "1.2.0" ;
  rdfs:label "电商领域本体"@zh .
```

`owl:imports` 的语义是“把被导入本体的所有公理视为本本体的一部分”，没有只导入某个类的机制。这意味着**导入一个重型上层本体，推理器就会加载它的全部公理**。复用前先评估载荷，而不是见到标准就 import。

## 怎么划分边界

实用的划分依据有三个，通常组合使用：

1. **稳定性**：上层/基础本体（时间、单位、组织、地理）变化最慢，领域本体居中，应用本体变化最快。依赖方向只能从“易变”指向“稳定”，即应用本体 import 领域本体，领域本体 import 基础本体。
2. **主题**：一个模块一个主题，例如商品、订单、客户、履约。不要按“类一个文件、属性一个文件”切，那样所有变更都会扩散。
3. **所有权**：谁维护、谁评审、谁负责发布。模块边界与团队边界大致对齐，协作成本最低。

依赖图必须无环。循环 import 会让推理器加载顺序不可控，也意味着两个模块实际上应该合并或抽取公共部分。

## 复用标准词表

常见可复用词表及其取舍：

| 词表 | 解决的问题 | 复用方式 | 注意 |
|---|---|---|---|
| schema.org | 商品、订单、组织、事件等通用概念 | 对齐或直接用 IRI | 面广但浅，不足以表达业务规则 |
| FOAF | 人、组织、社交关系 | 直接使用 | 与内部人员模型需要映射 |
| DCAT | 数据目录与数据集描述 | 直接使用 | 适合数据治理场景 |
| PROV-O | 数据来源与处理过程 | 直接使用 | 溯源建模的事实标准 |
| SOSA/SSN | 传感器、观测 | 直接使用 | 物联网场景 |
| SKOS | 受控词表、分类法 | 直接使用 | 不做逻辑推理，见[SKOS 词表与分类法](/spec/skos) |
| ORG | 组织结构与汇报关系 | 直接使用 | 与 HR 系统字段对齐 |
| OWL-Time | 时间区间与时刻 | 直接使用 | 时间区间推理 |
| QUDT/OM | 计量单位与量纲 | 直接使用 | 多单位换算场景 |
| BFO/IAO | 上层本体 | 谨慎复用 | 概念严谨但抽象，学习成本高 |

复用有三种强度，按成本从低到高：

- **只借用 IRI 词表**：在标签、映射关系里引用标准概念，不 import。
- **映射对齐**：自建概念 `owl:equivalentClass` 或 `rdfs:subClassOf` 到标准概念，保留自己的模型。
- **直接 import**：把标准词表作为依赖，自己的个体直接使用其类。

建议：核心业务概念自建（业务规则、流程、字段都在你自己的模型里），外围通用概念尽量复用标准词表。为了一个“地址”概念而 import 整个 schema.org，是典型的过度复用。

## 版本与依赖管理

- **版本化命名空间**：稳定 IRI 用于标识，版本 IRI（如 `.../2025-03/`）用于固定依赖；两者并存。
- **锁定依赖**：`owl:imports` 指向具体版本，避免上游静默变更导致推理结果漂移。
- **语义化版本**：加类、加可选属性通常兼容；删类、改语义、收紧公理不兼容。
- **废弃而不删除**：用 `owl:deprecated true` 加 `rdfs:comment` 说明替代方案，给使用方迁移时间。
- **CI 校验**：每次提交跑一致性检查、SHACL 校验和 CQ 回归，防止“改一处、坏一片”。

版本策略的完整做法见[版本与演进](/impl/arch-pattern/versioning)。

## 与 DDD 限界上下文的对照

| 维度 | 限界上下文 | 本体模块 |
|---|---|---|
| 边界依据 | 领域语言一致性与业务自治 | 概念来源、复用层级与变更频率 |
| 自治方式 | 团队、代码库、发布节奏 | 文件、命名空间、版本 |
| 集成方式 | API、事件、防腐层 | `owl:imports`、映射对齐 |
| 失败模式 | 模型泥球、边界侵蚀 | 单体本体、循环依赖 |
| 共享方式 | 上下文映射、共享内核 | 上层本体、公共词表 |

两者可以对齐但不应简单等同：一个限界上下文内部的本地术语，不一定适合提升为全局本体概念；跨上下文共享的应该是经过对齐的核心概念，而不是某一方的实现细节。方法上的参照见[建模](https://ddd-fans.github.io/ddd-guideline/modeling/)。

## 实践清单

- 每个模块有明确的 owner、版本号、变更记录和导入清单。
- 模块内 IRI 前缀一致，对外暴露的概念都有 `rdfs:label` 与 `rdfs:comment`。
- 禁止循环导入；依赖方向单向。
- 序列化时可以按模块拆文件，加载时合并；发布时整包打版本。
- 模块变更走评审，至少跑一次 CQ 回归。
- 上层与标准词表依赖固定版本，升级单独排期。

## 常见坑

1. **循环 import**：A 导入 B、B 又导入 A，推理器行为不可控。
2. **单体本体**：所有概念挤在一个文件，无法分工与复用。
3. **同名不同义**：两个模块都建了 `Customer` 但含义不同，跨模块查询时张冠李戴。正确做法是使用不同 IRI 并显式映射，而不是随手 `sameAs`。
4. **依赖不锁版本**：上游一改，自己的推理结果和查询全部变化。
5. **过度复用**：为了几个类引入庞大的上层本体，推理成本和理解成本都失控。
