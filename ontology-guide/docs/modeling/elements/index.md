# 本体元素总览

一个可用的本体由五类核心元素构成：类、对象属性、数据属性、个体、公理。加上三类配套元素——约束、注释与元数据、模块——就覆盖了从建模到落地的全部构造。理解每个元素“回答什么问题”，比记住它的 OWL 写法更重要。

## 一张表看清八类元素

| 元素 | 回答的问题 | 主要构造 | 常见错误 | DDD 类比 |
|---|---|---|---|---|
| 类 / 概念 | 领域里有哪些类型？ | `owl:Class`、`rdfs:subClassOf` | 把同义词建成类、类与个体混淆 | 实体/值对象的类型 |
| 对象属性 | 对象之间有什么关系？ | `owl:ObjectProperty`、`owl:inverseOf` | 方向混乱、把外键当语义 | 关联、聚合引用 |
| 数据属性 | 对象有哪些字面量取值？ | `owl:DatatypeProperty`、`rdfs:range` | 用字符串存日期/金额 | 值对象属性 |
| 个体 | 具体有哪些对象？ | `owl:NamedIndividual`、类型断言 | IRI 不稳定、重复个体 | 聚合实例、实体实例 |
| 公理 | 概念体系有什么逻辑规律？ | 等价、不相交、`hasKey`、属性链 | 过度公理化、用公理做校验 | 不变量、规则 |
| 约束 | 数据是否完整、是否合规？ | SHACL 形状 | 用 `rdfs:domain` 当校验 | 聚合不变量、DTO 校验 |
| 注释/元数据 | 给人和机器补充说明与出处？ | `rdfs:label`、`skos:altLabel`、`dcterms:source` | 只写在文档里、不写进模型 | 通用语言词汇表 |
| 模块 | 模型如何切分与复用？ | 命名空间、`owl:imports` | 单体本体、循环导入 | 限界上下文 |

表中的 DDD 类比只是帮助定位，不是等价关系：本体没有封装，也不承担行为实现，把它当成“另一种类图”会立刻走偏。

## 五要素与三配套的关系

- **类 + 对象属性 + 数据属性** 构成 TBox 的骨架，决定“能描述什么”。
- **个体** 构成 ABox，决定“实际描述了什么”。
- **公理** 给骨架附加逻辑语义，让推理器能推出隐含知识。
- **约束** 与公理互补：公理管一致性（不矛盾即可），约束管完整性（缺数据就报错）。这一分工是本体工程里最容易踩坑的地方。
- **注释与元数据** 决定模型可理解、可追溯，是长期维护的成本项。
- **模块** 决定模型能否增量演进和被复用。

## 元素与 OO、ER 的对应与差异

从类图或 ER 图转过来的人，最容易把两套东西按字段一一映射。差异主要在四点：

1. **属性是一等公民**。OWL 属性是独立的 IRI，有自己的 domain、range、逆属性、传递性；类图里的字段只是类的一部分，无法单独被引用和推理。
2. **类没有成员列表**。一个个体属于某类，靠类型断言，而不是“构造函数的参数”。同一个个体可以同时属于多个类。
3. **没有封装与行为**。本体描述“是什么、有什么关系”，不描述“怎么执行”。业务行为仍在代码里，见[实现本体总览](/impl/)。
4. **类型可以推理出来**。借助 `rdfs:subClassOf`、`rdfs:domain/range` 等公理，个体可能被推出新的类型；这在类图里不存在。

## 建模不必一次建全

一个能跑通闭环的最小本体通常只需要：3–5 个类、3–5 个对象属性、2–3 个数据属性、2–3 条公理、1 个 SHACL 形状、10 条左右样例数据。先写这个闭环，再按 CQ 扩展。

推荐的书写顺序是：**类 → 对象属性 → 数据属性 → 公理 → 样例个体 → 约束**。理由很实际：类和关系稳定后才谈公理，有了样板数据才知道约束该写多严。

元素数量不是成熟度指标。一个 20 个类、注释齐全、能力问题全过的本体，比 200 个类、一半没有注释、没人使用的本体有价值得多。

## 元素归属：哪些进本体，哪些进别处

| 内容 | 放在哪 | 说明 |
|---|---|---|
| 类、属性、公理 | 本体文件（`.ttl`/`.owl`） | 稳定、跨系统共享 |
| SHACL 形状 | 独立的 shapes 文件 | 校验规则变化频繁，与模式解耦 |
| 常用查询 | 独立查询文件或用例代码 | 查询是使用方式，不是模式 |
| IRI 常量、命名空间 | 代码常量类/模块 | 避免字符串散落，见[实现本体对象](/impl/objects/) |
| 术语说明与变更记录 | 本体注释 + 版本库 | `rdfs:comment`、`owl:versionInfo` |

## FAQ

### 本体元素等于类图元素吗？

不等于。类图元素以类型和字段为中心；本体元素以可共享的 IRI、属性和可推理语义为中心。类图可以看作本体的一种“面向对象视图”。

### 约束算本体元素吗？

在 OWL 本体本身里没有“约束元素”这一说，`rdfs:domain/range` 与基数限制都是推理公理。真正面向校验的约束由 SHACL 提供，属于本体的配套资产，通常单独维护，见[约束与业务规则](/modeling/elements/constraint)。

### 注释和元数据重要吗？

重要，而且越大的本体越重要。没有 `rdfs:label` 和 `rdfs:comment`，建模者离开后模型就难以维护；没有来源和版本信息，跨团队复用时无法追溯。成本很低，收益很高。

### 每个元素都必须写注释吗？

不必逐个写长篇说明，但四类元素必须有注释：类（一句话界定范围）、对外属性（业务含义与单位）、公理（为什么需要它）、公共个体（状态、币种的取值含义）。私有、临时、只在一个查询里用到的元素可以只保留 label。判断标准是“半年后新人能否不问人就看懂”。

### 要不要把领域里所有个体都建出来？

通常不要。个体一般来自业务数据库、主数据或 ETL，不应手工维护成百上千条。本体先定模式与关键参考数据（状态、单位、类目），批量实例由数据管道生成，见[个体与实例数据](/modeling/elements/individual)。
