# 本体工程方法论

本体不是一次性的建模作业，而是要被系统长期使用、被多人维护、被反复扩展的资产。既然它是资产，就需要工程方法：明确范围、有验收标准、能评审、可版本化。否则最常见的结局是“画了半年类图，上线时没人用”。

本页给出方法论谱系、推荐的轻量流程、角色分工，以及与 DDD 建模流程的对照。具体操作见 [建模流程与规范](/modeling/method/process)，验收见 [能力问题](/modeling/method/competency-questions)，质量见 [质量评估与反模式](/modeling/method/quality)。

## 为什么本体需要工程方法

直接打开 Protégé 开始建类，通常会在三个地方出问题：

- **范围失控**：什么都想建，类越来越多，却回答不了任何一个具体业务问题；
- **没有验收**：模型“看起来对”，但没有可执行的检查，缺陷要到数据接入后才暴露；
- **无法演进**：没有版本、没有评审、没有文档，第二次修改就没人敢动。

工程方法解决的正是这三件事：先定边界，再定验收，最后用流程保证可持续。

## 方法论谱系

| 方法论 | 大致年代 | 核心主张 | 对本指南的价值 |
|---|---|---|---|
| Ontology Development 101 | 2001 | 从领域与范围出发，列术语、建类层次、定属性、造实例，迭代推进 | 最小可操作的入门流程 |
| METHONTOLOGY | 1997 | 覆盖规格说明、概念化、形式化、实现、维护的完整生命周期 | 提醒我们维护阶段同样重要 |
| On-To-Knowledge | 1999–2002 | 面向知识管理，强调应用场景驱动 | 本体要服务于具体应用 |
| NeOn | 2012 | 网络化本体工程，强调复用、分布式协作与场景化方法 | 复用优先、模块化协作 |
| 敏捷 / XD | 2000s 末起 | 用例驱动、小步迭代、模式复用 | 小团队落地最实用 |

这些方法论并不互斥。实践中推荐“101 的骨架 + 敏捷的节奏 + NeOn 的复用意识”：流程轻、反馈快、能长期维护。

## 推荐轻量流程

| 步骤 | 产出 | 退出条件 |
|---|---|---|
| 1. 确定范围 | 领域边界、目标应用、不做什么 | 一句话说清“这个本体为谁回答什么问题” |
| 2. 编写能力问题 | CQ 清单（首批 5–10 条，扩展期 10–30 条） | 每条都能判定、能追溯到来源 |
| 3. 复用调研 | 可复用标准/本体清单与取舍 | 明确“用哪些、不用哪些、为什么” |
| 4. 概念草图 | 术语表、类与关系草图 | 领域专家认可术语与主要关系 |
| 5. 形式化 | Turtle/OWL 模型、命名空间与 IRI | 语法通过、可被工具加载 |
| 6. 样例实例 | 覆盖 CQ 的样例数据 | 每条 CQ 都有可验证的数据 |
| 7. CQ 验证 | SPARQL 验收查询与结果 | 目标 CQ 通过率达到约定阈值 |
| 8. 评审发布 | 评审记录、版本与变更说明 | 评审通过并打版本号 |

八个步骤不是瀑布，而是螺旋：每轮聚焦一批 CQ，发布一个小版本，再进入下一轮。第一轮的目标不是“建全”，而是“打通一条从模型到查询的链路”。

```text
范围 → CQ → 复用调研 → 概念草图 → 形式化 → 样例实例 → CQ 验证 → 评审发布
  ▲                                                              │
  └──────────────────── 下一轮迭代 ◀─────────────────────────────┘
```

## 与 DDD 建模流程的对照

| 维度 | DDD 建模 | 本体工程 |
|---|---|---|
| 起点 | 业务问题与领域专家 | 能力问题与应用场景 |
| 主要产出 | 领域模型、聚合、领域事件、限界上下文 | 类、属性、公理、个体、形状约束 |
| 关注点 | 行为、边界、一致性、演进 | 共享语义、数据互操作、推理与校验 |
| 典型工作坊 | 事件风暴 | CQ 工作坊、术语对齐会 |
| 验证方式 | 代码实现、测试、可运行系统 | SPARQL CQ 验收、推理一致性、SHACL 校验 |
| 关系 | 管“系统怎么做事” | 管“数据与概念是什么意思” |

两者是互补关系。事件风暴产出的领域事件、聚合和限界上下文，可以作为本体的输入；本体产出的统一术语与语义层，也能反过来约束 DDD 的通用语言。熟悉 [DDD](https://ddd-fans.github.io/ddd-guideline/main) 的读者可以把本体理解为通用语言的形式化延伸，但不要把聚合边界直接画成类层次：DDD 关注行为与边界，本体关注数据与概念的含义。

## 角色分工

- **本体工程师**：负责形式化、命名规范、推理与校验流水线，是模型质量的第一责任人。
- **领域专家**：提供术语、口径、边界与反例，参与 CQ 评审与模型验收。
- **数据工程师**：负责数据映射、ETL/ELT 管道、实例质量与性能。
- **架构师**：决定语义层在系统中的位置、存储与推理策略，见 [实现总览](/impl/)。
- **产品/治理角色**：决定优先级、预算与推广节奏，见 [落地路线图](/adoption/)。

小团队可以一人多角色，但“谁对术语拍板”必须明确；没有拍板人，术语会随会议记录漂移。

## FAQ

**能不能不写 CQ，直接写 OWL？**
小范围、个人项目可以，但团队协作和长期维护建议首批至少写 5–10 条 CQ。CQ 是最便宜的需求文档，也是唯一能自动验收的部分。

**必须写文档吗？**
至少要有：IRI 规范、类与属性的定义、典型实例、CQ 清单。只靠模型文件，新成员无法理解设计意图。

**领域专家没时间怎么办？**
用 CQ 访谈代替长会：每次一小时，只确认 5–10 条问题与术语，回去建模，下次带结果来。不要等“专家有空”才开始。

**第一版要建多全？**
只建能通过第一批 CQ 所需的最小集合。模型是长出来的，不是一次设计完的。

**要不要追求完美模型？**
不要。不存在唯一正确的本体，只有对当前问题够用、且能演进的模型。过度设计比不设计更难维护。

## 常见失败模式

- **一次性项目**：交付模型文件后无人维护，半年后与业务脱节。
- **建模与数据脱节**：模型里有的属性，源系统根本没有数据；或数据有，模型没建。
- **只建模不验收**：没有 CQ 查询、没有校验，问题全部推迟到上线后。
- **过度形式化**：全量 OWL DL 公理，推理慢、没人看得懂，最后被弃用。
- **跳过复用**：把 schema.org、行业标准里已有的概念重新造一遍。
