# 质量评估与反模式

判断一个本体好不好，不能只看类图画得整不整齐。质量要能被检查：一致性、可满足性、覆盖度、可理解性、可维护性，每一项都有对应的检查手段。这一页给出评估维度、OntoClean 的用法、评审清单，以及最常见的反模式与修复方式。

## 质量维度

| 维度 | 含义 | 检查手段 |
|---|---|---|
| 一致性（consistency） | 公理之间不矛盾 | 推理器一致性检查 |
| 可满足性（satisfiability） | 没有不可满足的类 | 推理器列出不可满足类 |
| 覆盖度（coverage） | 能回答目标 CQ | CQ 通过率 |
| 可理解性（comprehensibility） | 人能看懂命名、定义与结构 | 评审、术语表、文档 |
| 可复用性（reusability） | 模块边界清晰、少耦合 | 模块依赖检查 |
| 可维护性（maintainability） | 变更影响可控、有版本 | 变更历史与回归测试 |
| 数据契合度 | 源数据能映射进来 | 样例数据与映射验证 |

其中前两项是“硬失败”，必须为零；覆盖度决定本体是否有用；其余决定它能否长期活下去。

## OntoClean：用元属性检查 is-a

OntoClean（Guarino 与 Welty 提出）用四个元属性判断分类层次是否合理，是评估 `subClassOf` 最有效的工具：

- **刚性（rigidity）**：一个类是否对其实例必然成立。`Person` 是刚性的（人必然是人），`Student`、`Employee`、`Customer` 是非刚性的（可能只是某个阶段扮演的角色）。
- **同一性（identity）**：类是否提供判定“两个实例是否同一个”的标准。
- **统一性（unity）**：实例是否有明确的整体边界，例如 `Person` 有，`AmountOfWater` 没有。
- **依赖性（dependence）**：实例的存在是否依赖另一个实例，例如 `Husband` 依赖 `Wife`。

最常用的规则是：**非刚性类不能包含刚性类作为子类**。`Person rdfs:subClassOf Student` 是错误建模，因为人有不是学生的时候；反过来 `Student rdfs:subClassOf Person` 是允许的，但要注意角色类会带来“同一实体在不同时间扮演不同角色”的问题。角色、状态这类非刚性概念，更适合用 [角色模式](/modeling/patterns) 表达，而不是永久改变实例的类型。

同一性冲突也常见：把按 SKU 识别的 `Product` 与按 ISBN 识别的 `Book` 做成父子类，会让子类继承错误的身份标准。正确做法是拆开或用映射表达“一本书也是一种商品”。

## 推理器一致性检查

推理器能发现两类问题：本体矛盾（inconsistent ontology）与不可满足类（unsatisfiable class）。后者更隐蔽：整个本体一致，但某个类永远不可能有实例。

```turtle
@prefix ex:  <https://example.com/ontology/hr#> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

ex:Employee a owl:Class ;
    rdfs:subClassOf ex:Person ;
    owl:disjointWith ex:Person .
```

这段模型语法正确、能加载，但 `Employee` 被声明为 `Person` 的子类又与 `Person` 不相交，因此它不可能有实例。推理器会报出不可满足类；如果不跑推理，这个错误可能潜伏很久。

实践建议：每次模型变更都在 CI 中跑一次推理一致性检查；用 OWL API、Jena 推理模型或对应语言的推理库都行；对关键公理保留“为什么加”的记录，避免后人不敢删也不敢改。

## CQ 通过率

覆盖度用 CQ 通过率量化：

```text
CQ 通过率 = 已通过的 CQ 数 / 纳入本版本范围的 CQ 数 × 100%
```

“通过”指 CQ 对应的 SPARQL 查询在样例数据上返回预期结果，且查询本身能在模型上执行。建议每轮迭代记录通过率与失败原因，形成趋势而不是一次性数字。发布阈值应由团队结合 CQ 难度与范围自定；例如首版以 80% 通过率作为门槛只是一个常见示例，剩余未通过项进入下一轮。

## 评审清单

| 检查项 | 合格标准 |
|---|---|
| 命名 | 类大驼峰单数、属性小驼峰、IRI 稳定、无中文与空格 |
| 定义 | 每个类与属性有 `rdfs:comment`，术语表有条目 |
| 标签 | 有 `rdfs:label`，多语言场景有语言标签 |
| 层次 | 无循环 `subClassOf`，无万能父类，角色与类型分开 |
| 公理 | 每条公理有明确推理目的，无冗余的 `domain`/`range` |
| 约束 | 必填、范围、格式由 SHACL 表达，而非 OWL |
| 实例 | 样例数据覆盖 CQ 的正常与边界情况 |
| 验证 | 推理器无矛盾、无不可满足类；CQ 查询通过 |
| 文档 | README、术语表、CQ 清单、变更日志齐备 |
| 版本 | 有版本号、`owl:versionIRI` 与弃用说明 |

## 常见反模式

**类/实例混淆**：把“北京”建成类、把“中国”建成类，然后困惑为什么无法查询具体城市。修复：具体对象建个体，只有需要分类的集合才建类。

**同义词建类**：`Customer` 与 `Client` 两个类，指同一概念。修复：保留一个类，另一个用 `skos:altLabel` 或注释记录，合并 IRI。

**过度公理化**：追求“语义完备”，加上大量不相交、全称限制、属性链，推理变慢且数据一有噪声就整体不一致。修复：公理按推理价值排序，只保留必要的；约束交给 SHACL。

**循环定义**：`A subClassOf B` 且 `B subClassOf A`，或 `equivalentClass` 成环。修复：这类循环通常意味着两个概念重复，应合并。

**元建模滥用**：用 punning（同一个 IRI 既是类又是个体）表达“类型本身也有属性”，结果推理语义混乱。修复：区分元层与对象层，必要时用注释或显式的元类模式。

**把属性当类**：把“颜色”建成类、把“红色”建成类，再让商品 `rdf:type ex:Red`。修复：颜色作为数据属性或 SKOS 概念，商品指向概念个体；只有当“颜色”本身有属性需要描述时才升级为类。

**万能上层类**：所有东西都挂在一个 `Thing` 下，层次没有信息量。修复：按业务语义分层，允许存在多个顶层类。

**`domain`/`range` 当校验**：期待类型推断报错。修复：需要校验就写 SHACL；`domain`/`range` 只用于推理。

**模型与数据脱节**：模型里有 `ex:warehouse`，但源系统根本没有仓库字段。修复：在建模阶段做数据可行性检查，样例数据必须真实可映射。

**无文档、无版本**：模型文件即全部。修复：最小文档集 + Git + CI 门禁。

## 持续评估

把质量检查固化进流水线，而不是依赖评审会：

1. 语法检查：Turtle 可解析、IRI 可解析；
2. 推理检查：无矛盾、无不可满足类；
3. 形状校验：SHACL 在样例与真实数据上通过；
4. CQ 回归：查询结果符合预期；
5. 评审门禁：命名、定义、文档 checklist 通过；
6. 版本记录：变更说明与弃用项完整。

指标上同时跟踪 CQ 通过率、校验失败率、不可满足类数量与查询性能，形成趋势图。质量不是一次评审的结论，而是每次提交都被验证的常态。接下来进入具体建模手法： [本体设计模式](/modeling/patterns)。
