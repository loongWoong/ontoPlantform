# 从零到一本体：建模流程与规范

前两页讲了方法论与 CQ。这一页把流程落到实处：从一张空白画布，到可评审、可发布、可维护的第一版本体。重点是可操作的步骤、IRI 与命名规范、Protégé 操作要点，以及团队协作时的差异。

## 1. 确定范围与复用策略

先用一段话写清范围，包含四件事：**为谁、回答什么问题、数据从哪来、不做什么**。例如：

> 为订单履约团队回答“订单当前状态、明细构成、发货与异常”相关问题；数据来自订单库与仓储系统；不覆盖支付清结算与售后。

范围确定后立刻做复用调研，不要从零造概念：

| 策略 | 适用情况 | 代价 |
|---|---|---|
| 直接复用 | 领域通用概念，标准质量高（如 `schema.org` 的商品、组织、时间） | 受标准表达方式约束 |
| 引入上层本体 | 需要严格分类与互操作（如 BFO、IAO、SOSA/SSN） | 学习成本与推理负担 |
| 仅做映射 | 外部标准与内部模型不一致，但需要交换 | 需要维护映射与转换 |
| 完全自建 | 业务特有概念，标准未覆盖 | 需要自己保证质量与文档 |

复用的原则是“能映射就不引入，能引入就不重造”。引入一个上层本体意味着接受它的公理体系与推理后果，不是加几行 `owl:imports` 那么简单。复用与模块化细节见 [模块化与复用](/modeling/elements/module)。

## 2. 术语表与命名规范

在写任何 Turtle 之前，先建术语表：中文术语、英文术语、定义、同义词、来源、负责人。它是模型与业务方之间的契约，也是后续多语言标签的来源。

**IRI 设计**建议遵循以下约定：

- 本体基址用稳定的 HTTPS 域名，例如 `https://example.com/ontology/order#`；
- 单一文档内的词汇用 `#` 片段，跨文档的模块用 `/` 路径，便于按文件拆分；
- 本体自身有 IRI（`owl:Ontology`），每个发布版本有 `owl:versionIRI`，术语 IRI 保持稳定；
- 类用大驼峰单数（`Order`、`OrderLine`），对象属性用小驼峰动词或介词（`placedBy`、`contains`），数据属性用小驼峰（`orderAmount`）；
- 个体用业务标识（`.../order/1001`），不要用自增数据库 ID 或随机串；个体 IRI 与本体 IRI 分属不同命名空间；
- 不要用中文或空格做 IRI，不要频繁改 IRI，弃用用 `owl:deprecated` 标记而不是删除。

```turtle
@prefix ex:      <https://example.com/ontology/order#> .
@prefix owl:     <http://www.w3.org/2002/07/owl#> .
@prefix rdfs:    <http://www.w3.org/2000/01/rdf-schema#> .
@prefix dcterms: <http://purl.org/dc/terms/> .

ex: a owl:Ontology ;
    dcterms:title       "订单本体"@zh , "Order Ontology"@en ;
    dcterms:description "订单、明细、履约状态的概念模型。"@zh ;
    owl:versionInfo     "0.3.0" ;
    owl:versionIRI      <https://example.com/ontology/order/0.3.0> .
```

## 3. 概念草图

草图阶段只做两件事：列出类、列出主要关系。不要过早设计属性类型和基数，更不要直接开 Protégé。白板或绘图工具都可以，但要保证每张图都能标出它服务哪几条 CQ。

草图评审的检查点是：术语是否与业务一致、有没有把角色/状态/事件误画成类、主要关系方向是否清楚。这一步改起来最便宜，到了形式化阶段再改成本就高了。

## 4. 形式化

形式化按“类 → 对象属性 → 数据属性 → 少量公理 → 形状约束”的顺序推进：

- 先定类层次，只保留有业务意义的父类，避免为了“整齐”造中间层；
- 对象属性必须有 `rdfs:domain` / `rdfs:range`，但要记住它们是推理公理，不是校验；
- 数据属性选定 XSD 类型，金额用 `xsd:decimal`，时间用 `xsd:dateTime` 并统一时区；
- 公理从 [OWL profile](/spec/owl) 的 EL 或 RL 起步，只加有推理价值的少数几条；
- 校验需求另写 [SHACL 形状](/spec/shacl)，不要塞进 OWL。

Protégé 的操作要点：新建本体时填好本体 IRI；在 Entities 页建类与属性；对象属性面板设置 domain/range、逆属性与特征；用内置推理器（如 HermiT）启动一致性检查；用 DL Query 页验证类表达式；最后另存为 Turtle 并提交到 Git。WebProtégé 适合多人评审与评论，但不适合复杂编辑。

## 5. 样例实例

为每条首批 CQ 准备 3–10 个代表性实例，覆盖正常情况、边界情况与“应该查不到”的情况。样例数据单独放一个文件（如 `examples.ttl`），不要与模型混在一起。样例有两个用途：验证模型能否装下真实数据，以及为 CQ 查询提供回归基线。

## 6. CQ 验证

把 [能力问题](/modeling/method/competency-questions)对应的 SPARQL 查询与期望结果放进自动化测试：

```bash
# 模型语法检查
riot --validate ontology.ttl

# 数据形状校验
pyshacl -s shapes.ttl -d examples.ttl -f human
```

推理一致性检查可以通过 OWL API + HermiT、Jena 的推理模型或对应语言的推理库完成，不一定有现成命令行。企业环境通常会把语法检查、推理器、SHACL 与 CQ 查询放进同一条 CI 流水线。任何一项失败就阻断合并，这比人工评审可靠。

## 7. 评审与发布

评审至少覆盖：术语准确性、IRI 与命名、公理必要性、CQ 通过率、文档完整性。发布时打语义化版本号（如 `0.1.0` → `0.2.0`），写变更说明与弃用项，保留 `owl:versionIRI`。版本与兼容性策略见 [版本与演进](/impl/arch-pattern/versioning)。

## 8. 文档化

最小文档集包括：README（范围、如何使用）、术语表、CQ 清单、模型图、典型查询、变更日志。文档不需要长篇大论，但必须能让新成员在半小时内知道“这个本体解决什么问题、从哪开始看”。

## 小团队与大团队的差异

| 维度 | 小团队 | 大团队 |
|---|---|---|
| 流程 | 一人多角色，1–2 周一轮 | 分模块并行，双周评审 |
| 评审 | 领域专家 + 一名工程师即可 | 设立本体委员会与发布门禁 |
| 工具 | Protégé + Git + 本地校验 | WebProtégé、注册表、CI 流水线 |
| 复用 | 优先 schema.org 等轻量标准 | 引入上层本体与行业标准，建立映射治理 |
| 风险 | 无人维护、文档缺失 | 模块冲突、版本失控、评审瓶颈 |

## 常见风险

- **范围蔓延**：所有需求都往本体里塞，版本永远发不出去。用 CQ 优先级控制。
- **命名漂移**：不同人给同一概念起不同名字，合并时才发现。术语表是唯一裁决。
- **只建模不验证**：没有 CI，缺陷全部留到集成阶段。
- **复用陷阱**：引入庞大上层本体后推理变慢、团队看不懂，最后整体弃用。
- **文档滞后**：模型改了文档没改，新成员按旧文档建模。

把上面每一步的产出物固定下来，流程就自然可重复。下一节从质量角度检查这个流程产出的模型是否靠谱： [质量评估与反模式](/modeling/method/quality)。
