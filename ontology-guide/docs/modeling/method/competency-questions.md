# 能力问题（CQ）

能力问题（Competency Question，CQ）是本体必须能够回答的问题。它是需求与验收之间的桥梁：向上承接业务诉求，向下变成可执行的 SPARQL 查询与样例数据。没有 CQ 的本体项目，最后只能靠“大家觉得模型对不对”来验收。

这个概念最早出现在 TOVE 项目中，后来成为本体工程的标准实践。方法很简单：先写出你想让本体回答的问题，再检查模型是否回答得出来。

## 什么是 CQ

一条好的 CQ 长这样：

> 给定一个客户，列出他最近 90 天内下单、尚未发货的订单及其金额。

它同时具备三个特征：有明确的输入（客户）、有明确的输出（订单列表与金额）、结果可以被验证（查出来的数据对不对）。CQ 不是抽象目标（“支持客户管理”），也不是技术任务（“建立客户表”），而是**一个能被具体回答的领域问题**。

CQ 清单本质上就是本体的功能需求文档。模型建成什么样，取决于你要回答哪些问题；反过来，每条 CQ 都应该能在模型上写出查询。

## 好 CQ 的标准

- **面向用户语言**：用业务方的说法描述，不出现 `owl:Class`、`rdf:type` 这类词。
- **可判定**：能写出查询，或有明确的判定方式；含糊的“是否合理”不合格。
- **范围明确**：输入、输出、时间范围、边界条件写清楚。
- **覆盖边界**：除了正常情况，还要有“没有数据”“跨多个对象”“不满足条件”的问题。
- **粒度适中**：一条 CQ 对应一个查询或一组紧密相关的查询，不要一条包住整个系统。
- **可追溯**：标明来源（谁提的、对应哪个业务场景），便于后续评审。

反例与改写的对比：

| 不合格 | 问题 | 改写 |
|---|---|---|
| 系统要支持商品管理 | 不可判定 | 给定商品 ID，返回它的类目路径与当前售价 |
| 列出所有类 | 技术查询，不是业务问题 | 某商品属于哪些一级类目 |
| 订单是否合规 | 太笼统 | 某订单是否存在“未支付却已发货”的明细 |
| 客户重要吗 | 无客观标准 | 近 12 个月消费额排名前 10% 的客户有哪些 |

## 示例一：电商

- **CQ-01**：给定客户，列出其近 90 天内下单且尚未发货的订单及金额。
- **CQ-02**：给定商品，找出所有包含该商品的进行中订单（反向查询）。
- **CQ-03**：某订单的应付总额是否等于其明细金额之和？列出不一致的订单。
- **CQ-04**：哪些客户在同一订单中同时购买了商品 A 与商品 B？
- **CQ-05**：给定仓库，列出受其库存影响的未发货订单。

CQ-03 是典型的“跨对象一致性”问题，它逼迫模型同时具备订单总额与明细金额两个属性，并能做聚合比较：

```sparql
PREFIX ex: <https://example.com/ontology/order#>

SELECT ?order ?declared (SUM(?lineAmount) AS ?calculated)
WHERE {
  ?order a ex:Order ;
         ex:orderAmount ?declared .
  OPTIONAL {
    ?order ex:contains ?line .
    ?line  ex:lineAmount ?lineAmount .
  }
}
GROUP BY ?order ?declared
HAVING (SUM(?lineAmount) != ?declared)
```

如果模型里没有 `ex:lineAmount`，或者明细与订单之间没有可连接的属性，这条查询就写不出来——这就是 CQ 在暴露模型缺口。

## 示例二：制造

- **CQ-11**：给定成品，列出其 BOM 的全部下级零件及累计用量（多级展开）。
- **CQ-12**：某零件发生工程变更时，影响哪些在产工单与已排产订单？
- **CQ-13**：给定设备与工序，当前适用的工艺参数版本是哪一个？
- **CQ-14**：某供应商的来料最近一次质检不合格，涉及哪些批次与成品？

制造场景的 CQ 往往涉及层次结构与时间版本：BOM 展开需要属性路径或递归查询，工艺参数需要区分“生效区间”，供应商追溯需要串起批次与成品。这些正是 [设计模式](/modeling/patterns) 中的部分-整体模式与时间区间模式要解决的问题。

## CQ 与用例、用户故事、验收标准的关系

| 形式 | 关注点 | 与本体的关系 |
|---|---|---|
| 用户故事 | 谁、想要什么价值 | 提供 CQ 的来源与优先级 |
| 用例 | 交互流程与系统行为 | CQ 通常对应用例中的信息需求 |
| 验收标准（AC） | 功能行为是否可测 | 关注“系统做什么”，CQ 关注“数据能回答什么” |
| 能力问题（CQ） | 本体能否回答某个领域问题 | 直接转化为 SPARQL 验收查询 |

一句话区分：AC 验证系统行为，CQ 验证模型表达能力。两者可以互相推导，但不能互相替代。

## 把 CQ 转成验收查询

流程固定为五步：

1. 选一条 CQ，写出输入与期望输出；
2. 在模型中识别所需的概念、属性与路径；
3. 写 SPARQL 查询；
4. 准备覆盖该 CQ 的样例实例数据；
5. 把查询与期望结果放进自动化测试，每次模型变更都回归。

查询写不出来，说明模型缺元素；查询能写但结果为空，说明样例数据没覆盖或映射有问题；查询结果与预期不符，说明模型语义或数据有问题。三类失败分别对应不同的修复动作，比笼统的“模型评审”有效得多。

## 维护 CQ 清单

CQ 是活的资产，建议用一张表管理，并纳入版本控制：

| 字段 | 说明 |
|---|---|
| ID | CQ-01 这样的稳定编号，不复用 |
| 问题 | 一句话，业务语言 |
| 来源 | 业务方、法规、系统需求或数据治理诉求 |
| 优先级 | 必须有 / 应该有 / 可以有 |
| 验收查询 | SPARQL 文件路径或查询 ID |
| 样例数据 | 覆盖该 CQ 的数据集标识 |
| 状态 | 待建模 / 已通过 / 阻塞 / 废弃 |
| 负责人 | 模型负责人与数据负责人 |

指标上可以跟踪“CQ 通过率”：已通过 CQ 数 / 纳入范围的 CQ 数。它比类数量更能说明本体是否真的可用。

## 常见错误

- **CQ 写成技术查询**：“查询所有 `owl:Class`”不是能力问题，是调试语句。
- **CQ 太笼统**：“支持全渠道订单管理”无法验收，也无法建模。
- **只写正向问题**：忽略空结果、边界值、异常路径，模型会在真实数据上翻车。
- **CQ 与模型脱节**：CQ 写完就存档，从不执行查询，等于没有。
- **CQ 数量失控**：几十上百条不分优先级，项目永远无法收敛。首批控制在 5–10 条，扩展期再逐步增加到 10–30 条，并持续做优先级排序。
- **忽略数据可得性**：模型能回答，但源系统没有数据，等于不可用。

## 小结

CQ 是本体工程里投入产出比最高的一步：几页问题清单，就能同时解决范围、验收和沟通三个问题。先写 CQ，再建模型；先跑查询，再谈发布。接下来按 [建模流程与规范](/modeling/method/process) 把 CQ 落成模型。
