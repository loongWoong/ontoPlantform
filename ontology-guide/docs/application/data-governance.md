# 数据治理与主数据

数据治理最常见的失败不是缺工具，而是**缺一套共享语义**：业务说“客户”、报表说“会员”、风控说“主体”，三份口径互不一致，对账永远对不完。本体在这里的角色是**把术语、结构、规则和来源变成机器可读的资产**，让治理措施能被自动执行。

## 本体作为共享语义层

治理工作中的四个落点，都可以由本体承载：

| 落点 | 传统做法 | 本体做法 |
|---|---|---|
| 业务术语表 | Excel / Wiki 词条 | SKOS 概念 + 定义 + 同义词 + 责任方，可查询 |
| 数据字典 | 表结构文档 | 数据属性 + 取值域 + 与业务概念的映射 |
| 数据目录 | 治理平台元数据 | DCAT 描述数据集/服务 + 本体标注 |
| 血缘与来源 | 平台自动采集 | PROV-O 表达派生关系，跨平台可合并 |

关键在于**机器可读**：术语表写在 Wiki 里，只能靠人查；写成 SKOS 后，检索系统、校验流水线、BI 工具都能读。这就是本体与文档的本质差别。

## 业务术语表：从 SKOS 起步

不需要一上来就用 OWL。术语表阶段用 SKOS 就够：

```turtle
@prefix skos: <http://www.w3.org/2004/02/skos/core#> .
@prefix ex:   <https://example.com/glossary/> .

ex:Customer a skos:Concept ;
    skos:prefLabel "客户"@zh , "Customer"@en ;
    skos:altLabel  "用户"@zh , "会员"@zh , "客户主体"@zh ;
    skos:definition "与本公司签署销售合同并承担付款义务的法人或自然人。"@zh ;
    skos:broader ex:Party ;
    skos:related ex:Contact ;
    skos:notation "CUST" .
```

三条纪律：

- **定义要能判定**：写“签署销售合同并承担付款义务”，而不是“购买产品或服务的人”。前者能判断真假，后者不能；
- **同义词必须收全**：`altLabel` 直接决定检索与实体链接的召回率，是治理工作中投入产出最高的部分；
- **标注责任方**：用 `dcterms:owner` 或自定义属性记录术语的负责人与评审状态，否则术语会随人员流动而失管。

当术语需要参与推理（如“客户”是“交易方”的子类，且与“供应商”不相交），再升级为 OWL 类。升级路径见 [SKOS 词表与分类法](/spec/skos) 与 [本体元素总览](/modeling/elements/)。

## 数据目录：用 DCAT 描述资产

数据目录要回答“有什么数据、谁负责、怎么取、多久更新”。DCAT 是 W3C 的目录词汇标准，用 `dcat:Dataset`、`dcat:Distribution`、`dcat:DataService` 等描述数据集及其分发形式，可以直接复用，不必自造。

落地要点：

- **数据集与本体概念对齐**。每个数据集标注它覆盖的业务概念（`dcterms:subject` 指向 SKOS 概念），这样业务方能从“客户”反查有哪些数据源；
- **目录自动采集优先**。手填目录必然过期。能从元数据系统、数据库、对象存储采集的字段就自动采；
- **目录要能被查询**。用 SPARQL 端点提供“某个概念对应哪些数据集”的查询，比让人翻网页有效。

## 血缘与来源：PROV-O

数据血缘用 PROV-O（W3C 推荐）表达：`prov:Entity`（数据）、`prov:Activity`（加工过程）、`prov:Agent`（系统或人）、`prov:wasDerivedFrom` / `prov:wasGeneratedBy`。

治理价值在于**跨平台合并**：ETL 工具、调度系统、报表工具各记一套血缘，只有用统一模型才能串成完整链路。实践建议：

- 血缘粒度先到“表/数据集”级，不要一开始追求字段级；
- 血缘要能回答“这个指标出错，影响哪些报表和下游系统”，这是最常被问的问题；
- 血缘数据本身也要有质量：加工任务重跑、改名、废弃都会让血缘失真，需要定期校准。

## 质量规则：SHACL 承载可执行约束

治理规则最怕“写了不执行”。把规则写成 SHACL 形状，就能挂到 CI 或调度任务里自动跑，输出可定位的违规报告。示例见 [SHACL 形状约束](/spec/shacl)。

规则分层放置：

- **结构/取值规则**（必填、类型、范围、格式）→ SHACL；
- **跨实体一致性**（订单金额 = 明细之和）→ SHACL-SPARQL 或独立校验任务；
- **业务不变量**（一个订单只能属于一个客户）→ 部分可由 OWL 基数公理或 key 表达，但要注意开放世界的语义差异，见 [公理](/modeling/elements/axiom)；
- **统计型监控**（空值率、分布漂移）→ 数据质量平台，不必塞进 SHACL。

严重级别（`sh:severity`）要区分：`sh:Violation` 阻断发布，`sh:Warning` 记录待修，`sh:Info` 仅提示。全部设为 Violation 会导致没人看报告。

## 主数据建模

主数据（客户、产品、供应商、组织、物料）是治理的核心对象，也是本体最容易见效的地方：

1. **确定主数据实体的唯一标识**：优先复用行业编码（如商品条码、统一社会信用代码），没有就设计稳定内部编码；
2. **划分来源优先级**：每个属性指定权威源系统（source of truth），冲突时按优先级取值，不要把合并逻辑散落在代码里；
3. **跨系统映射独立维护**：源系统 ID 与主数据 ID 的映射表是长期资产，变更要留版本；
4. **属性分级**：核心属性（名称、编码、状态）严格校验；描述属性宽松处理，避免因细节阻塞主数据发布。

主数据建模与 DDD 的对应关系：主数据实体大致对应跨上下文的共享内核，而各业务上下文仍保留自己的聚合。不要试图用一份全局模型替代所有上下文内部模型。

## 指标口径统一

指标口径争议通常源于定义中的隐含维度。用本体把指标拆成可计算的结构：

```turtle
@prefix ex: <https://example.com/metric#> .
@prefix skos: <http://www.w3.org/2004/02/skos/core#> .

ex:GrossMarginRate a ex:Metric ;
    skos:prefLabel "毛利率"@zh ;
    ex:formula "(营业收入 - 营业成本) / 营业收入" ;
    ex:hasDimension ex:Region , ex:ProductCategory , ex:Period ;
    ex:numeratorMetric ex:OperatingRevenue ;
    ex:denominatorMetric ex:OperatingCost .
```

口径统一的关键动作是**把分子分母、维度、时间窗口、排除项写清楚**，并与物理实现绑定（哪张表、哪个字段）。指标定义进版本库，变更走评审。这样“为什么两个报表的毛利率不同”就能被直接查出来，而不是开会吵。

## 与湖仓、数据中台的关系

- **湖仓/数仓**负责存储与计算，指标在数仓实现；
- **治理平台**负责人、流程、审批；
- **本体/知识图谱**负责语义：术语、映射、血缘、质量规则。

三者通过 ID 与元数据对接。不要指望用本体替代数仓的聚合计算，也不要指望治理平台自己长出语义。常见集成方式：数仓表 → 映射为本体实例（R2RML/程序映射）→ 暴露语义查询；治理平台的元数据 → 导出为 DCAT + PROV-O。

## 组织与角色

| 角色 | 职责 | 常见误区 |
|---|---|---|
| 数据管家（Steward） | 维护术语、审核变更、处理质量问题 | 被当成兼职行政工作，没有时间投入 |
| 领域专家 | 定义业务概念与规则 | 只在启动会露面，之后不再参与 |
| 数据工程师 | 映射开发、质量规则实现、流水线 | 只关心管道跑通，不关心语义正确 |
| 语义/知识工程师 | 本体设计、推理与校验、模型评审 | 过度追求形式完美，脱离业务 |

治理要能持续，必须给管家**明确的时间预算与考核项**，否则术语表三个月后就没人更新。这一点比工具选型重要得多。

## 落地步骤与指标

建议按季度推进：

1. **第 1 季度**：选一个域，建术语表（SKOS），覆盖核心 50–100 个概念，明确责任方；
2. **第 2 季度**：把该域核心数据集纳入目录（DCAT），标注概念映射；上线 5–10 条 SHACL 质量规则；
3. **第 3 季度**：建主数据实体与跨系统映射，接入血缘（PROV-O），打通“概念 → 数据集 → 指标”的查询；
4. **第 4 季度**：扩展第二个域，建立变更评审流程与 CI 校验，把指标口径纳入版本管理。

指标建议：术语覆盖率（核心概念中有定义且有责任方的比例）、映射覆盖率、质量规则自动执行率、问题平均修复时长、目录查询使用量。数值目标按自身基线设定，不要照搬外部基准。

## 常见坑

1. **术语表只写不读**：没有检索或校验消费，等于文档。至少接一个查询入口。
2. **一上来做全企业本体**：范围失控。按域推进。
3. **定义写成同义反复**：“客户就是客户信息”，无法判定。
4. **质量规则没有责任人**：违规报告没人处理，三个月后自动失效。
5. **主数据合并逻辑藏在 ETL 里**：无法审计、无法回滚。映射与优先级要显式建模。
6. **把治理当纯 IT 项目**：没有业务方参与，术语一定失真。
