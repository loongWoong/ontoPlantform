# 知识图谱构建

知识图谱（Knowledge Graph）是由本体定义模式、由实例数据填充的图结构数据资产。本页讲清楚从源系统到可服务图谱的完整流水线、每个阶段的具体做法、质量指标，以及最容易被低估的坑。

## 知识图谱与本体是什么关系

一个常见误解是把图数据库里的数据都叫“知识图谱”。严格说：

- **知识图谱 = 本体（模式）+ 实例数据（+ 推理结果）**。没有模式的图只是数据，语义靠字段名和口头约定，换个团队就读不懂；
- **本体 ≠ 知识图谱**。本体是类和公理，通常几百到几千个声明；图谱是 TBox 加 ABox 的整体。同一个本体可以支撑多个图谱；
- **图数据库 ≠ 知识图谱**。图数据库是存储引擎，属性图模型没有内建语义推理，RDF 三元组库也不强制你写本体。

所以“建知识图谱”的真实工作量，大部分不在存储上，而在**语义建模、实体对齐和数据质量**上。经验上，模型设计、映射开发和质量治理占大头，加载与查询只占小头。规划时按这个比例分配人力。

## 流水线总览

```text
源系统（数据库/API/文件/文档）
  → 抽取（增量/全量、脱敏、格式统一）
    → 清洗与规范化（单位、编码、时间、去重）
      → 实体识别与消歧（把“同一个人/公司/商品”合并）
        → 本体映射（映射到类与属性，生成 RDF）
          → 加载与索引（三元组库/图库）
            → 推理与校验（隐含事实、SHACL 一致性）
              → 质量评估（覆盖率、准确率、连通性）
                → 服务（查询 API、检索、图谱可视化）
                  → 反馈迭代（补映射、修数据、改模型）
```

下面逐段说明。每段都给出最简可上线版本和后续加强方式。

## 阶段一：界定范围与能力问题

先写 5–10 条能力问题（CQ），再决定抽什么数据。做法见 [能力问题（CQ）](/modeling/method/competency-questions)。

范围要同时限定三个维度：**业务域**（如“售后商品”而不是“全部商品”）、**源系统**（3–5 个）、**时间范围**（首批只导入近一年数据）。三个维度都不限，项目必然延期。

同时明确“图谱不需要什么”。例如不需要全量订单明细、不需要用户行为日志，这些放在数据仓库更合适。

## 阶段二：抽取与清洗

抽取方式按源系统类型选择：

| 源类型 | 抽取方式 | 注意点 |
|---|---|---|
| 关系数据库 | 批量 SQL 导出、CDC 增量 | 主键变更会破坏实体 IRI 稳定性 |
| REST/GraphQL API | 定时拉取、分页游标 | 速率限制与字段含义文档缺失是主要风险 |
| 文件（CSV/Excel） | 批处理导入 | 编码、单位、空值表示要统一 |
| 文档（PDF/HTML） | 文本抽取 + 规则/模型抽取 | 抽取结果必须带来源与置信度 |
| 行业交换格式 | 复用标准映射（如 FHIR、IFC、GS1） | 先核对版本差异 |

清洗阶段的核心是**把值域收敛**：国家代码统一 ISO 3166、货币统一 ISO 4217、单位统一 SI、时间统一 UTC 或明确时区。做不到统一，就先建映射表，别急着上图谱。

## 阶段三：实体识别、消歧与链接

这是知识图谱质量的分水岭。同一条真实记录在不同系统里有不同标识，必须合并，否则图谱只是“把多张表堆在一起”。

常用策略按可靠性排序：

1. **权威 ID 直连**：源系统共享同一个业务编码（如商品 SKU、统一社会信用代码），直接复用为实体 IRI。最可靠，优先做。
2. **确定性规则匹配**：规范化后的邮箱、手机号、证件号完全相等即视为同一实体。
3. **模糊匹配 + 人工确认**：名称相似度、地址相似度组合打分，高置信度自动合并，中置信度进人工队列。
4. **`owl:sameAs` 声明**：合并结果用 `sameAs` 表达，但**不要滥用**。`sameAs` 是等价公理，推理器会把两个个体的所有属性合并，错一条会污染一大片。更稳妥的做法是保留各自的“系统内 ID”，另用专门的实体表记录对齐关系，需要时再投影成 `sameAs`。

消歧必须可审计：每条合并记录保存依据（哪个字段、什么规则、置信度）与操作人。之后出现错并，才能拆分修复。

## 阶段四：本体映射

把清洗后的结构化数据映射到本体。三种主流方式，按复杂度选择：

- **R2RML**：W3C 推荐标准，用映射文档把关系表映射为三元组，适合“表结构稳定、映射规则清晰”的场景；
- **RML**：在 R2RML 思想上扩展，支持多格式源（CSV、JSON、XML），目前是社区规范；
- **SPARQL CONSTRUCT / 程序映射**：用 `CONSTRUCT` 或代码逐行生成三元组，灵活度最高，适合复杂转换和需要调用外部服务的场景。

一段最小的 `CONSTRUCT` 映射示例（把源表的商品行映射为本体实例）：

```sparql
PREFIX ex: <https://example.com/onto#>
PREFIX prop: <https://example.com/onto/prop/>
PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>

CONSTRUCT {
  ?product a ex:Product ;
           ex:productName ?name ;
           ex:hasCategory ?category ;
           ex:listPrice ?price .
  ?category a ex:Category .
}
WHERE {
  ?row prop:sku ?sku ;
       prop:name ?name ;
       prop:categoryCode ?categoryCode ;
       prop:price ?price .
  BIND(IRI(CONCAT("https://example.com/product/", ENCODE_FOR_URI(?sku))) AS ?product)
  BIND(IRI(CONCAT("https://example.com/category/", ENCODE_FOR_URI(?categoryCode))) AS ?category)
  FILTER(DATATYPE(?price) = xsd:decimal)
}
```

映射开发的三条纪律：

- **IRI 生成规则唯一且稳定**。用业务主键派生，不要用自增行号或时间戳，否则重跑会造出重复实体；
- **映射即代码**，进版本库、有测试、可重跑。手工在 Protégé 里点出来的数据无法维护；
- **记录来源**。每个实体保留 `prov:wasDerivedFrom` 或自定义来源属性，指向源系统与记录 ID，用于追溯和重新抽取。

## 阶段五：加载、推理与校验

加载前先定存储。选型见 [存储选型](/impl/arch-pattern/storage)。要点：

- **批量导入用专用加载器**，不要用逐条 SPARQL Update 灌几百万条数据；
- **推理物化与查询时推理二选一**。全量物化简单但占空间、更新慢；查询时推理省空间但延迟不可控。混合方案通常是“RDFS 子集物化 + 规则按需”。详见 [推理与物化](/impl/arch-pattern/inference)；
- **加载后跑 SHACL**。数据不通过形状校验就发布，等于把问题推给消费方。校验规则见 [SHACL 形状约束](/spec/shacl)。

## 阶段六：质量指标

不要用“数据量”衡量图谱。用下面四类指标，并且**给出基线值和目标值**（具体数值由项目根据历史数据确定，不要抄别人的百分比）：

| 指标 | 定义 | 测量方式 |
|---|---|---|
| 覆盖率 | 目标实体中有多少已入图、必填属性填充率 | 抽样比对源系统计数 |
| 准确率 | 抽样实体中属性值与实体对齐正确的比例 | 人工抽样评审，记录样本量与置信区间 |
| 连通性 | 孤立实体比例、平均度数、关键关系缺失率 | 图查询统计 |
| 一致性 | OWL 推理一致性、SHACL 违规数、重复实体数 | 自动校验流水线 |

指标要能追溯到具体规则。例如“订单-商品关系缺失率”对应一条 SHACL `minCount` 约束，这样质量下降时能定位到原因，而不是只知道“图变差了”。

## 阶段七：服务与运营

图谱要有人用，必须有服务层：

- **查询 API**：把常用 CQ 封装为参数化接口，不让前端直接拼 SPARQL（注入与性能都不可控）；
- **检索融合**：图查询与关键词/向量检索组合，见 [语义检索与 RAG](/application/semantic-search)；
- **可视化**：按业务问题定制视图，不做通用“全图展示”，节点超过几百个就没有可读性。

运营上，把回调链路建起来：消费方反馈的错例 → 映射或模型修正 → 重跑受影响分区 → 回归校验。没有这条链路的图谱，半年后就会和源系统脱节。

## 与数据仓库、数据湖的关系

三者不冲突，分工不同：

- **数仓**擅长聚合统计与历史快照，结构化查询性能好；
- **湖**擅长存原始多态数据；
- **图谱**擅长关系遍历、多跳查询与跨源实体整合。

现实做法通常是混合：数仓做指标计算，图谱负责实体关系与语义服务，通过 ID 对齐，不追求把数仓全量搬进图里。把所有明细都灌进三元组库，往往换来查询变慢和运维复杂，收益有限。

## 常见坑

1. **先建图后想用途**：图建好了没人查。先定 CQ 和消费方。
2. **追求大而全的本体**：一个域一个模块，逐步扩展，见 [模块化与复用](/modeling/elements/module)。
3. **`sameAs` 滥合并**：错并难拆，且推理会放大污染。保留来源 ID 与对齐表。
4. **IRI 不稳定**：重跑生成新实体，图谱越来越脏。
5. **忽略增量更新**：只做一次性全量导入，三个月后数据过期。
6. **无校验直接上线**：脏数据进入检索和决策链路，比没有图谱更糟。
7. **推理开满**：全量物化导致加载以小时计，调参无门。按需限制到 RDFS 子集或目标 profile。
