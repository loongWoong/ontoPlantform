# 运营与生命周期

本体不是交付物，而是长期运行的资产。一个本体活下来的标志不是“文件还在”，而是**有人提需求、有人评审、有自动校验、有人在用**。本页讲运营机制：角色、流程、指标、失败模式，以及如何用最小的组织成本起步。

## 为什么运营比建模更难

建模是一次性投入，运营是持续成本。本体失活通常经历同样四步：

1. 上线时模型完整、热度高；
2. 源系统改字段，映射滞后，数据开始缺；
3. 消费方发现结果不准，逐渐弃用；
4. 无人维护，模型与数据彻底脱节，成为“历史文档”。

阻断这条滑坡只有两个手段：**把校验自动化、把维护责任落到人**。任何依赖“大家自觉”的治理方案都撑不过半年。

## 角色与职责

| 角色 | 职责 | 时间投入 |
|---|---|---|
| 本体负责人（Owner） | 终审模型变更、对语义一致性负责 | 每周固定小时数，不能是挂名 |
| 领域专家 | 提出与确认概念、判定业务语义争议 | 评审会 + 按需答疑 |
| 语义/知识工程师 | 设计模型、写映射与约束、跑校验 | 主要维护者 |
| 数据工程师 | 源系统接入、映射实现、数据质量 | 按项目阶段投入 |
| 消费方代表 | 提出能力问题、验收、反馈错例 | 每迭代一次 |

关键点：**Owner 必须有决策权**。如果每次语义争议都要上升到委员会，模型就会停滞。小团队里可以由架构师兼任，但要明确写入职责。

## 提案—评审—发布流程

轻量但明确，四步即可：

1. **提案（Issue）**：谁提的、什么能力问题驱动、影响哪些类/属性/约束、是否破坏兼容；
2. **评审（Review）**：语义工程师审形式正确性（一致性、约束合理性），领域专家审业务正确性，消费方审影响面；
3. **实现与测试**：改模型、改映射、补测试（CQ 查询、SHACL 样例、单元测试），在 CI 中验证；
4. **发布（Release）**：打版本号、写变更说明、更新消费方、必要时并行运行一段时间。

变更分级很重要：

- **补丁级**：加注释、加同义词、修正拼写——直接合并；
- **次版本**：加类、加可选属性、加约束（可能暴露历史数据问题）——需要评审与数据影响评估；
- **主版本**：删类、改语义、改 IRI——需要迁移方案与消费方确认。

版本与兼容策略详见 [版本与演进](/impl/arch-pattern/versioning)。

## 用 Git 与 CI 管理本体

本体文件（Turtle、SHACL）当代码管理，是最成熟的实践：

```text
ontology-repo/
├── ontologies/
│   ├── core.ttl             # 核心概念
│   ├── product.ttl          # 业务模块
│   └── vocab/               # 复用的外部词表（固定版本）
├── shapes/
│   ├── product-shapes.ttl
│   └── order-shapes.ttl
├── queries/                 # 能力问题对应的 SPARQL，作为验收测试
│   └── cq-001-products-by-category.rq
├── mappings/                # R2RML / CONSTRUCT 映射
├── tests/                   # 样例数据与期望结果
└── CHANGELOG.md
```

CI 里至少跑四件事：

- **语法解析**：所有 Turtle 文件可解析（`riot --validate` 或对应库的解析器）；
- **一致性检查**：推理器加载全量模式，确认无不可满足类、无矛盾（ELK、HermiT 等）；
- **CQ 回归**：跑 `queries/` 下的查询，结果与期望集比对；
- **SHACL 回归**：样例数据必须通过、违规样例必须被抓到。

再加一条：**外部依赖锁版本**。复用 schema.org、FOAF、DCAT 等外部词表时，把文件快照进仓库或固定下载版本，避免上游变更导致构建漂移。

协作编辑上，WebProtégé 之类的浏览器工具适合领域专家参与评审；正式版本仍以 Git 仓库为准。Protégé 本地编辑容易出现格式冲突，提交前统一格式（序列化排序）能减少无意义 diff。

## 监控指标

运营指标要能回答“本体是否还活着”：

| 维度 | 指标 | 采集方式 |
|---|---|---|
| 模型质量 | CQ 通过率、推理一致性状态、SHACL 违规数 | CI + 定时任务 |
| 数据同步 | 映射滞后时长、实体覆盖率、重复实体数 | 加载监控 |
| 使用情况 | 查询次数、活跃消费方数量、API 调用来源 | 端点日志 |
| 变更节奏 | 提案数、评审时长、平均合并周期 | 仓库与工单系统 |
| 服务性能 | 查询 P95 延迟、超时率、推理任务耗时 | 端点监控 |

最少要盯住三项：**CQ 通过率、映射滞后、活跃消费方数量**。三者中任何一项持续下降，说明本体正在失去价值。

数据侧质量指标的定义见 [数据治理与主数据](/application/data-governance)，检索场景的效果指标见 [语义检索与 RAG](/application/semantic-search)。

## 常见失败模式

1. **一次性项目**：立项时叫“知识图谱建设”，验收后无人接手。对策：验收标准里包含运营机制与预算。
2. **无人维护**：没有 Owner，或 Owner 只是挂名。对策：明确写入岗位职责与考核。
3. **建模与数据脱节**：模型改了，映射没改；或数据变了，模型不更新。对策：映射与模型同仓库、同 CI。
4. **过度设计**：追求全量公理与完美分类，交付周期拉长，消费方失去耐心。对策：能力问题驱动，增量发布。
5. **只对内不对外**：模型不对外文档化，新成员无法上手。对策：每个类与属性必须有 `rdfs:label` 与 `skos:definition`，术语表可检索。
6. **治理流程过重**：每个小改动都要开会评审，维护者放弃提交。对策：变更分级，按风险区分流程。
7. **指标只看数量**：统计“有多少类和属性”，不看是否被使用。数量增长不等于价值增长。

## 从小做起的路线

如果组织还没有本体运营经验，按下面顺序推进，每一步都能独立交付：

1. **第 1 个月**：选定一个业务域，建立 Git 仓库与目录结构，写 10 条 CQ，建模 20–40 个核心类；
2. **第 2 个月**：接入 1 个源系统，实现映射；配置 CI 跑解析、一致性、CQ 回归；
3. **第 3 个月**：上线第一个消费方（查询接口或校验流水线），建立 Owner 与双周评审节奏；
4. **第 4–6 个月**：补 SHACL 质量规则、扩展第二个源系统，开始记录运营指标；
5. **半年后**：复盘 CQ 通过率与使用量，决定是扩展域还是加深应用。

这条路线避免了两个极端：一开始就追求平台化（必然烂尾），或者只做一次性交付（必然失活）。
