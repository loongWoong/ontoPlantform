# 语义检索与 RAG

把本体用在检索与 RAG 上，目标不是“让搜索更智能”，而是**让检索命中正确的实体、让生成有据可依、让答案可追溯**。本页给出三条检索路线的取舍、本体在链路上的六个插入点、参考架构与评估指标，并对 GraphRAG 给出审慎判断。

## 三种检索范式

| 范式 | 原理 | 强项 | 弱项 | 适用 |
|---|---|---|---|---|
| 关键词检索（BM25 等） | 词项匹配与统计相关度 | 精确词、编号、专名命中最准；可解释 | 同义词、跨语言、语义漂移失效 | 有明确术语的垂直检索 |
| 向量检索 | 语义嵌入 + 近邻搜索 | 语义相近、问法与文档措辞不同也能召回 | 精确匹配弱、易召回“意思像但不对”的内容、难解释 | 问答、长文本召回 |
| 图 + 向量混合 | 向量召回实体/块，再沿本体关系扩展或过滤 | 结构化约束、多跳关系、可追溯 | 实现复杂，依赖图谱质量 | 关系密集、需要多跳的领域 |

结论：**关键词检索不会消失，向量检索不是银弹，混合路线是当前主流**。向量召回解决“找不到”，图结构解决“找得乱”。如果只有向量库、没有本体，就无法把“这款产品的替代型号”这类关系型问题答对。

## 本体在链路中的六个位置

多数团队只用本体做一件小事，其实它有六处可用：

1. **查询理解**：把自然语言问题解析为实体、属性、约束。识别出“去年 Q3”“华东区”“毛利率”分别对应本体的时间区间、区域、指标定义。
2. **查询扩展**：用 `skos:altLabel`、上下位关系、等价类补全同义词与更宽/更窄的检索词。这是 SWRL 之外最便宜、收益最稳的一招。
3. **实体链接**：把提问中的名称链接到图谱中的实体 IRI，消解同名与别名问题。链接准确率直接决定后续结构化召回的质量。
4. **结构化召回**：用 SPARQL 精确筛选（如“属于某品类且价格区间内且已停产”），再把结果作为上下文。比纯向量召回可控得多。
5. **约束生成与校验**：把本体中的取值域、基数、单位转成生成阶段的约束，输出后按 SHACL/本体一致性做检查，拦截不合法答案。
6. **答案可解释**：返回答案时同时返回依据的三元组或路径，用户能核对，也能据此判断该信任多少。

前三点投入小、见效快，建议先做；后三点依赖图谱质量与工程投入，按需推进。

## 参考架构

```text
用户问题
  → 查询理解（分词/意图/实体识别 + 本体词典）
    → 实体链接（别名 → 实体 IRI，取候选打分）
      → 三路召回并行：
          a) 关键词检索（BM25）
          b) 向量检索（chunk embedding）
          c) 图查询（SPARQL 结构化召回 + 邻域扩展）
        → 融合去重（按实体/文档聚合打分）
          → 重排（rerank 模型或规则）
            → 生成（LLM，提示中注入结构化上下文）
              → 校验（SHACL/一致性/事实核对）
                → 返回答案 + 依据
```

工程上要注意几点：

- **分块策略与本体对齐**。chunk 的元数据里带上实体 IRI、文档来源、时间，检索时才能按本体约束过滤，而不是把全文丢给向量库；
- **向量库与三元组库分离**，通过实体 IRI 关联。不要试图用三元组库替代向量检索；
- **上下文预算**。结构化上下文要精简到“回答问题所必需的子图”，把整张子图塞进提示会挤掉其他证据。

## 查询理解与扩展示例

用 `skos:altLabel` 与上下位关系做扩展，是最容易落地的一段：

```sparql
PREFIX skos: <http://www.w3.org/2004/02/skos/core#>
PREFIX ex: <https://example.com/onto#>

# 输入：用户提到的词 ?term；返回同义词 + 下位词作为扩展检索词
SELECT DISTINCT ?expanded WHERE {
  ?concept skos:prefLabel ?term ;
           ?link ?expanded .
  VALUES ?link { skos:altLabel skos:narrower }
}
```

注意 `narrower` 只在确实需要“更具体也算命中”时展开；否则会召回大量噪声。扩展策略应当按查询类型分别配置，而不是全局开关。

## GraphRAG：新兴实践，别急着上

GraphRAG 指用 LLM 从语料中抽取实体与关系，构建图，再基于图与社区摘要增强检索与生成。微软研究院在 2024 年提出了这一方向的代表性工作，此后社区工具快速跟进。需要明确：

- 它**仍在演进**：抽取质量依赖模型与提示，评测方法尚未统一，不同实现的结论差异很大；
- 建图成本高：需要 LLM 逐块抽取实体关系，语料规模、更新频率都会放大成本；
- 它解决的是“全局性问题”（跨文档归纳、主题聚类），对“精确事实检索”未必优于混合检索；
- 如果你的领域已有稳定本体，**不必让 LLM 从零建图**，直接映射到已有模式质量更高、可复现性更好。

建议：先做“本体 + 混合检索”，把实体链接与结构化召回做扎实；确有跨文档归纳需求，再评估 GraphRAG，并且用小样本做 A/B 验证，而不是全量上线。

## 评估指标

检索与 RAG 的评估必须拆开看，否则无法定位问题：

| 环节 | 指标 | 测量方式 |
|---|---|---|
| 检索召回 | Recall@k、实体链接准确率 | 人工标注问题集，统计命中 |
| 检索排序 | NDCG@k、MRR | 标注相关度分级后计算 |
| 生成质量 | 答案正确率、依据支持率（是否被检索证据支撑）、幻觉率 | 抽样人工评审 + 自动核对三元组 |
| 稳定性 | 同一问题的答案一致性 | 重复提问对比 |
| 性能 | P50/P95 延迟、单次查询成本 | 埋点统计 |

样本集要覆盖四类问题：**事实型**（单一实体属性）、**比较型**（多实体对比）、**关系型**（多跳关系）、**聚合型**（跨实体的统计或归纳）。只测事实型会导致指标虚高。

## 成本与落地建议

- **先建词典，再建向量**。术语表与别名词典（可用 SKOS 维护）成本最低，实体链接准确率提升最直接；
- **混合检索优先于纯向量**。有明确术语的行业场景，BM25 + 实体过滤往往就够；
- **生成阶段强制引用**。提示中要求给出依据 IRI 或文档编号，没有依据就拒答。这比事后校验便宜；
- **控制领域范围**。检索范围越小，召回干扰越少。先做一个业务域，再横向扩展；
- **别用 RAG 掩盖数据问题**。源数据有错，检索只会稳定地返回错误答案。

## 常见坑

1. **只做向量检索**：精确编号、型号、法规条款查询效果差，而这类查询在行业场景里占比很高。
2. **本体只用于同义词扩展**：浪费了结构化召回与约束校验的价值；反过来，也不必强求全部六点都上。
3. **实体链接不做消歧**：同名实体混在一起，答案张冠李戴，且很难被发现。
4. **评测算平均值**：聚合指标掩盖长尾失败。按问题类型分组看指标。
5. **chunk 不带元数据**：无法按本体过滤，检索退化为纯文本相似度。
6. **让 LLM 自由总结图谱**：生成阶段脱离检索证据就会编造，必须限制在给定子图内。
