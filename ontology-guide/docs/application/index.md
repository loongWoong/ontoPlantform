# 应用总览

本体的价值不在建模本身，而在模型被系统稳定使用。本页给出本体在工程中的常见应用地图、判断“值不值得做”的方法、与 DDD 的分工，以及如何选出第一个落点场景。每个场景的展开见各子页。

## 本体在系统里解决什么问题

把本体放进系统，通常是为了解决下面四类问题中的一类或几类。判断一个需求是否真需要本体，先看它命中了哪一类。

| 问题类型 | 典型症状 | 本体的作用 | 无本体的替代方案 |
|---|---|---|---|
| 语义歧义 | 同一个词在不同系统里含义不同，对账总对不上 | 用显式类和属性固定含义，靠 IRI 全局标识 | 人工维护字典、逐系统硬编码映射 |
| 数据异构 | 同一实体有几十种字段命名和结构 | 统一到共享模式，映射一次、复用多次 | 点对点 ETL，系统数为 n 时映射数为 n² |
| 需要推理 | 结论由多条事实组合得出，规则分散在代码里 | 用公理和规则推导隐含事实，可解释 | 在业务代码里写分支判断 |
| 需要互操作 | 与外部伙伴、行业标准、开放数据交换 | 复用标准词表（schema.org、FHIR、DCAT 等） | 自定义 JSON 契约，逐对谈判 |

这四类问题有一个共同点：**语义是跨边界的**。如果语义只在一个限界上下文内部使用，用 DDD 的领域模型和类图就够了，不需要本体。这是把本体与 DDD 区分开的关键判据。

## 应用地图

| 场景 | 核心能力 | 主要收益 | 展开阅读 |
|---|---|---|---|
| 知识图谱构建 | 抽取、对齐、映射、加载、推理、服务 | 把分散数据合成可查询的实体网络 | [知识图谱构建](/application/knowledge-graph) |
| 语义检索与 RAG | 查询理解与扩展、结构化召回、答案校验 | 降低歧义、减少幻觉、答案可追溯 | [语义检索与 RAG](/application/semantic-search) |
| 数据治理与主数据 | 共享术语、数据目录、血缘、质量规则 | 口径统一、责任清晰、质量可测量 | [数据治理与主数据](/application/data-governance) |
| 业务规则与校验 | 一致性推理、SHACL 校验、规则治理 | 规则显式化、可测试、可版本化 | [业务规则与校验](/application/rules-validation) |
| 语义集成与互操作 | 映射、联邦查询、语义化 API | 降低集成成本，对接行业标准 | [语义集成与互操作](/application/integration) |
| 运营与生命周期 | 治理流程、CI 校验、指标监控 | 让本体成为可持续资产 | [运营与生命周期](/application/lifecycle) |

此外还有两类常被提及的场景：**决策支持**（把规则与事实结合，做合规判定、风险筛查、推荐解释）与 **AI 可信**（为模型输出提供事实依据与来源追溯）。它们多数是上述场景的组合：决策支持 ≈ 规则校验 + 推理；AI 可信 ≈ 语义检索 + 来源建模（provenance）。不建议单独为它们立项，而应落到具体链路上。

## 什么时候值得做

满足下列条件中的多数，才值得投入本体：

- **有多个系统或组织需要共享同一套语义**，且用点对点映射已经明显吃力；
- **语义本身是争点**，例如“客户”到底指签约主体还是使用者，靠讨论难以对齐；
- **需要推理或可解释性**，结论必须能说明依据；
- **有合规、审计、互操作的外部压力**，标准词表能直接复用；
- **有长期维护的预期**，至少两三年内语义资产不会被整体废弃。

反过来，下面这些情况通常不该上本体：

- **单系统、单团队、边界清晰**：DDD 的领域模型加数据库约束即可；
- **只是想做可视化大屏**：图数据库或前端图可视化组件就够，不需要形式化语义；
- **数据规模很大但语义简单**：先解决数据质量问题，本体救不了脏数据；
- **没有明确的消费方**：建完没人查、没人验，就会变成一次性项目；
- **团队没有能力维护 OWL/SHACL**：那就从 SKOS 词表起步，不要直接上重公理。

## 反例：这些做法注定失败

1. **先建大本体，再找应用**。典型的“企业级本体”项目，半年产出一堆类和属性，却没有一个系统读取它。正确顺序是：找到消费方，从能力问题反推模型。
2. **把本体当文档交付**。文档不参与运行，就不会被校验，也就不会保持准确。至少要有一条自动校验链路（SHACL 或 CQ 查询）挂在 CI 上。
3. **试图让本体承担全部业务逻辑**。本体的强项是描述语义和推导事实，不是编排流程、处理事务。业务行为仍归应用层。
4. **过度公理化**。为了“更智能”加满 OWL 公理，结果推理变慢、模型难改、业务方看不懂，收益却很小。

这些反例的共同特征是：**没有可验收的消费场景**。立项时就要写清楚“谁在什么流程里读这个模型、读不到会怎样”。

## ROI 怎么估算

本体的收益通常是“避免损失”，比“创造收入”更难量化，但并非不能算。按三栏对照：

- **成本**：建模人力、映射与管道开发、存储与工具（开源方案的主要成本往往在运维人力）、长期的维护与评审投入；
- **收益**：减少的返工工时、对账差异减少、查询与取数等待缩短、合规与互操作风险敞口下降、新系统接入周期缩短；
- **风险**：模型停滞、数据失真、消费方流失。没有治理机制时，收益会归零，这部分要计入风险成本。

估算方法是**先立基线再谈收益**：统计当前每月因语义不一致产生的返工工时、对账差异笔数、跨系统取数耗时，折算成可比较的投入；再看试点期内这些数字是否改善。做不出基线的场景，先别立项。

## 与 DDD 的分工

本体与 DDD 是互补关系，不是替代关系。一句话区分：**DDD 管业务边界与行为，本体管共享语义与数据互操作。**

| 维度 | DDD | 本体 |
|---|---|---|
| 关注点 | 限界上下文内的业务规则与行为 | 跨上下文的共享概念与事实 |
| 主要产物 | 聚合、实体、值对象、领域事件、领域服务 | 类、对象属性、数据属性、公理、个体 |
| 边界处理 | 上下文映射（防腐层、共享内核） | 模块化、`owl:imports`、IRI 命名空间 |
| 一致性 | 聚合不变量、事务边界 | 推理一致性（OWL）、完整性校验（SHACL） |
| 变化节奏 | 随业务迭代频繁调整 | 相对稳定，按版本演进 |

实践中的组合方式有两种：

- **DDD 为主、本体为辅**：业务系统按 DDD 建，跨系统的语义与主数据用本体表达。这是大多数团队的现实路径，见 [分层与六边形架构](/impl/arch-pattern/layered)。
- **本体为主、DDD 管行为**：以数据/知识为核心的系统（知识图谱平台、数据治理平台），语义层由本体驱动，行为逻辑仍用 DDD 组织。

不要生搬类比。聚合不变量与 OWL 公理形式相似，但前者约束一个一致性边界内的事务，后者是开放世界下的逻辑断言，混用会出问题。详见 [约束与业务规则](/modeling/elements/constraint)。

## 如何选第一个应用场景

用下面四个问题筛选，全部通过才进入试点：

1. **痛点是否可量化**：现在每天花多少人力对账、查数、清洗？有多大概率出错？没有基线就无法验收。
2. **范围是否收敛**：能否限定在 1–2 个业务域、3–5 个源系统、10 条以内的能力问题？范围越大，越容易拖成无底洞。
3. **数据是否可得**：源系统能否提供稳定接口或导出？有没有可控的更新频率？
4. **消费方是否明确**：谁会用？是查询接口、检索服务，还是校验流水线？没有消费方的场景不要选。

常见的第一场景排序（按落地难度从低到高）：

- **语义检索/问答**：见效快、可演示，适合争取支持，但对语义严谨度要求不高；
- **数据治理术语与目录**：组织阻力小，是后续所有场景的基础；
- **规则校验**：边界清晰、价值直接，适合合规驱动的组织；
- **知识图谱平台**：投入最大，建议在其他场景验证过语义模型后再做。

## 应用工程的通用链路

尽管场景不同，落地链路大体一致，后续各页都会回到这条主线：

```text
能力问题（CQ）
  → 本体模型（TBox：类/属性/公理/约束）
    → 实例数据（ABox：映射、清洗、实体对齐）
      → 存储（三元组库或混合架构）
        → 服务（查询/校验/推理/检索接口）
          → 消费方（应用、报表、模型、外部伙伴）
            → 反馈（CQ 通过率、数据质量、使用量）回到模型迭代
```

链路上每一环都可以先做最简版本：TBox 用轻量词表起步，ABox 先导入一个源系统，存储先用单机三元组库，服务先暴露一个 SPARQL 查询接口。不要等所有环节都设计完美再开始。
