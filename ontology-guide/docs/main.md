# 本体（Ontology）建模是什么？

本体（Ontology）源自哲学中的“本体论”，研究存在及其本质。在信息科学中，本体指对一个领域中概念、关系、约束的**显式、形式化**描述。最常被引用的定义来自 Gruber（1993）：本体是“对概念化的显式规范”（an explicit specification of a conceptualization）；Studer 等（1998）进一步把它表述为“对共享概念化的形式化、显式规范”（a formal, explicit specification of a shared conceptualization）。

通俗地说：本体把一个领域里“有哪些概念、概念之间是什么关系、什么情况一定成立、什么情况不允许发生”讲清楚，并且用机器能理解的方式表达出来，让不同系统、不同团队对同一批数据有一致的理解。

## 本体建模的核心方法论是什么？

本体建模的核心方法论，可以概括为：**从领域问题出发，建立共享概念体系，把概念体系形式化，再用本体驱动数据与应用**。它和 DDD“领域问题驱动模型设计，模型驱动软件设计”的思路是一致的，只是对象从“业务行为模型”扩展到了“共享语义与数据”。

整个过程大致分三个阶段：

1. **概念化**：与领域专家一起，从业务问题和能力问题（Competency Questions）中提取概念、关系、规则，形成术语表和概念草图。
2. **形式化**：用 RDF、OWL、SKOS、SHACL 等标准表达概念与约束，让语义精确、可推理、可校验。
3. **应用**：用本体组织数据（知识图谱）、驱动查询与推理、做数据校验、支撑语义检索、系统集成与 AI 应用。

概念化决定本体有没有用，形式化决定本体能不能被机器使用，应用决定本体有没有价值。三者缺一不可。具体的流程、元素与设计模式见[本体建模](/modeling/)，这个学科的发展脉络见[本体与语义网历史](/history)。

## 本体有什么优势？

- **消除歧义、统一语义**：同一个词在不同系统里可能含义不同（“客户”是签约主体还是联系人？“订单”是购物车还是已支付单据？）。本体用显式定义和关系把语义固定下来，减少沟通和数据对不上的问题。
- **跨系统互操作**：用共享的词汇表与 IRI 标识概念，不同来源的数据可以对齐、合并、联合查询，而不是靠人工写映射脚本。
- **让数据可推理、可校验、可解释**：本体加上推理可以得到隐含知识（如传递关系、分类归属），加上 SHACL 等约束可以做数据质量与业务规则校验；推理过程可解释。
- **支撑知识图谱、语义检索、RAG、数据治理**：本体是这些应用共同的语义底座，避免每个项目重复造一套“概念约定”。具体场景与判断标准见[应用场景](/application/)。
- **沉淀组织知识，形成长期资产**：领域术语、关系、规则一旦形式化，就可以被复用、被审核、被版本管理。
- **与 LLM 互补**：大模型擅长理解自然语言但不保证事实与一致性；本体提供确定性的语义约束、结构化事实与校验能力，可以用来做检索增强、结果校验与可解释性支撑。

同时要清楚边界：本体不是银弹。它擅长表达“概念与语义”，不擅长表达算法和业务流程；建模与维护有成本；没有应用场景的本体，本质上只是一份文档。

## 如何判断一个项目是否真的用了本体？

满足以下三点，才算真正把本体用起来了：

1. **有显式的概念体系**：有术语表、受控词表或形式化模型，而不是只存在于少数人的脑袋里。
2. **形式化模型被系统使用**：数据按本体组织，查询、推理、校验或系统集成真的依赖它。
3. **有治理机制**：有版本、评审、变更流程，本体能随业务演进。

如果只是画了一张概念关系图放进 PPT，或者把数据库表名换一套“专业词汇”，那不是本体实践。

## 本体和知识图谱是什么关系？

知识图谱通常可以理解为：**本体（模式层）+ 实例数据（实体、关系、属性值）+ 可选的推理**。本体描述“可以说什么”，数据描述“实际有什么”。

知识图谱可以只有很轻的模式，甚至接近 schema-less；但一旦要做语义互操作、推理、数据校验和跨系统集成，就需要显式的本体作为骨架。反过来，只有本体没有数据，也只是空架子。

## 本体必须用 OWL 吗？

不是。本体是“形式化的共享概念体系”，具体用什么语言取决于需求：

- 只需要术语表、分类体系：SKOS 或简单 RDFS 就够。
- 需要描述逻辑推理（分类、一致性检查、隐含关系）：OWL 2。
- 主要需要数据完整性校验与业务规则：SHACL。
- 工程团队使用属性图：LPG 模式 + 应用层约束也可以承载一部分本体职责。
- 面向 Web 的轻量标注：schema.org + JSON-LD。

形式化程度越高，表达与推理能力越强，但建模成本、学习成本和推理成本也越高。够用即可，不要为了“标准”而标准。各种标准的关系见[标准与语言](/spec/)。

## 什么是概念体系？和 DDD 的通用语言是什么关系？

概念体系是一个领域里被认可的概念、术语、定义、分类和关系的集合。DDD 的通用语言（Ubiquitous Language）要求团队用统一的术语交流；本体把通用语言进一步显式化、形式化，让机器也能使用。

可以这样理解：通用语言是本体的人话版本，本体是通用语言的机器版本。两者目标一致，但不是一一对应——通用语言允许口语化、局部简写，本体需要更严格的边界与定义。

## 什么是本体模型？

本体模型是针对领域问题设计的语义模型：它用类、关系、属性、公理、约束描述领域中的概念及其语义，忽略具体的表结构、编程语言和存储实现。它既是团队共识的载体，也是数据与应用的语义契约。参见[本体模型是什么、不是什么](/ontology-model)。

## 有哪些错误的本体实践？

- **只建模不落地**：本体做完就放进文档库，没有数据、没有查询、没有应用，无法验证也无法产生价值。
- **把 ER 图/类图当本体**：只描述数据结构，没有语义公理和约束，也没有形式化表达，机器无法推理和校验。
- **迷信形式化，全量 OWL 公理**：为了“严谨”把能写的公理全写上，导致推理慢、难维护、数据稍有不符就整体不一致。
- **一次建完、不做治理**：没有版本、评审和变更管理，本体很快与真实数据脱节。
- **追求大而全**：试图一次覆盖整个企业所有领域，战线过长，最后无人维护。
- **用 LLM 自动生成本体却不做领域评审**：生成结果看起来合理，但概念边界、关系方向、公理强度都可能有错，必须由领域专家审核。
- **没有能力问题与验收标准**：无法判断本体好坏，只能凭感觉争论。

## 只有复杂项目或大企业才需要本体吗？

判断标准不是项目规模，而是**语义复杂度**。出现以下信号时，值得引入本体：

- 数据来自多个系统，同一个概念有多种叫法和含义，集成成本高；
- 业务规则密集、跨实体、经常变化，需要可维护的规则表达；
- 需要知识推理、语义检索、智能问答、推荐或决策支持；
- 需要对数据做统一治理、口径对齐、血缘追踪；
- 需要为 AI 应用提供可靠、可解释的语义基础。

小项目、简单 CRUD 通常不必一上来就做重本体。可以先从轻量词表、字段级语义约定或 SHACL 校验起步，等需求增长再逐步形式化。

## 本体与 DDD 是什么关系？可以一起用吗？

两者是互补关系，不冲突：

- DDD 关注业务边界（限界上下文）、行为（聚合、命令、领域事件）与业务不变量；本体关注跨边界共享的概念、数据语义与互操作。
- 用 DDD 的通用语言作为本体术语的重要来源；每个限界上下文可以维护自己的局部本体或词表。
- 聚合的不变量、数据完整性规则可以用 SHACL 等约束实现；领域事件可以用来驱动知识图谱或语义层更新。
- 跨上下文、跨系统的集成，用本体做语义映射和对齐，比点对点写映射更可持续。

不要用本体替代领域模型，也不要用领域模型替代本体。两者解决的是不同层次的问题。DDD 部分请阅读[领域驱动设计指南](https://ddd-fans.github.io/ddd-guideline/main)。

## 谁来建本体？需要哪些角色？

- **本体工程师/知识工程师**：负责建模、形式化、工具链与质量把关。
- **领域专家**：提供概念、关系、规则与验收标准，必须深度参与。
- **数据工程师/数据管家**：负责数据接入、映射、质量与日常运营。
- **应用方**：提出场景与验收标准，确保本体服务于真实需求。
- **管理者**：提供治理机制与长期投入的保障。

单靠程序员闭门造车，或者把建模整体外包给“专家”而业务方不参与，都很难成功。

## 投入大吗？应该怎么开始？

本体是长期资产，但起步可以很小：

1. 选一个有明确痛点、范围可控的场景（例如商品主数据统一、设备知识库、合规规则校验）。
2. 写 3–10 个能力问题（CQ），明确“本体要能回答什么”。
3. 先做轻量词表或小本体，优先复用 schema.org 等成熟标准。
4. 用真实数据跑通一个闭环：查询、校验或检索任选其一。
5. 通过 CQ 验收后再扩展，逐步形式化、模块化。
