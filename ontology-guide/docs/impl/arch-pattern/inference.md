# 推理与物化

结论先给：**推理是可选能力，不是本体的必备件**。先确定业务是否真的需要“未显式写出的结论”，再决定用哪一级推理、在什么时机算。绝大多数项目只需要 RDFS 级闭包加少量规则，并且只把关键结论物化；一上来就开全量 OWL DL 推理，是失败率最高的做法之一。存储里怎么隔离推理结果见[存储选型](/impl/arch-pattern/storage)，公理怎么写得克制见[公理](/modeling/elements/axiom)。

## 推理能推出什么

推理的价值是把模型里的公理“展开”成显式事实，让查询和校验都能直接使用。常见能力如下：

| 能力 | 输入 | 推出的结论 | 来源 |
|---|---|---|---|
| 子类闭包 | `:DraftOrder ⊑ :Order`、`:order-1 a :DraftOrder` | `:order-1 a :Order` | RDFS |
| 类型推断 | `:placedBy domain :Order`、`:order-1 :placedBy :c1` | `:order-1 a :Order` | RDFS |
| 逆属性/对称 | `:parentOf owl:inverseOf :childOf` | 反向三元组 | OWL |
| 传递闭包 | `:partOf a owl:TransitiveProperty` | 多跳 `:partOf` | OWL |
| 等价与同一性 | `:Customer owl:equivalentClass :Buyer` | 类型互换 | OWL |
| 不一致检测 | 不相交类同时被断言 | 本体的不可满足性 | OWL DL |
| 业务结论 | 金额、状态、计数等条件 | 风险等级、归类标记 | 自定义规则 |

注意 RDFS 的两条最容易踩：`rdfs:domain/range` 是**推理公理**，写错只会把实例推成错误的类型，不会报错；SHACL 才是校验。这是 OWL 与 SHACL 分工的核心，详见[SHACL 形状约束](/spec/shacl)。

## 先判断要不要推理

三个判据：

1. 结论数量有限、类型稳定、可以被枚举 → 直接物化成显式三元组，甚至不必引入推理引擎。
2. 需要检查本体自身是否自洽（类不可满足、个体矛盾）→ 用 OWL DL 推理器离线跑，建模期与 CI 里跑，不进在线查询路径。
3. 只是要保证“数据符合要求”→ 用 SHACL，不需要推理。校验和推理解决的是不同问题。

## 物化还是查询时推理

| 维度 | 物化（写时算） | 查询时算 |
|---|---|---|
| 查询延迟 | 低，等价于普通三元组查询 | 高，随推理复杂度增长 |
| 存储成本 | 放大，闭包越大越明显 | 几乎为零 |
| 写入成本 | 高，每次变更都要更新闭包 | 低 |
| 增量难度 | 删除尤其难 | 无需维护 |
| 可解释性 | 可保留推导来源，便于审计 | 结论临时生成，难追溯 |
| 实现复杂度 | 需要重建、切换、一致性方案 | 依赖引擎与查询改写 |
| 适用场景 | 读多写少、结论稳定 | 数据高频变化、结论少 |

常见折中是**分级处理**：RDFS 闭包（子类、类型）物化，写少读多；DL 级一致性检查放到离线任务；易变结论用查询时规则或干脆用业务代码算。查询时推理在 SPARQL 里也能做一部分，例如用属性路径手工展开子类闭包：

```sparql
PREFIX : <https://example.com/onto/order#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

SELECT ?order WHERE {
  ?order a ?type .
  ?type rdfs:subClassOf* :Order .
}
```

这条查询不依赖推理器，代价是每次都要遍历类层次，且无法覆盖 domain/range 之类的推断。

## 物化会膨胀多少

膨胀来自四个方向：每个个体对每个祖先类各加一条类型三元组；domain/range 推断出的类型；逆属性导致的边翻倍；传递闭包在长链上的组合爆炸（单链长度 n 的传递闭包是 O(n²) 条）。

估算方式很简单：先数原始三元组，再乘以“平均祖先深度”和“逆属性条数”，得到量级。类层次深、个体多的本体，物化后放大数倍到十几倍都属正常。控制手段：

- **限定 profile**：只开业务真正需要的规则子集，不要“全开以防万一”。
- **只物化关键谓词**：例如只对 `:Order` 相关类展开，其余按需查询。
- **隔离推理图**：推理结果写入独立命名图，查询默认合并，重算时只替换该图。
- **接受集合语义**：RDF 图本身去重，重复推导不会产生重复三元组，膨胀只来自真正新增的结论。

## 增量更新与一致性

写入不难，**删除才难**：删掉一条原始事实后，依赖它的推导结论需要撤销，而大多数引擎不会自动维护完整的支持关系。工程上的三种做法：

1. **标脏 + 定期重算**：变更记录到脏标记，按小时或按天从原始图重建推理图，重建期间旧图继续服务，完成后原子切换命名图。
2. **依赖增量推理的产品能力**：部分存储（如以增量物化为特点的 RDFox、GraphDB 的规则机制）能降低重算成本，但需要实测其删除语义与延迟。
3. **不物化易变结论**：把易变部分排除在闭包之外，从源头回避撤销问题。

无论哪种，都要记住：推理图必须**可由原始图 + 规则版本重算**。做不到这点，就等于埋了一个不敢碰的黑盒。规则文件进版本库，重建脚本进 CI。

## 引擎与各自边界

| 引擎 | 覆盖范围 | 运行方式 | 适用 |
|---|---|---|---|
| Jena reasoner | RDFS、OWL 子集、自定义规则 | Java 库内 | 应用内中小规模推理，规则灵活 |
| ELK | OWL 2 EL | Java 库 | 大规模类层次的快速分类，以 TBox 分类为主 |
| HermiT / Openllet | OWL 2 DL | Java 库 | 建模期一致性检查、类可满足性，ABox 大时慢 |
| GraphDB 规则集 | RDFS/OWL-Horst/OWL 2 QL/RL 及自定义规则 | 库内 | 生产查询可直接使用推导结果 |
| RDFox | Datalog 规则、内存增量物化 | 独立服务/库 | 规则复杂、需要增量更新；内存预算与授权条款需先确认 |
| Stardog | 推理 + 虚拟图 | 商业平台 | 需要统一推理与数据虚拟化 |
| owlready2 | 通过 HermiT 做推理 | Python 库（需 Java） | 数据科学侧探索、离线校验 |
| SHACL-AF | 规则与校验扩展 | 各实现不一 | 需要“校验 + 推导”混合时评估 |

两个必须说清的边界：ELK 不是通用 DL 推理器，含析取、复杂基数的本体它处理不了；owlready2 的 `sync_reasoner()` 默认调用 HermiT，需要本机 Java 环境，不能当作纯 Python 方案。SHACL-AF 是 W3C 工作组注记而非正式推荐标准，各产品支持程度不同，跨产品移植前必须验证。

## 规则设计原则

- **少而稳**：规则数量控制在能被团队讲清楚的规模。每条规则应能对应一句业务语言。
- **可命名、可版本化**：规则文件放版本库，命名体现意图（`high-value-order.rules`），而不是 `rule-07`。
- **可测试**：用 CONSTRUCT 查询或规则的单测断言期望输出，形成回归集。改规则前先跑通旧用例。
- **可解释**：物化结论最好能回答“为什么它是高风险”。做法是保留推导日志或来源标注（例如记录规则 ID 与输入三元组的哈希），必要时用 reification 或 RDF-star 表达来源。
- **不写易变策略**：促销门槛、审批阈值这类每月变的东西，不要固化进本体规则。

Jena 的自定义规则写起来很轻：

```text
# rules/risk.rules
@prefix : <https://example.com/onto/order#> .
@prefix rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .

[highValue:
  (?o rdf:type :Order), (?o :totalAmount ?a), greaterThan(?a, 10000)
  -> (?o :riskLevel :High)]
```

```java
Model data = RDFDataMgr.loadModel("data/orders.ttl");
Reasoner reasoner = new GenericRuleReasoner(Rule.rulesFromURL("rules/risk.rules"));
InfModel inf = ModelFactory.createInfModel(reasoner, data);
```

GraphDB 一侧通常在仓库配置里选择规则集（如 `rdfs-plus`、`owl2-rl`），自定义规则以规则文件挂载；字段名与可用规则集请以所用版本文档为准，不要照抄博客里的旧配置。

## 推理与业务规则引擎怎么分工

| 维度 | 本体推理 | 业务规则引擎 |
|---|---|---|
| 表达对象 | 稳定的语义闭包（分类、传递、等价） | 易变的业务策略（审批、风控、计费） |
| 变更频率 | 低，走评审 | 高，业务方自行调整 |
| 可解释性 | 强，基于公理与规则 | 取决于引擎，需显式设计 |
| 实时性 | 通常离线/准实时 | 常在请求路径上 |
| 权威性 | 语义事实的唯一来源 | 决策策略的唯一来源 |

判定原则：**“这个结论是否无论业务策略怎么变都成立”** —— 是，放本体；否，放规则引擎或代码。两者同时使用时，务必明确谁是权威，避免同一结论两处计算、两处不一致。

## 性能与一致性注意

- 不要把推理塞进在线请求路径。请求内推理的延迟不可预测，尤其涉及传递闭包时。
- 物化更新与原始数据更新通常不在同一事务里，要接受“短暂读到旧闭包”，并用命名图切换减少窗口。
- 读写一致性按产品能力设计：有的存储推理在查询时生效，有的需要显式维护推理图，混用时会出现“我本地能查到、生产查不到”。
- 定期跑一致性检查（本体不可满足、SHACL 违规、推理图与原始图行数偏差），把它们做成监控指标。
