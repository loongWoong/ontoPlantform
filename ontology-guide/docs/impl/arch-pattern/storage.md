# 存储选型

存储选型是本体项目里代价最高、最难回退的决定。结论先给：**先判断是否需要 RDF 的语义互操作与标准查询，再决定产品**；不需要时，属性图或“关系库 + 只读语义视图”往往更省事。推理带来的存储放大见[推理与物化](/impl/arch-pattern/inference)，与业务库的协同方式见[分层与六边形架构](/impl/arch-pattern/layered)。

## 先回答三个问题

1. 数据是否需要与外部系统、行业标准共享语义，或者需要标准查询语言？需要，则 RDF 栈优先。
2. 是否需要推理和 SHACL 校验？需要，则 RDF 生态的工具链最完整。
3. 是否已有承载核心交易的关系库或图库？有，则多半应该做混合，而不是迁移。

三个都是“否”时，不要因为“本体”这个词就上图数据库。一份 Turtle 文件加一个嵌入式解析库，可能已经是正确方案。

## 四类候选

| 类别 | 代表 | 强项 | 弱项 |
|---|---|---|---|
| RDF 三元组库 | Apache Jena TDB2/Fuseki、RDF4J、GraphDB、Stardog、RDFox、Virtuoso、AllegroGraph、Amazon Neptune、Oxigraph | 标准 SPARQL、命名图、推理与 SHACL 生态、跨源合并 | 学习曲线、运维成本、部分产品商业授权 |
| 属性图（LPG） | Neo4j 等 | 边带属性、路径查询直观、生态与人才多、事务成熟 | 无标准 schema/推理，跨系统语义互操作弱 |
| 关系库 | PostgreSQL 等，部分商业库带 RDF 扩展 | 事务与运维成熟、团队熟悉 | 深层多跳查询别扭，语义表达靠表结构，易失真 |
| 混合 | RDF 语义层 + 业务库 + 检索 | 各取所长，渐进落地 | 同步与一致性复杂，需要治理 |

## 可决策的对比

| 维度 | RDF 三元组库 | 属性图 | 关系库 | 混合 |
|---|---|---|---|---|
| 数据模型 | 三元组 / 命名图，全局 IRI | 节点与边，边可带属性 | 表与连接 | 各模型分工 |
| 查询语言 | SPARQL 1.1（标准） | Cypher 等（非标准，生态各异） | SQL | SPARQL + SQL |
| 模式与约束 | OWL + SHACL（标准） | 约束有限，schema 靠约定 | DDL 约束完整 | 各自负责 |
| 推理 | 原生或插件支持（视产品） | 基本靠应用层 | 基本靠应用层 | 语义层承担 |
| 深层多跳 | 强 | 强 | 弱（递归 CTE 可解但难维护） | 强 |
| 事务 | 视产品，通常弱于 OLTP 库 | 较强 | 强 | 写路径靠业务库 |
| 运维门槛 | 中到高 | 中 | 低到中 | 高 |
| 锁定风险 | 低（标准可迁移） | 中 | 低 | 中 |

几个产品特征值得知道（具体能力以官方文档与自测为准）：Jena 的 TDB2 适合单机/嵌入式持久化，配 Fuseki 提供端点；RDF4J 是 Java 侧另一套成熟框架与存储；GraphDB 提供规则集与推理；Stardog 支持虚拟图，可把关系库映射成 RDF 视图；RDFox 以内存 Datalog 推理和增量物化为特点；Virtuoso、AllegroGraph 常见于大规模部署；Amazon Neptune 同时提供 RDF 与属性图两种模型；Oxigraph 可作为嵌入式 Rust 库使用。Blazegraph 的社区维护状态需要自行确认后再上生产。

## RDF 还是属性图

判定可以压缩成一句话：**要把“含义”共享出去，就用 RDF；只在自己系统里做关系分析，属性图通常更快落地。**

选 RDF 的典型信号：

- 需要与行业标准或第三方词表对齐（schema.org、DCAT、PROV-O 等）；
- 需要 SPARQL 联邦查询或跨机构数据交换；
- 需要 OWL 推理或 SHACL 校验；
- 数据模型的演进需要被显式记录和复用。

选属性图的典型信号：

- 查询以路径遍历和推荐为主，不需要推理；
- 边上有大量属性（权重、时间、来源），LPG 表达更自然；
- 团队已有 Neo4j 运维经验，数据不对外交换。

注意“图数据库 = 本体”是常见误解：属性图能存图，但不等于有形式化语义。Neo4j 的 n10s 可以导入 RDF，属于桥接手段，而非把 LPG 变成 RDF。两种范式的详细对比见[RDF 数据模型与序列化](/spec/rdf)。

## 混合架构怎么落地

```text
 业务库（关系库/LPG，强事务）
        │  变更事件 / 批量抽取
        ▼
 语义落图（ETL 或虚拟图）
        │
        ▼
 RDF 存储（TBox + ABox + 推理图）
        │
        ├─▶ SPARQL 语义服务
        ├─▶ SHACL 校验
        └─▶ 检索/向量索引（可选）
```

三条纪律决定混合架构能否维护：

- **单一写入口**：业务数据只在业务库被写，知识库由管道同步；不要在业务事务里双写。
- **可重建**：知识库必须能由源数据 + 映射规则全量重建，否则不敢重跑。
- **虚拟图优先于复制**：数据量不大或时效要求高时，用虚拟图/OBDA 方式（如 R2RML 映射、Stardog 虚拟图、Ontop 一类工具）按需查询关系库，能省掉一套同步链路。

## 数据加载与导出

常见做法是格式转换、批量导入、增量更新分开做：

```bash
# 校验语法与 IRI，确认文件可被解析
riot --validate orders.ttl

# JSON-LD 转 Turtle，便于 diff 与评审
riot --output=TURTLE orders.jsonld > orders.ttl

# 离线全量导入 TDB2，适合初始化或重建
tdb2.tdbloader --loc=DB2 ontologies/orders.ttl data/orders.ttl

# 通过 SPARQL Update 做增量写入
curl -sS -X POST "http://localhost:3030/ds/update" \
  -H "Content-Type: application/sparql-update" \
  --data-binary @incremental.ru
```

增量脚本本身只是若干条更新语句：

```sparql
PREFIX : <https://example.com/onto/order#>
INSERT DATA {
  :order-1002 a :Order ;
             :status :Paid ;
             :placedBy :customer-42 .
}
```

导出时优先用命名图分批导出，避免一次性 dump 影响服务：

```bash
tdb2.tdbdump --loc=DB2 > backup.nq
```

CSV/JSON 源系统通常走 R2RML 或 RML 映射生成 RDF，再用上面的流程加载。映射规则要进版本库，和数据一起评审。

## 容量与运维要点

- **估算三元组量级**：行数 × 每行属性数，再乘以推理放大倍数（见推理页）得到物化后规模。
- **按命名图分区**：来源图、推理图、版本图分开，重算时只替换推理图，避免读到半成品。
- **备份策略**：原始图必须可恢复；推理结果可从原始图重算，不必单独备份，但要保留规则版本。
- **读写分离**：查询压力大时加只读副本（视产品支持），写路径保持单一。
- **监控指标**：查询 P95、慢查询 top N、导入失败率、推理重算耗时、图大小增长趋势。

## 常见坑

- **把图库当 OLTP 主库**：高频小事务写入、强事务保证，通常不是图库的强项。
- **业务库与知识库双写**：任何一侧失败都会留下长期不一致，且没人发现。
- **用空白节点标识业务实体**：空白节点无法被外部引用、无法跨图合并，业务实体必须用稳定 IRI。
- **命名图随意使用**：没有约定时，联邦查询和增量替换都会失控。
- **只选型不做回滚方案**：至少准备“导出为 N-Triples/Turtle 后迁到另一存储”的路径，标准格式是唯一的退路。

## 选型清单

1. 第一个用例需要的查询能否用 SQL/属性图更简单地满足？能，就先别上图库。
2. 需要推理吗？需要哪一级（RDFS/EL/RL/自定义规则）？产品是否原生支持？
3. 需要 SHACL 校验吗？在库内校验，还是应用侧用 pyshacl 一类库在入库前校验？
4. 数据量与增长预期？单机能否覆盖未来 12 个月？
5. 高可用、备份、权限、审计的要求是什么？运维团队能否承接？
6. 授权成本与锁定风险是否可接受？标准格式导出是否可行？
7. 与业务库的同步方式：事件、批量、还是虚拟图？
