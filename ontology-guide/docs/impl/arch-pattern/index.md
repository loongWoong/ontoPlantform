# 实现本体的架构模式

本体落进系统后，会带来四个新问题：它在架构里放在哪、数据存到哪、结论怎么算出来、模型怎么演进。这四个问题各自沉淀出一些做法，本页把它们列在一起，给出“什么时候必须、什么时候可选”的判断依据，细节分别见四篇子页。需要先说明：这些模式不是必选项，也**不存在“上了本体就必须上图数据库”**这样的默认结论。

## 四个关注点与对应模式

| 关注点 | 模式 | 解决的核心问题 | 详见 |
|---|---|---|---|
| 边界与依赖 | 分层 + 端口适配器（六边形） | 语义能力独立演化，业务代码不耦合具体图库 | [分层与六边形架构](/impl/arch-pattern/layered) |
| 数据落点 | 三元组库 / 属性图 / 关系库 / 混合 | 选择承载 TBox 与 ABox 的存储，并处理与业务库的关系 | [存储选型](/impl/arch-pattern/storage) |
| 结论计算 | 物化 vs 查询时推理、规则集 | 隐含结论由谁算、何时算、算多少 | [推理与物化](/impl/arch-pattern/inference) |
| 长期演进 | 版本策略、兼容规则、迁移 | IRI 与语义稳定，数据与代码能平滑升级 | [版本与演进](/impl/arch-pattern/versioning) |

## 什么时候必须、什么时候可选

不同模式的收益差距很大，判断时要回到具体问题，而不是架构风格偏好。

| 模式 | 必须的典型条件 | 可以省略的典型条件 |
|---|---|---|
| 独立语义层 | 两个以上系统/团队消费同一份模型；模型有独立评审与发布节奏 | 单应用内部的小词表，只有一处消费 |
| 端口适配器 | 需要替换存储或推理器；需要在 CI 中用内存库跑测试 | 一次性分析脚本，逻辑不长期维护 |
| RDF 三元组库 | 需要标准 SPARQL、跨源合并、可推理、对外互操作 | 只做单表查询、无推理需求 |
| 独立推理服务 | 需要 DL 级推理（如用 ELK/HermiT 做可满足性检查） | 只需 RDFS 级子类闭包，存储自带即可 |
| 物化 | 查询延迟要求高、推理结果稳定、写少读多 | 数据高频写入、结论变化快 |
| 版本与注册表 | 模型被多方依赖，跨系统共享 | 内部原型，一周内会推翻重做 |

判断口诀是：**看消费方数量、看是否需要标准与推理、看模型的生命周期长度**。三者都小的时候，最简方案通常是对的。

## 与 DDD 架构模式的对照

本体架构模式借用了 DDD 的很多思路，但两者的中心不同，直接照搬会出问题。

| DDD 架构模式 | 本体侧的相似物 | 关键差异 |
|---|---|---|
| 四层架构 | 接口 / 应用 / 语义 / 适配器 | 语义层不承载业务行为，只承载概念、查询与校验 |
| 端口适配器 | 语义服务为端口，三元组库、推理器、外部 API 为适配器 | 端口粒度是“用例查询”而不是“聚合读写” |
| CQRS | 查询走 SPARQL、写入走数据管道或 SPARQL Update | 读模型常是物化推理图，写模型是原始事实，两者不必对称 |
| 事件溯源 | 本体版本历史、知识库增量更新 | 事件溯源以聚合为单位保序；本体演进的单位是图或模块，通常不做事件回放 |
| 仓储 | 语义层 Repository | 仓储强调聚合一致性；语义查询往往是跨类、跨模块的图遍历 |
| 限界上下文 | 本体模块 + 命名空间 | 上下文边界靠 IRI 与 `owl:imports` 隔离，缺少事务边界 |

最重要的差异有两条：

- **一致性强度不同**。聚合不变量要求强一致、立即校验；本体更关注跨系统的语义一致，通常允许最终一致。把本体当“全局聚合”来保证强一致，会付出极高代价。
- **失败方式不同**。OWL 层面写错约束通常不会报错，只会推出奇怪的结论；所以本体侧的重点从“防御非法状态”转向“用 SHACL 显式校验 + 定期一致性检查”。

## 不推荐的做法

以下四类做法在项目里反复出现，代价高、收益低：

1. **把本体直接塞进业务聚合**。在实体里挂 RDF Model、在聚合方法里调 SPARQL，结果是领域模型被图库 API 污染，测试和重构都变难。
2. **无治理的全量推理**。上来就开 OWL 2 RL 或自定义规则全量物化，数据一更新就重算整图，延迟和存储迅速失控。
3. **业务库与知识库双写**。同一个事务里写两处，任何一边失败都会留下长期不一致，且没有补偿机制。
4. **把图数据库当万能库**。用图库承载高频事务写入、做报表聚合、当主数据主库，通常既慢又难运维。

## 一个够用的小型架构

如果消费方就一两个、数据量在单机可承受范围内，可以直接采用最简形态，等出现真实压力再拆：

```text
[接口层 API]
     |
[语义服务]  ← 按用例命名的查询/校验接口
     |
[三元组库（嵌入式或单机）+ 可选 RDFS 推理]
     |
[Turtle / JSON-LD 文件 + 定时导入]
```

等价实现可以是：Jena TDB2 + Fuseki，或 RDF4J 内存库 + Spring 服务，或 Oxigraph + 一个 HTTP 接口。中间不需要消息队列、不需要独立推理服务、不需要图库集群。等出现下列信号再升级：查询变慢且无法靠索引解决、需要多副本高可用、需要复杂规则增量推理、消费方数量增长到需要权限隔离。

## 起步建议

1. 先确定**第一个真实用例**（一次检索、一次校验、一次对账），据此决定要不要三元组库。
2. 用最小组件把端到端链路跑通，验证模型能支撑该用例。
3. 再补版本与评审机制，而不是一开始就设计完备的架构。
4. 每引入一个模式都问一句：它替我们挡住了哪个具体风险？答不上来就暂时不加。
