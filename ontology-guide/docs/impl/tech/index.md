# 技术栈与平台总览

本体落地没有“一站式框架”。一个能跑的系统通常由六类组件拼起来：建模编辑、存储与查询、推理、校验、应用接入、可视化。任何平台都只覆盖其中一部分，剩下的靠组合。因此选型的第一步不是比较产品，而是弄清我们的问题落在哪几类组件上。

三条结论先放在前面。第一，标准比产品重要：Turtle、OWL、SHACL、SPARQL 是可迁移资产，专有查询语言和私有存储格式会形成锁定。第二，先定推理与校验的位置，再选存储；很多项目反过来做，最后发现图库的推理能力用不上，校验还得自己补。第三，单机能解决的不要上集群，用一周以内的 PoC 拿真实查询与真实数据做判断。

## 一套本体系统由哪些组件组成

| 层 | 职责 | 代表工具 |
|---|---|---|
| 建模与编辑 | 编写类、属性、公理，跑推理测试 | Protégé、WebProtégé、TopBraid EDG |
| 存储与查询 | 持久化三元组，执行 SPARQL | Jena TDB2/Fuseki、RDF4J、GraphDB、Stardog、RDFox、Virtuoso、AllegroGraph、Amazon Neptune、Oxigraph |
| 推理 | RDFS、OWL profile、规则、物化 | Jena 推理器、ELK、HermiT、GraphDB 规则、RDFox、Stardog |
| 校验 | SHACL 形状校验与报告 | Jena SHACL、RDF4J SHACL、pyshacl、rdf-validate-shacl |
| 应用接入 | 在业务代码里读写、查询 | Apache Jena、RDF4J、rdflib、pyoxigraph、N3.js、rdflib.js |
| 可视化 | 子图展示与探索 | Cytoscape.js、vis-network、AntV G6 |

组件之间是标准接口，通常可以替换。真正难换的是“推理放在哪”：放在存储层（如 GraphDB 规则、RDFox）意味着性能好但受产品约束；放在应用层（Jena 推理器、OWL API）意味着灵活但要自己管物化与增量。

## 按语言与运行时选库

| 运行时 | 解析与模型 | 查询 | 校验 | 推理 | 适合 |
|---|---|---|---|---|---|
| JVM | Apache Jena、RDF4J、OWL API | ARQ、RDF4J SPARQL | jena-shacl、rdf4j-shacl | HermiT、ELK、Jena 规则推理 | 服务端主力，生态最完整 |
| Python | rdflib、pyoxigraph | rdflib SPARQL、SPARQLWrapper | pyshacl | owlready2（依赖 Java）、owlrl | ETL、数据科学、LLM 原型 |
| JavaScript/TypeScript | N3.js、rdflib.js、oxigraph（WASM） | SPARQL 端点、Oxigraph | rdf-validate-shacl 等 | 浏览器内不做 DL 推理 | 前端展示、BFF、离线工具 |

JVM 与 Python 是两套主流选择：需要成熟服务端、完整推理器和企业级运维，选 JVM；需要快速试错、和数据管道及 LLM 生态贴合，选 Python。两者可以共存，用 SPARQL 或文件交换数据。细节见[JVM 技术栈](/impl/tech/jvm)与[Python 技术栈](/impl/tech/python)。

## 平台与三元组库对比

| 产品 | 形态 | 推理 | 校验 | 许可与部署 | 适合 |
|---|---|---|---|---|---|
| Apache Jena + Fuseki + TDB2 | 开源库与服务 | 规则型 RDFS/OWL 子集，非完整 DL | Jena SHACL 库 | Apache-2.0，自建自运维 | 通用服务端，成本可控 |
| Eclipse RDF4J | 开源 Java 框架 | RDF4J 推理器与自定义规则 | rdf4j-shacl | Eclipse 许可，可嵌入 | 已有 Java 应用内的语义模块 |
| GraphDB | 商业图数据库（有免费版） | 规则推理能力较强 | 支持 | 商业许可 | 企业知识图谱、规则密集场景 |
| Stardog | 商业图数据库 | 推理与数据虚拟化 | 支持 | 商业许可 | 多源数据虚拟化加知识图谱 |
| RDFox | 商业内存图数据库 | 增量规则推理 | 支持 | 商业许可 | 高推理吞吐、规则实时更新 |
| TopBraid EDG | 商业建模治理平台 | 依赖其规则与推理组件 | SHACL 支持较完整 | 商业许可 | 业务用户参与的本体治理 |
| Virtuoso | 开源版加商业版 | 以查询与规模见长，推理需搭配 | 需按版本确认 | 开源加商业 | 大规模 SPARQL 端点 |
| AllegroGraph | 商业图数据库 | 规则推理与图分析 | 需按版本确认 | 商业许可 | 图分析与语义应用 |
| Amazon Neptune | 托管图数据库 | 不做通用 OWL 推理 | 需外部组件 | 按云服务计费 | 已在使用 AWS 的托管场景 |
| Oxigraph | 开源 Rust 实现 | 无 OWL 推理 | 需外部组件 | 开源，可嵌入 | 边缘、测试、轻量服务 |
| Neo4j + neosemantics | 属性图数据库加 RDF 插件 | 无 OWL 推理，走属性图模型 | 需外部组件 | 社区版与商业版 | 已有属性图，只需 RDF 互操作 |

这张表只用于缩小范围。产品能力与版本强相关，最终以官方文档为准；尤其“校验”一列，商业产品的 SHACL 支持范围差异很大，PoC 时必须用真实的形状跑一遍。

编辑与治理工具相对独立：Protégé 适合单人建模型、跑推理检查；WebProtégé 适合多人协作评审；TopBraid EDG 这类平台把建模、校验、发布流程打包，代价是许可成本与学习曲线。小团队用“Protégé + Git + CI”就能获得大部分收益。

## 评估维度

| 维度 | 要回答的问题 | 判断提示 |
|---|---|---|
| 推理需求 | 只要 RDFS？还是 OWL EL、DL、规则？ | 决定 profile 与引擎，见[推理与物化](/impl/arch-pattern/inference) |
| 校验需求 | SHACL 是核心需求还是附带功能？ | 原生支持与外部库的运维成本不同 |
| 数据规模 | 多少三元组、每天多少更新、查询并发多大？ | 先测真实数据，不用官方基准 |
| 事务与一致性 | 写入是否需要 ACID、是否需要版本回滚？ | 图数据库的事务语义差异大 |
| 高可用 | 是否需要集群、备份、故障切换？ | 单机加备份常已够用 |
| 许可与成本 | 生产环境条款、节点/核数限制是什么？ | 把许可审计和续费算进总成本 |
| 生态与人才 | 客户端库、文档、社区、招聘难度如何？ | 冷门产品的长期维护风险高 |
| 运维 | 部署、监控、升级、备份是否有人负责？ | 图库不是装上就不用管 |
| 集成 | 与现有数据栈、身份认证、CI 如何对接？ | 认证与权限常是卡点 |
| 可迁移性 | 能否完整导出 RDF 与本体文件？ | 导出不全是隐性锁定 |

PoC 的做法：准备 5 条能力问题、2 个 SHACL 形状、一份真实规模的样例数据，在候选平台上各跑一遍，记录导入耗时、查询延迟、校验报告质量、推理结果和运维步骤。不要拿厂商基准数字做决策。

## 部署形态：嵌入式、独立服务与托管

同一个库往往支持多种部署形态，选错形态的代价比选错库更大。

**嵌入式**：把图存储放进应用进程，例如 RDF4J 的内存或原生存储、Jena 的 Model、Oxigraph 库。延迟最低，部署最简单，但容量受单机内存与磁盘限制，也无法让多个应用共享同一份图。适合测试、边缘设备、单应用的中小规模场景。

**独立服务**：Fuseki、GraphDB、Stardog 等以独立进程运行，通过 HTTP 暴露 SPARQL 端点。多个消费方共享一份数据，权限、配额、监控都有统一入口；代价是多一跳网络、多一套需要运维的服务，以及端点暴露带来的安全面。多数生产系统落在这个形态。

**托管服务**：如 Amazon Neptune 等云上产品，省去安装与备份，但受云平台、区域、计费方式和能力边界约束，推理与校验往往需要外挂组件。

判断方法很简单：只有一个应用独占数据、规模不大，嵌入即可；有多个消费方或需要统一权限，上独立服务；没有运维人力且已经在云上，考虑托管。无论哪种形态，都要保留把数据完整导出为 RDF、把本体文件留在自己仓库的能力。

## 常见组合

- **小团队与试点**：Protégé 建模，Jena + TDB2 + Fuseki 提供端点，pyshacl 或 Jena SHACL 做校验，应用通过 SPARQL 访问。成本最低，扩展路径清晰。
- **企业知识图谱**：GraphDB 或 Stardog 承担存储与推理，SHACL 做数据质量门禁，WebProtégé 协作评审，应用侧只面向语义服务接口。
- **高推理吞吐**：RDFox 这类内存增量推理引擎，适合规则多、更新频繁、查询要求低延迟的场景，代价是内存与许可成本。
- **数据科学与 LLM**：Python 侧用 rdflib 或 pyoxigraph 做 ETL 与查询，pyshacl 做校验，FastAPI 暴露查询服务；LLM 只负责生成候选查询或自然语言答案，不直接操作生产图。
- **前端展示**：N3.js、rdflib.js 解析与渲染子图，SPARQL 查询走自家 BFF；离线演示可用 Oxigraph 的 WASM 版本。

## 选型建议

先写清楚三件事：要回答哪些问题（能力问题）、数据从哪来、谁维护。三者清楚了，平台范围就缩小到两三个。

不要在没跑通一条端到端链路前采购商业许可。商业产品买的是支持、治理能力和规模，不是“更懂本体”。

推理与校验分开选。需要 DL 推理时，存储层的规则引擎往往不够；需要业务校验时，推理器也替代不了 SHACL。两者的边界见[SHACL 形状约束](/spec/shacl)。

把本体文件留在自己手里，把数据用标准格式导出。这样即使换平台，迁移成本也可控。版本与兼容策略见[版本与演进](/impl/arch-pattern/versioning)。

## 常见问题

**必须上图数据库吗？** 不必须。几千到几十万三元组、查询不复杂时，内存模型加文件即可；数据量、并发或治理要求上来后再换。存储取舍见[存储选型](/impl/arch-pattern/storage)。

**开源够用吗？** 多数场景够用。Jena、RDF4J、Oxigraph、pyshacl 覆盖了服务端的主要能力。需要原生高可用、企业支持、图形化治理时再考虑商业产品。

**关系数据库能存 RDF 吗？** 能，三元组表或 JSON 列都可以，但语义查询与推理要自己实现，容易变成重复造轮子。混合架构（关系库存业务数据、三元组库存语义视图）是常见折中。

**团队只会 JavaScript，能落地吗？** 可以，但建议把重推理与全量数据放在服务端，前端只做子图展示与轻量校验，见[JavaScript/TypeScript 技术栈](/impl/tech/js)。

**怎么避免过度设计？** 从一条能力问题、一个形状、一份样例数据开始，跑通再扩。路线图见[落地路线图](/adoption/)。
