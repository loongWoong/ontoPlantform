# 实现本体

建模阶段产出的是一份“约定”，实现阶段产出的才是“能力”。本页说明实现本体到底要交付什么、为什么建议给它单独一层、以及它和 DDD 的实现怎样配合。架构层面的选择见[架构模式总览](/impl/arch-pattern/)，工具与平台细节见[技术栈与平台总览](/impl/tech/)，模型元素怎么落到代码里见[实现本体对象](/impl/objects/)。

## 实现本体要交付哪些东西

很多团队说的“完成了本体”，其实就是几份 Protégé 里画出来的类图导出成 PDF。这只是建模阶段的部分产物。真正让本体在系统里发挥作用，至少要凑齐下面六件东西，缺哪一件，本体就退化成一样没人消费的静态资产。

| 交付物 | 典型形态 | 主要维护者 | 缺失后的后果 |
|---|---|---|---|
| 术语层（TBox） | Turtle/OWL 文件、IRI 命名规范、版本信息 | 知识工程师 + 领域专家 | 没有共享语义，各系统各说各话 |
| 实例数据（ABox） | 导入管道、实例 IRI 策略、来源标注 | 数据工程师 | 本体只有骨架，查不出任何业务事实 |
| 查询层 | 命名好的 SPARQL 查询集、按用例封装的语义服务 API | 后端工程师 | 模型无法被业务功能使用 |
| 校验层 | SHACL 形状、发布前校验任务 | 数据治理 + 开发 | 数据质量靠人工看，错误数据入库 |
| 推理配置 | 选定的 profile 或规则集、物化策略与增量方案 | 架构师 | 推理由不同人各自为政，结果不可复现 |
| 治理机制 | 提案-评审-发布流程、CI 校验、变更记录 | 本体 Owner | 模型一年后无人敢改 |

前两项属于“模型与数据”，后四项属于“工程与治理”。实践中失败的项目大多是只交付了第一项，第二到第六项从未规划。

## 判断项目是否真的实现了本体

不用看文档篇幅，看三个判据：

1. **有显式的概念体系**：类和关系的含义写在模型里，而不是散落在代码命名和口头共识中。
2. **有形式化表达**：机器可解析、可校验、可推理，不是纯文字说明。
3. **被系统使用**：生产路径上有查询、校验或推理在消费它。

三者缺一，就还停留在“写了个模型”。第三条最容易落空，也最值得在立项时就设计出来——至少要先有一个真实用例（一次检索、一次对账、一次发布前校验）跑通端到端。

## 为什么建议给语义留出独立的一层

把本体相关代码散落在业务模块里，短期看不出问题，长期有三个代价：

- **多消费方共享不了**：语义检索、规则校验、数据集成、报表口径往往需要同一份概念模型，散落各处就会出现四套略有差异的“事实标准”。
- **演化节奏冲突**：业务代码按周迭代，本体语义应保持稳定、按季度评审，混在一起会互相拖拽。
- **技能栈不同**：写 OWL/SHACL 与写领域代码是两类工作，混在同一个模块会让评审标准失效。

所以主流做法是设立一个**语义层**（也可叫知识层、语义服务层）：向上提供按用例命名的接口，向下屏蔽三元组库、推理器、外部数据源。DDD 的[端口适配器](https://ddd-fans.github.io/ddd-guideline/impl/arch-pattern/ports-and-adapters)同样适用于这一层，具体分层见[分层与六边形架构](/impl/arch-pattern/layered)。

## 实现与建模是双环，不是瀑布

实现过程中一定会发现模型问题，这属于正常反馈，而不是返工。有效的做法是让两个环快速转起来：建模出一个最小版本，立刻配样例数据和一个查询跑通，再回头改模型。

下面的最小闭环通常半天就能搭起来，比评审五十页文档更能暴露问题。

```turtle
@prefix : <https://example.com/onto/order#> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

:Order a owl:Class .
:DraftOrder rdfs:subClassOf :Order .

:order-1001 a :DraftOrder ;
    :placedBy :customer-42 .
```

```sparql
PREFIX : <https://example.com/onto/order#>
SELECT ?order WHERE { ?order a :Order . }
```

如果第二条查询返回的 `:order-1001` 是靠 `DraftOrder ⊑ Order` 推出来的，说明类层次、实例数据、查询链路都已打通；如果返回空，问题可能出在数据没加载、命名空间写错或推理没开，而这三类问题都必须在实现早期暴露。接着补 SHACL 校验和一条“能不能查出待处理订单”的能力问题（CQ），闭环就完整了。CQ 的写法见[能力问题](/modeling/method/competency-questions)。

## 技术选型的原则

选型不是选“最好的产品”，而是选“最不坏的一组约束”。按优先级：

1. **由问题倒推能力**。需要跨系统语义互操作、标准查询、可推理，才需要 RDF 栈；只是想要邻居遍历，属性图可能更省事；只是想要一张术语表，SKOS 加文档就够了。
2. **最小可运行优先**。先用嵌入式或单机三元组库（如 Jena TDB2、Oxigraph、RDF4J 内存库）把链路跑通，再决定要不要上集群。
3. **标准优先于产品**。Turtle、OWL、SHACL、SPARQL 是可迁移资产，专有查询语言和专用存储格式会形成锁定。
4. **把运维成本算进去**。图数据库的备份、升级、权限、监控都需要人力，小团队常低估这一块。
5. **与团队能力匹配**。团队里没人能读懂 OWL 公理时，复杂推理不要上生产。

存储的具体取舍见[存储选型](/impl/arch-pattern/storage)，推理能力见[推理与物化](/impl/arch-pattern/inference)。

## 与 DDD 的实现如何配合

本体和 DDD 不冲突，它们是两种不同中心：DDD 以**行为与一致性边界**为中心，本体以**共享语义与跨系统数据**为中心。落到实现上大致是这样分工的：

| DDD 概念 | 本体侧的对应物 | 注意 |
|---|---|---|
| 聚合 / 聚合根 | 通常对应本体中的核心类与个体 | 聚合内不变量用代码或 SHACL 表达，不要用 OWL |
| 仓储 | 语义层的查询/更新入口 | 仓储返回领域对象，语义层返回视图或查询结果 |
| 领域服务 | 语义服务（查询、推理、校验） | 语义服务不是业务行为的替代品 |
| 领域事件 | 知识库变更的来源之一 | 异步投递即可，避免与业务库强一致双写 |
| 限界上下文 | 本体模块与命名空间划分 | 见[模块化与复用](/modeling/elements/module) |

三条边界原则值得写进团队规范：

- **聚合不变量不要用 OWL 表达**。OWL 是开放世界假设，缺数据不会报错，只会推出更多结论；要“必须存在”就用 SHACL 或领域代码。这条与[约束与业务规则](/modeling/elements/constraint)一致。
- **不要在业务事务里双写**。写业务库成功、写知识库失败会造成长期不一致；用事件投递、批量同步或定期重建。
- **不要让业务代码直接拼 SPARQL**。查询应封装在语义层里按用例命名，便于优化、缓存和权限控制。

## 常见问题

**本体是不是就是文档？** 不是，但现实中很容易变成文档。判据见上文“三个判据”：能被系统消费才算实现。

**实现本体必须上图数据库吗？** 不必须。数据量小、查询简单时，内存三元组库或“关系库 + RDF 视图”完全够用；是否上图库取决于查询模式、推理需求和运维预算，见[存储选型](/impl/arch-pattern/storage)。

**一定要有推理吗？** 不一定。推理解决的是“隐含结论能否自动得出”，很多场景只靠显式数据和 SPARQL 就够。是否开启推理见[推理与物化](/impl/arch-pattern/inference)。

**和 DDD 项目二选一吗？** 不是。常见做法是业务系统继续用 DDD 管行为与一致性，另设语义层承载共享概念与跨系统查询，两者通过事件和查询接口松耦合。
