# OntoPlatform v0.2 控制闭环审计：逐功能判定与问题总结

> **审计对象**：`F:\piAgent\ontoPlantform`，版本 `0.2.0` 工作树。
> **审计视角**：工程控制论。把每个功能拆成设定值 `r`、观测 `y`、比较器 `e = r - y`、控制器、执行器 `u`、被控对象、反馈与收敛判定，检查回路是否真的闭合。
> **证据口径**：静态通读源码，加上在内存平台或临时 SQLite 平台上执行的小型探针。没有做生产压测、没有接真实 LLM、没有测量端到端时延。文中所有结论都标注了证据出处，探针结果见附录 A。
> **与旧报告的关系**：`docs/control-theory-review.md` 审的是 v0.1，当时的主要结论是"没有时间基准、没有执行门限与回执、没有独立验证、没有权限闭合"。v0.2 已经补上了这四类**零件**，但没有把它们接成可靠的**判定链**。本报告不重复旧结论，重点判断 v0.2 的零件是否咬合。
> **范围**：工作台、本体、数据、能力、应用、对象实例、运行、AI 助手、设置九个页面，以及身份权限、调度时钟两个横切能力。CLI 与 MCP 只在与页面共用用例时顺带提及，没有单独做完整审计。

## 摘要（结论先行）

**一句话**：v0.2 已经具备了控制回路的大部分零件，但还没有形成可依赖的自动闭环。当前系统的主要风险不再是"缺观测、缺执行器"，而是**假闭环**：传感器会给出绿色，执行器会给出成功，金丝雀会给出"已隔离"，控制器会给出"已修复"，但这些信号都不等于被控对象真的达成了目标。人仍然是系统里唯一的时钟、比较器和最终验收人。

**最重要的五个判断**：

1. **没有任何一个功能是自动闭环。** 投影同步、事件投递、目标评估、控制器周期、金丝雀分析全部依赖人打开页面或点击按钮。工作台里的"控制回路"示意图表达的是设计意图，不是当前运行事实。
2. **零样本会显示为绿色。** 新工作空间没有任何执行记录时，`success_rate = 1.0`、`samples = 0`、`projection_age_seconds = 0`，SLO 总体 `ok = true`。工作台随后显示"成功率 100%"和"全部达标"。
3. **成功是标签，不是验证。** 超时返回 `status = unknown`，但 `ok = true`；后置条件验证失败，`ok` 仍然是 `true`；前端只读 `ok`，于是把"结果未知"和"条件不满足"都显示成"执行完成，业务状态已更新"。
4. **执行器没有真正的回执。** 同一个幂等键的并发调用可以执行两次；超时后放弃的工作线程仍可能继续写世界；回滚在当前进程里生效，进程重启后会重新装载最新 schema，而不是回滚指针指向的 schema；金丝雀发布直接改写当前服务使用的运行时。
5. **反馈链末端是空的。** 生产代码没有注册任何 outbox 订阅者，`dispatch` 仍会把事件标记为"已投递"；对账器忽略映射过滤和对象归属，把投影之外的对象当成漂移；控制器只会重跑投影，遇到不可收敛的漂移时会反复提出同一个动作，且没有升级路径。

**问题分级**：P0 四项，集中在"成功判定失真"和"发布控制失效"；P1 七项，集中在"反馈链未接线"和"人工替代时钟"；P2 四项，集中在"可观测性表达"和"配置治理"。

## 一、判定标准与阅读方式

### 1.1 控制回路的最小闭环

控制论里的闭环不是"有输入有输出"，而是下面这条因果链必须完整，并且每一段都要有工程约束：

```text
    r（目标/设定值） ──▶ 比较器 e = r - y ──▶ 控制器 ──▶ 执行器 u ──▶ 被控对象 ──▶ y（输出）
                              ▲                                              │
                              └──────────── 观测器/传感器（含噪声与时滞） ◀──┘
```

一个功能只有在满足下列条件时，才可以在本报告里称为"闭环"：

| 环节 | 判据 | 本报告检查什么 |
|---|---|---|
| 目标 `r` | 可量化、可判定达成，且有明确的时间窗 | 有没有目标、阈值、窗口、成功谓词 |
| 观测 `y` | 有采样时刻、有样本量、能区分"没变"与"没看到" | 指标是否全时段累加、零样本如何处理、是否刷新 |
| 比较 `e` | 由独立测量计算，不由执行者自报 | 验证是否真正参与判定，还是只记录 |
| 执行 `u` | 有权限、有幂等、有超时、有回执、可补偿 | 失败后状态是否一致，重试会不会重复施加 |
| 反馈 | 执行后重新观测，确认误差缩小 | 有没有"动作后复测"，复测失败是否升级 |
| 收敛/稳定 | 扰动下有界，不能反复震荡或无限重试 | 不收敛时是否有停止条件和人工升级 |

### 1.2 五种判定

| 判定 | 含义 |
|---|---|
| **闭环（执行级）** | 一个执行周期内目标、观测、比较、执行、补偿齐全，能处理失败，但不一定有跨周期的自动调度 |
| **半闭环（人工）** | 零件齐全，但需要人触发、人判断或人复测；人不来时回路静止 |
| **开环** | 只有展示或只有执行，结果没有回到判定，或者只有设计期输入 |
| **假闭环** | 有"成功/达标/已投递/已隔离"的信号，但信号不真实、不可验证，或动作后不收敛 |
| **只读/不适用** | 纯查询、纯设计或纯展示功能，本身不需要控制回路；只检查输出是否可信 |

"假闭环"是本报告最关注的类别。它不是"没有功能"，而是**功能给出了会误导操作者的确定性**。

### 1.3 v0.1 四个旧断点的复核

v0.2 确实补了零件，但多数停在"有记录"而不是"参与判定"：

| 旧断点 | v0.2 已补的零件 | 复核结论 | 仍然缺什么 |
|---|---|---|---|
| 没有时间基准 | change `seq/ts`、execution 记录、projection run、as-of 历史 | 半闭合 | 指标没有时间窗；目标窗口只裁剪样本；新鲜度把"没同步"和"没变化"混在一起 |
| 没有执行门限与回执 | 租约、速率限制、32 个执行槽、超时、三态、幂等键、execution 记录 | 半闭合 | 幂等检查在租约外；超时放弃线程；unknown 没有解析器；UI 把 unknown 当成功 |
| 没有独立验证 | verifier、reconciler、controller、SLO、objective | 半闭合 | 后置条件不参与 `ok`；对账集合错误；控制器不收敛；SLO 零样本绿 |
| 没有权限闭合 | 角色矩阵、action 级检查、bearer token、审计 | 半闭合 | 默认 actor 是 admin；token 模式所有调用者折叠成同一个 actor；读操作没有可见性边界 |

这个复核结果很重要：v0.2 的进步是真实的，问题从"没有零件"变成了"零件不咬合"。因此下面的建议不是推翻重来，而是把已有的传感器、验证器、执行器接到判定链上。

## 三、按页面看回路断在哪里

### 3.1 工作台：一张好看的回路图，不是运行中的回路

工作台聚合了 SLO、成功率、未知率、待投递事件和控制回路示意图。它的数据来自后端 `/metrics` 和 `/slo`，本身没有控制动作，属于只读看板。问题在于它把"零件存在"表达成了"回路闭合"。

- `frontend/src/views/Workbench.tsx:243` 用 `slo.ok` 渲染"全部达标"，`:244` 显示成功率，`:252` 用待投递事件画积压。
- `frontend/src/views/Workbench.tsx:388` 附近的 `LoopDiagram` 画出"目标 -> 控制器 -> 内核 -> 对象世界 -> 观测 -> 对账"的完整箭头，但没有标注任何"人工触发""手动刷新""无自动调度"。
- 同一页面每张卡片只在挂载或手动刷新时取数，没有轮询。页面上的"实时"语义只对本次请求成立。
- 最近事件卡用 `dispatched_at` 显示"已投递"（`:320`），但生产代码没有 outbox 订阅者，详见 P1-7。

**判定**：看板本身是开环展示；SLO 卡是假闭环；回路图是表达误导。这里不需要增加自动动作，但必须把"快照时间""样本量""人工触发"画出来，否则操作者会以为系统在持续控制。

### 3.2 本体：设计期闭环最好，发布期缺少部署后复测

本体编辑、检查、修订、AI 快速建模这一组是 v0.2 做得最完整的设计期闭环：

- 编辑保存草稿，`lint` 发现问题，人修改后再发布，这是典型的人工在环设计回路。
- AI 快速建模把 LLM 限定为"提议者"：LLM 只产生草稿，平台做归一化和校验，人确认后才 apply。这个边界是正确的，LLM 没有直接写运行时。
- 发布走编译、运行时安装、切发布、部署指针。`cut` 与本体/能力聚合在同一个事务里，发布快照不可变，指纹也能对上。

但发布链有两个缺口：

1. **运行时先于控制面提交。** `SchemaPublisher.publish` 在 `src/onto_platform/application/ontology_usecases.py:486` 先调用 `gateway.publish_schema(payload)`，之后才保存 `schema_payload`，调用方 `PublishOntology` 再到 `:351` 才开启事务保存本体、切发布、部署。中间任何一步失败，运行时已经是新 schema，但数据库里的本体、发布指针或 `schema_payload` 可能是旧的。没有补偿，也没有启动时的"发布意图恢复"。
2. **部署后没有独立健康复测。** 发布成功只代表内核接受了 schema，不代表对象世界、查询、能力调用在真实流量下正常。`deploy_release` 返回后，没有一次"读回当前部署指纹、跑一条代表性查询、比对 SLO"的动作。

**判定**：本体编辑和 AI 草稿是半闭环（人工），发布是半闭环（原子性缺口），不能称为生产级闭环。

### 3.3 数据：同步是人工的，新鲜度传感器把"没变"误判为"没看"

`RunProjection` 已经有水位、run 记录、内容哈希跳过，这些是 v0.2 的实质进步：

- 相同内容再次同步会返回 `skipped: true`，避免无意义写入。
- 每次真正运行都会记录 `projection_run`，包含状态、水位、写入数量。
- 变更传播时会删除上一次 materialize 过、这次不存在的对象，方向是对的。

但这条回路的三个关键点仍然不闭合：

1. **没有调度。** 同步只能由人点击"立即同步"或控制器显式重跑触发。外部数据源变化不会自动进入系统，`frontend/src/views/Data.tsx:24` 的 `sync` 是纯手动 action。
2. **删除与 upsert 不在一个事务里。** `src/onto_platform/application/data_usecases.py:202` 先 `apply_delta`，`:210` 再 `delete_objects`。如果删除失败，upsert 已经生效，run 会被记为 `failed`，但世界处于半写状态。`Data.tsx` 卡片文案说"失败不会留下半写状态"，与实现不一致。
3. **新鲜度语义错误。** `slo.py:68-72` 用最近一次有 `finished_at` 的 projection run 计算年龄。源没变化时同步会被 skip，不产生新 run，年龄继续增长。一小时后 SLO 会报"新鲜度越线"，但数据其实是最新的；反过来，源已经变化但人一直没点同步，也可以用旧的 run 让页面暂时看起来"新鲜"（直到年龄越线）。它测的是"上次写入时间"，不是"上次校验时间"。

另外，数据源连接器的 `fetch` 没有行数上限或分页，REST 超时是 30 秒，同步在 HTTP 请求线程里同步执行。大源会造成请求超时、内存压力和"前端放弃但服务端仍在跑"的时滞问题。这是稳定性与饱和风险，不是已经实测的故障。

**判定**：半闭环（人工），且有完整性缺陷。新鲜度传感器需要区分 `last_change` 与 `last_check`。

### 3.4 能力：执行器有行程限制，但成功判定和重试语义不可靠

能力是控制论意义上最像"执行器"的部分。v0.2 已经有三态、租约、超时、执行槽、审计和执行记录，这些零件都在：

- `src/onto_platform/ports/runtime.py:86-105` 定义 `succeeded/failed/unknown`，并明确 unknown 不能当失败。
- `src/onto_platform/infrastructure/runtime/kernel_gateway.py:45` 的 `BoundedSemaphore(32)` 限制并发执行，`:367-375` 超时返回 unknown。
- `src/onto_platform/application/limits.py:72` 的租约按 `workspace:target` 串行化，避免同一目标上的读改写互相覆盖。
- `src/onto_platform/application/capability_usecases.py:144-148` 的文档明确写了幂等键和 unknown 重试语义。

但实际行为有三个严重偏差：

1. **unknown 被下游压成成功。** `InvocationResult.ok` 是 `status != "failed"`，所以 unknown 的 `ok` 为 `true`。`capability_usecases.py:216` 把 `ok` 原样放进响应，前端 `Capability.tsx:282` 只看 `r.ok`，于是超时显示"执行完成，业务状态已更新"。前端 `InvokeResult` 类型甚至没有 `status` 和 `verification` 字段，无法正确渲染三态。
2. **幂等检查在租约外。** `capability_usecases.py:164` 先查幂等记录，`:176` 才进入租约。两个并发请求可以同时通过检查，然后串行执行两次。探针实测同一幂等键并发调用后余额增加两次，而 execution 记录只剩一条（后写覆盖前写）。
3. **超时放弃的线程仍可写世界。** 超时返回后租约释放，原线程继续运行；用同一个幂等键立即重试会再执行一次。探针实测超时后重试，最终余额增加两次，执行记录被第二次覆盖成 succeeded，第一次 unknown 消失。

后置条件的情况同样严重：`CapabilityVerifier.verify_invocation` 会记录 `post.ok = false`，但 `payload["ok"]` 仍来自 `result.ok`，没有因为后置失败而改变。探针里后置条件要求余额为 999，实际被写成 1，接口仍返回 `ok = true, status = succeeded`，只有 `verification.post.ok = false`。这个验证结果不会触发补偿、不会改变 SLO（SLO 只数 status）、也不会被 UI 展示，属于典型的"验证存在但不参与判定"。

契约 UI 还有一个直接错位：`Capability.tsx:236` 提示的"输入契约"是 `{"required": ["amount"], "amount": {"min": 1}}`，而后端 `validate_contract` 期望的是 `preconditions/postconditions/effects/compensate`。用户按提示填写的 JSON 会被接受为空契约，验证器不会运行。契约里的 `effects` 和 `compensate` 会被校验，但当前没有执行路径真正使用它们；工作流步骤的补偿是另一套机制。

**判定**：直接调用是假闭环。它有最完整的零件，却在最关键的"结果真实性"和"重试不重复"上失效。工作流是唯一执行级闭环，因为 `GatewayWorkflowRunner` 在步骤失败时反向补偿，并把 unknown 当失败处理，但工作流本身没有自动重试、断点续跑和超时预算。

### 3.5 应用与目标：目标评估是读页面触发的，待办只是备忘录

应用目标看起来最像"设定值"：

- `SetObjective` 接收 `metric/target/band/window`。
- `EvaluateObjective` 计算偏差，越线时开 todo 并发 `application.objective_breached`。
- 应用页读取目标时触发评估，todo 可以标记 resolved。

但这条回路断在三个地方：

1. **评估不是周期采样。** 只有 `GET /applications/{aid}/objective` 被调用时才评估，即人打开应用页。没人看页面，就没有评估、没有 todo、没有事件。`window` 只用于裁剪历史样本，不用于计算指标窗口；指标来源仍是全局 SLO 的全时段值。
2. **传感器是全局的。** 应用目标拿的是整个工作空间的 SLO，而不是这个应用自己的窗口指标。不同应用共享同一个成功率和新鲜度，目标之间没有独立观测。
3. **resolve 没有动作和复测。** `ResolveTodo` 只把状态改成 resolved，不要求执行任何修复，也不重新评估。如果越线仍在，下次读页面会再开一个新 todo。todo 是提醒，不是控制动作。

另外，SLO 的零样本假绿会直接传给目标：新空间没有执行记录，目标评估仍可能认为成功率达标。`window` 在样本少于两条时返回 flat，趋势也不是时间序列意义上的趋势，而是"最近两次打开页面"的差。

**判定**：假闭环。它有目标、有偏差、有 todo，但没有周期采样、没有应用级观测、没有修复动作和验收。

### 3.6 对象实例：读路径基本可靠，但显示和时区会污染观测

对象查询、变更流、历史回读是读路径，本身不需要控制目标。它们的价值是给人和控制器提供可信的 `y`。

做得好的部分：

- 历史回读在请求早于 change log 窗口时会拒绝，而不是返回错误答案。这是很重要的正确性设计。
- 变更流有 cursor 和 compaction 边界，超出窗口要求 resync。
- 查询支持过滤和分页（`find` 有 limit/offset/report）。

但观测质量有三个问题：

1. **属性显示仍可能失真。** `StateBrowser.tsx:172` 和 `:297` 用 `String(v)` 渲染属性值。本体支持 `object` 和 `array` 类型，嵌套值会显示成 `[object Object]` 或逗号拼接，读的人会得到错误的状态印象。这不是控制逻辑错误，但属于"传感器显示噪声"。
2. **对象详情是一次性快照。** `ObjectDrawer` 加载后不自动刷新；变更流是另一个面板，两者不是同一个采样时刻。用户可能把旧详情和新变更混在一起看。
3. **按时间回读的时区语义不一致。** UI 提示"生效时间（UTC）"，但 `datetime-local` 输入的是浏览器本地时间；后端 `history._parse_ts` 把无时区值当作 UTC。东八区用户选择本地时间会得到偏差 8 小时的快照。本报告不把它列为 P0，因为它只影响回读，不影响写入，但它会误导故障复盘。

**判定**：查询与历史是只读闭环（窗口内可信），对象详情是开环观察，显示层有时区与嵌套值噪声。

### 3.7 运行：所有慢回路都在这里，但没有一个自动运行

运行页是控制论意义上的"控制室"，包含指标、SLO、发布、事件、校验、对账、控制器。它的问题不是缺功能，而是缺时钟：

- **指标是全时段计数器**，没有 window、没有 rate、没有分母的最小样本。`metrics.py:42-62` 直接从 repo 累加，`executions_total` 包含历史全部执行。
- **SLO 的零样本假绿**见 P0-4。`slo.py:43` 在 `total == 0` 时返回 1.0；`:68-72` 在没有 projection run 时返回 0 秒；`:84-87` 的 `_indicator` 不检查样本量。
- **发布/金丝雀/回滚**见 P0-3。`releases.py:99` 让 canary 和 current 共用一个 gateway，`:180` 的提升健康门只看全局 SLO。
- **事件投递**见 P1-7。`events.py:130-141` 在没有 handler 时仍然 `delivered += 1` 并 `mark_dispatched`。
- **校验与对账**：`RuntimeVerifier` 只检查必填属性与同类型内的身份重复，不检查属性类型、关系完整性，身份唯一性也只在当前加载或采样集合内判断；`Reconciler` 只比较 ID 集合。`verifier.py:253-256` 用投影源 ID 集合减去全部运行时 ID 集合，忽略了 `mapping.filter`、`exclude_missing_id` 和"由其他来源创建"的对象。控制器于是会把合法对象当成漂移。
- **控制器**：`controller.py:44-51` 只会提出 `run_projection`，`act` 在 `:93` 复测一次，但无论复测是否通过都只记录 `verified: false`，没有升级、没有停止条件、没有第二次不同动作。对账器每次运行都会发 `reconciliation.found_differences`（`:266`），即使 findings 为空，造成事件噪声。

这些慢回路全部由 API 请求或按钮触发。没有后台 worker、没有周期任务、没有 lease 式调度器。于是"闭环"只在一次点击的瞬间成立，之后世界继续漂移，系统不会自己发现。

### 3.8 AI 助手：工具回路是闭的，目标回路是开的

AI 助手有两个入口：

- "问业务世界"是确定性的语义检索，返回答案、依据对象和术语。它没有控制目标，属于只读问答。它至少把依据列出来了，比纯 LLM 回答可信。
- "交给它一件事"是 `AgentRunner` 的 goal -> 工具调用 -> observation -> answer 循环。工具调用本身有审计，嵌套能力调用仍走 `InvokeCapability` 的权限检查，这点是正确的。

但目标回路没有闭合：

- `agent_runner.py:132-138` 只要 LLM 返回 `answer` 就 `run.ok = True` 并结束。`finish` 是模型自报，不是平台对目标的独立验收。
- 步数预算耗尽时 `_force_answer` 再问一次，仍由模型决定答案，`ok = bool(run.answer)`。这解决了"有观察却无答案"的体验问题，但没有解决"答案是否达成目标"的问题。
- 步骤只存在于响应里，`intelligence_usecases.py:124` 的审计只记录 goal、ok、steps 数量，不持久化每一步的 thought/action/observation。UI 说"每一步都留痕"，实际只有最终答案和审计摘要可回看，无法复现推理链。
- 没有时间预算、成本预算、目标成功谓词。LLM 的"完成"和世界的"完成"之间没有独立测量。

**判定**：工具执行级有观测回路，目标级是假闭环。对"查询型"目标可以接受；对"改变世界型"目标，必须有平台侧验收。

### 3.9 设置与权限：界面写了边界，身份没有闭合

设置页明确写了成员角色"作为后续权限校验的边界；不会改变已有数据的可见性"（`Settings.tsx:125`）。这是诚实的，但也说明角色不是数据可见性控制。

后端 `api.py:145-165` 的 actor 解析：

- 没有 `ONTO_API_TOKEN` 时，body/query 的 `user` 直接作为 actor，默认 `admin`。
- 有 token 时，所有调用者被映射为 `ONTO_API_TOKEN_ACTOR`，默认 `api-client`。
- 前端 `api.ts:253` 固定 `USER = "admin"`，所有请求都以 admin 身份发出。

因此：

- 默认部署没有身份验证，任何能访问端口的人都是 admin。
- token 模式解决了"不能冒充任意 user"，但把多用户折叠成一个 actor，审计无法区分人。
- 角色矩阵能阻止 viewer 执行写动作，但读操作没有按成员角色过滤，成员关系不构成可见性边界。
- 审计记录的是声明的 actor，不是经过认证的主体。

**判定**：权限是"动作级检查"的半闭环，不是身份闭环。对本地单用户演示可接受，对生产不可接受。

### 3.10 模型配置：全局单例，没有审计和版本

`LlmPicker.tsx:22` 把 provider 保存到服务端，`:28` 提示"已保存到平台"，同时 `store.tsx:149` 把包括 `api_key` 在内的设置写进浏览器 `localStorage`。`POST /api/llm` 只在内存里配置平台 provider，没有审计、没有按工作空间隔离、没有模型版本固定。

这带来的控制论问题：

- 模型是控制器的一部分。控制器参数（模型、温度、提示词）变化时，回路增益会变化，但平台没有记录"这次执行用的是哪个模型"。
- 全局模型意味着一个工作空间换模型会影响所有工作空间，无法做 A/B 或 canary。
- 浏览器保存密钥扩大了泄露面；对本地单用户是便利，对多用户不是。
- 模型切换没有事件、没有审批、没有回滚。

**判定**：开环配置。对本地演示可接受，对生产需要按工作空间固定版本、加密密钥、审计变更。

## 四、系统性问题（按优先级）

### P0-1 成功判定失真：unknown 与后置条件失败都被显示成成功

**断点**：反馈环节。系统确实观测到了 unknown 或 postcondition false，但没有把它送进 `ok`、UI、SLO 和后续动作。

**证据**：

- `src/onto_platform/ports/runtime.py:103-105`：`ok` 定义为 `status != "failed"`，unknown 因此为 true。
- `src/onto_platform/application/capability_usecases.py:216`：响应 `ok` 直接取 `result.ok`。
- `src/onto_platform/application/capability_usecases.py:209-225`：post 验证结果只放进 `verification`，不改变 `ok/status`。
- `frontend/src/views/Capability.tsx:282`：toast 只判断 `r.ok`。
- `frontend/src/api.ts` 的 `InvokeResult` 没有 `status` 和 `verification` 字段。

**探针**：

- 后置条件要求余额 999，能力把余额写成 1，返回 `ok=True, status=succeeded, post.ok=False`。
- 超时 0.2 秒的调用返回 `status=unknown, ok=True`，UI 会显示成功。

**影响**：操作者以为动作成功，实际结果未知或条件不满足；SLO 仍把该次执行算作成功；审计也无法从 `ok` 区分。对写世界的能力，这是正确性问题，不是体验问题。

**建议**：把 `status` 作为响应的一等字段，`ok` 只对 `succeeded` 为 true；unknown 和 postcondition false 必须有独立的红色状态和明确下一步（重试、查证、补偿）。后置失败至少要改变执行状态并触发 todo/事件，不能让 `verification` 成为装饰。

### P0-2 幂等与超时语义不成立：重试会重复施加

**断点**：执行器与稳定性。重试是控制器应对 unknown 的标准动作，但当前重试不安全。

**证据**：

- `src/onto_platform/application/capability_usecases.py:164-178`：先查幂等记录，再进租约，检查不是原子的。
- `src/onto_platform/infrastructure/runtime/kernel_gateway.py:367-375`：超时返回 unknown 后，工作线程继续运行。
- `src/onto_platform/application/capability_usecases.py:167`：unknown 记录会被重试，但没有阻止旧线程继续写。
- `src/onto_platform/application/capability_usecases.py:234-276`：execution 以幂等键为主键，后写覆盖前写，unknown 的历史可能丢失。

**探针**：

- 两个并发同键慢调用：余额从 100 变成 102，execution 只有一条，两个响应都不是 replay。
- 超时后立即同键重试：第一次 unknown，第二次 succeeded，最终余额 +2，记录只剩 succeeded。

**影响**：幂等键本来是"恰好一次"的承诺，现在只是"通常一次"；超时重试会把重复写入带进业务状态。控制器如果自动重试，会放大这个问题。

**建议**：在租约内用数据库唯一约束原子占位；unknown 记录保留并绑定 `execution_id`；旧线程写世界需要 fencing token 或取消机制；同一键的重试在旧执行未确认前必须拒绝或进入人工解析队列。先实现"unknown 解析器"，再谈自动重试。

### P0-3 金丝雀不隔离，回滚不持久

**断点**：被控对象与执行器。发布控制的目的是让"服务版本"可预测地变化，当前 canary 和 rollback 都没有做到。

**证据**：

- `src/onto_platform/application/releases.py:99-103`：`deploy_release` 对 current 和 canary 都调用同一个 `gateway.publish_schema`，canary 直接改写正在服务的运行时。
- `src/onto_platform/application/releases.py:159-168`：`canary` 只移动 canary 指针，但运行时已经被改写；`:180-186` 的 `require_healthy` 只看全局 SLO，没有 canary 流量、canary 窗口或 canary 指标。
- `src/onto_platform/application/releases.py:84-123`：`deploy_release` 不保存 `schema_payload`；`src/onto_platform/application/common.py:132-145` 在重启时用最新 `schema_payload` 自愈，而不是用部署指针。
- `src/onto_platform/application/common.py:148-174`：指纹不一致只 audit/事件，不阻止服务漂移。

**探针**：

- 当前发布是最新版本（含 probe 能力），把旧发布设为 canary 后，当前指针仍是新版本，但运行时 functions 只剩 `Vehicle.recharge`，当前发布里的 probe 能力消失。
- SQLite 平台回滚到旧发布后，当前进程运行时正确；重启后指针仍是旧发布，但运行时 functions 变成 `Vehicle.probe, Vehicle.recharge`，并出现 `schema.fingerprint_mismatch`。

**影响**：操作者以为 canary 只影响一小部分流量，实际当前服务已经被 canary schema 改写；操作者以为回滚成功，重启后却回到未回滚的 schema。发布控制的金标准是"指针、运行时、实际流量三者一致"，当前三者可以互相矛盾。

**建议**：canary 使用独立 runtime 命名空间或影子网关，不能调用当前 gateway；提升门必须基于 canary 自己的流量窗口和指标；部署/回滚必须把 payload 绑定到 deployment 记录，或从 release 重建，不能依赖全局最新 `schema_payload`；启动自愈必须以部署指针为准，指纹不一致时拒绝服务或强制修复，而不是只记录。

### P0-4 SLO 零样本假绿与全时段指标

**断点**：传感器与比较器。没有样本时系统给出"达标"，这会让所有上层控制器失去正确的误差信号。

**证据**：

- `src/onto_platform/application/slo.py:43`：`success_rate = 1.0 if total == 0`。
- `slo.py:44`：`unknown_rate = 0.0 if total == 0`。
- `slo.py:68-72`：没有 projection run 时返回 0 秒。
- `slo.py:84-87`：`_indicator` 只比较数值，不要求最小样本。
- `slo.py:60`：`ok = all(...)`，零样本时全部为 true。
- `frontend/src/views/Workbench.tsx:243-245`：直接渲染"全部达标"和成功率。
- `frontend/src/views/Operations.tsx` 的 `SloList` 显示"0 样本"但仍打"达标"。

**探针**：新建空工作空间，`/slo` 返回 `ok=True`，成功率 `value=1.0, samples=0`，新鲜度 `0.0`，unknown 率 `0.0`。

**影响**：新工作空间、刚清空历史、或某类执行从未发生时，系统看起来是健康的；目标评估、控制器、工作台都会继承这个假信号。全时段累加还会让很久以前的失败永久压低当前成功率，让修复后的系统长期"越线"。

**建议**：指标必须有窗口（例如 5 分钟、1 小时、24 小时）和最小样本；零样本返回 `no_data`，不要返回 `ok=true`；SLO 总体在 `no_data` 时显示"数据不足"而不是"达标"；区分"最近一次检查"与"最近一次变更"；目标窗口真正参与指标计算，而不是只裁剪样本。

### P1-5 发布与部署不是原子操作

**断点**：执行器与恢复。运行时先改、数据库后改，失败时没有补偿。

**证据**：

- `src/onto_platform/application/ontology_usecases.py:486` 先 `gateway.publish_schema`，`:490` 保存 `schema_payload`，`:351` 才进入事务保存本体、切发布；`:368` 再 `deploy_release`。
- `src/onto_platform/application/capability_usecases.py:108-121` 同样先发布，再事务，再部署。
- `deploy_release` 自己也是"先 publish，再指针事务"。
- 没有恢复日志或启动时 reconcile 未完成发布。

**影响**：如果进程在运行时发布后崩溃，数据库可能没有新发布，下一进程用旧 `schema_payload` 自愈，产生指纹不一致；或者数据库有发布但指针没移动。当前只在自愈时 audit，不会自动修复。

**建议**：把"发布意图"先写入控制面（intent/release），运行时安装幂等，指针提交作为最后一步；启动时扫描未完成 intent 并重放或回滚；部署以 release 的 payload 为准，而不是全局最新 payload。

### P1-6 对账传感器有假阳性，控制器不收敛

**断点**：观测模型与收敛判定。控制器基于错误的误差信号动作，动作后不收敛也没有升级。

**证据**：

- `verifier.py:253-256`：运行时 ID 集合包含该类型全部对象，源集合只包含当前投影的行；没有按 `mapping.filter`、`exclude_missing_id` 或 owner 过滤。
- `verifier.py:257-264`：只比较 ID，不比较属性值、关系、类型。
- `controller.py:44-51`：只有 `run_projection` 一种修复动作。
- `controller.py:93-107`：复测 `verified` 只返回给调用者，没有失败升级；`:99` 审计只记计数，没有 proposal 细节。
- `verifier.py:266-269`：每次 reconcile 都发 `reconciliation.found_differences`，即使 findings 为空。

**探针**：在投影之外创建一个合法对象 `TollStation/EXTRA`，对账把它报为 `missing_in_source`；控制器执行 `run_projection` 后复测仍为 false，对象仍在，第二次对账还是同一个 finding。

**影响**：合法对象被当成漂移，控制器重跑投影无法删除它；人看到"已验证 false"但没有下一步，容易反复点击。反过来，属性值错误、关系缺失、来源对象带 filter 的情况可能被漏报。

**建议**：对账要按投影的 ownership 和 filter 计算期望集合，并比较属性值、关系、类型；控制器需要多种修复动作（重跑、删除、重建、隔离）和"连续 N 次不收敛就开 todo/告警"的停止条件；reconcile 只在有差异时发事件。

### P1-7 outbox 是空转的反馈链

**断点**：反馈链末端。事件已经产生，但没有消费者，投递动作却标记成功。

**证据**：

- `src/onto_platform/application/events.py:124-125` 定义了 `subscribe`，但 `src/` 内没有任何调用。
- `events.py:130-141`：`handlers` 为空时仍 `delivered += 1` 并 `mark_dispatched`。
- 生产没有后台 dispatcher，只有 `POST /events/dispatch` 手动触发。
- UI `Operations.tsx:437` 说"按订阅者逐个投递"，`:447` 允许"投递待处理"，`:406` 显示"已投递"。

**探针**：一个全新平台有 7 条 pending 事件，没有注册任何订阅者；`dispatch` 返回 `dispatched=7, failed=0`，pending 变成 0，subscriber map 为空。

**影响**：外部系统没有收到任何事件，但控制台显示"已投递"；工作台把积压清零，操作者以为集成正常。这是最典型的"反馈假信号"。

**建议**：没有 handler 时事件不能被标记 delivered，或者至少标记为 `no_consumer` 并保持 pending；生产必须注册至少一个审计/日志消费者，或明确显示"未配置消费者"；投递失败要有退避、重试上限和死信；dispatcher 应由后台任务周期运行。

### P1-8 应用目标与待办是"读页面触发"的提醒系统

**断点**：目标、观测、执行三处都不闭环。

**证据**：

- `src/onto_platform/interfaces/api.py:312-313`：只有 GET objective 时调用 `evaluate`。
- `objective_usecases.py` 的 `window` 只在 `_prune_samples` 里使用；指标来自全局 SLO。
- `ResolveTodo` 只改状态，不要求动作，不重新评估。
- 前端应用页只在加载时取 objective。

**影响**：目标越线不会主动被发现；待办可以被"标记解决"而世界没有变化；下次打开页面会重新开 todo。控制器和目标是两套独立系统，没有共享误差信号。

**建议**：由调度器周期性评估目标；目标指标必须窗口化、应用级；todo 携带证据、建议动作和验收条件；resolve 前要求重新评估或至少显示当前偏差；越线未解决时不要重复开新 todo，而是更新同一个事件。

### P1-9 没有调度器，人就是时钟

**断点**：时间基准。所有慢回路都缺少采样周期和动作周期。

**证据**：

- 没有后台 worker 或 scheduler；投影、outbox、objective、controller 都由 HTTP 请求触发。
- 工作台/运行页没有轮询，只有手动刷新。
- `Operations.tsx:223` 说"控制器只提建议，不自动执行"，这对安全是合理的，但没有"谁在什么时候必须来看"的约束。
- SLO 没有采样周期，objective 没有定时评估，event dispatch 没有定时器。

**影响**：控制回路的时延等于"人下次打开页面的时间"，不可界定。扰动可能在无人查看时持续扩大；人来了才看到快照，快照还可能已经过期。这不是稳定性问题，而是"回路是否在运行"的问题。

**建议**：增加一个最小调度器（线程或独立 worker）和 lease，周期执行 outbox dispatch、SLO 采样、objective 评估、controller observe；所有周期任务可配置、可观测、可暂停；工作台显示"上次采样时间"和"下次计划时间"；人工触发仍保留，但不再是唯一时钟。

### P1-10 数据同步的完整性、饱和与新鲜度

**断点**：执行器原子性、稳定性、传感器语义。

**证据**：

- `data_usecases.py:202-211`：upsert 与 delete 分开，删除失败留下半写状态。
- `data_usecases.py:176-183`：skip 不记录 run，新鲜度仍按上一次写入算。
- `data_usecases.py:160-174`：connector 一次取全部行，没有 limit/分页/背压。
- REST 连接器超时 30 秒，同步在请求线程执行。
- `Data.tsx:28`：toast 只显示写入数量，不显示 skipped、失败原因或当前水位。

**影响**：源很大或删除失败时，操作者看到的是"成功/失败"二元提示，实际状态可能半写；源没变时新鲜度会误报越线；前端 15 秒超时放弃请求，但服务端继续执行，产生"前端认为失败、后端已成功"的时滞。

**建议**：把 upsert/delete 放进同一个 kernel 事务或增加补偿；记录 last_check 和 last_change 两个时间；连接器支持 limit/分页和超时预算；同步改为后台任务并返回 run id，前端轮询 run 状态；UI 显示 skipped 和差异数量。

### P1-11 权限边界不是身份闭环

**断点**：控制器的授权输入不可信。

**证据**：

- `api.py:163-165`：默认 actor 为 `admin`，body/query 可自报 user。
- `api.py:156-162`：token 模式所有调用者折叠为同一个 actor。
- `frontend/src/api.ts:253`：前端固定 `USER = "admin"`。
- `Settings.tsx:125`：成员角色不改变数据可见性。
- 读操作没有按成员角色过滤。

**影响**：审计里的 actor 不是经过认证的主体；多用户部署无法归因；viewer 的读边界不存在，敏感数据对所有能访问端口的人可见。

**建议**：至少支持一种真实身份（签名 session 或 OIDC）；默认拒绝匿名 admin；token 模式传入 actor id 而不是固定字符串；把成员角色接到读过滤，或者明确声明系统是单租户单用户并移除误导性的成员 UI。

### P2-12 Agent 目标没有独立验收

**断点**：目标判定与反馈。工具回路闭合，目标回路由 LLM 自报。

**证据**：

- `agent_runner.py:132-138`：收到 `answer` 即 `ok`。
- `agent_runner.py:151-159`：步数耗尽强制回答，`ok = bool(answer)`。
- `intelligence_usecases.py:124-125`：审计只记 goal、ok、steps 数量，不持久化每一步。
- 前端 `Assistant.tsx:173-174` 用 `run.ok` 显示"已完成/未完成"。

**影响**：模型说完成不等于世界完成；失败无法复盘；多步推理链不可审计。

**建议**：为目标增加平台侧成功谓词（对象状态、查询结果、后置条件）；保存完整 step trace 和工具输出；增加时间/成本预算；完成前由独立 verifier 检查；失败时返回未达成原因，而不是只有 `ok=false`。

### P2-13 观测显示会污染判断

**断点**：传感器显示噪声与时滞。

**证据**：

- `StateBrowser.tsx:172` 与 `:297` 用 `String(v)` 渲染嵌套属性，仍可能出现 `[object Object]`。
- `ObjectDrawer` 只加载一次，变更流是独立面板，时间点不一致。
- 按时间回读把本地 `datetime-local` 当 UTC 解析，东八区会偏 8 小时。
- 运行页指标标为"实时快照"，但没有轮询。

**影响**：人看到的值可能不是真实值，或不是同一时刻的值；回读时间错误会让故障复盘得出错误结论。

**建议**：用结构化属性渲染器（对象展开、数组列表、JSON 折叠）；详情与变更流共享刷新时刻或显示各自采样时间；时间输入明确时区并转换；所有"实时"标签改成"截至 HH:mm:ss 的快照"。

### P2-14 模型配置是全局可变参数

**断点**：控制器参数治理。

**证据**：

- `LlmPicker.tsx:22-29`：保存到平台并 toast"已保存"。
- `store.tsx:149`：`api_key` 写入 localStorage。
- `POST /api/llm` 没有审计、没有工作空间隔离、没有模型版本记录。
- 执行审计不记录本次使用的模型。

**影响**：模型变化不可追溯，无法做 canary 或回滚；密钥泄露面扩大；同一个工作空间的执行可能在不同模型下产生不同结果。

**建议**：按工作空间配置模型并记录版本；服务端加密密钥，前端不持久化；模型变更走审计和权限；执行记录写入 provider/model/version；支持按发布固定模型。

### P2-15 界面承诺强于实现

**断点**：人机界面的可信度。

**证据**：

- `Workbench.tsx:388` 的回路图没有标注"人工触发"。
- `Operations.tsx:153` 说"实时快照"；`:443` 说"按订阅者逐个投递"；`:223` 说"控制器只提建议"。
- `Capability.tsx:236` 的契约提示与后端 schema 不一致。
- `Data.tsx` 卡片说"失败不会留下半写状态"，与两步写不一致。
- `Assistant.tsx:151` 说"每一步都留痕"，但步骤不持久化。

**影响**：界面是操作者唯一的观测界面，过度承诺会直接导致错误判断。这不是文案问题，而是控制回路的"人机接口失真"。

**建议**：文案与实现对齐；所有"自动/实时/已投递/已隔离/已完成"标签都必须有可验证的依据；没有依据时显示"人工触发""快照""未配置消费者""结果未知"。

## 五、做得对的部分

这份报告容易让人以为系统一无是处，实际不是。以下设计应该在修复中保留：

1. **提议与执行分离。** LLM 只能通过能力调用改变世界，最终由 kernel 提交。AI 快速建模也坚持"LLM 提议、平台裁决、人确认"。这是正确的控制论边界。
2. **运行时单一事实源。** 平台不保存第二份业务状态；发布 schema 只换定义不换语义状态。这避免了双状态同步问题。
3. **工作流 saga 补偿。** `GatewayWorkflowRunner` 在步骤失败时反向补偿，unknown 也触发补偿，补偿失败会报告而不是吞掉。这是当前唯一执行级闭环。
4. **历史回读窗口边界。** 超出 change log 窗口时拒绝回读，而不是返回错误答案。这是可信观测的好设计。
5. **不可变发布与指纹。** 发布快照不可变，指纹能发现自愈后的 schema 漂移；问题在于发现后没有修复，不在于没有发现。
6. **三态契约和审计。** runtime port 明确定义 `succeeded/failed/unknown`，执行记录、审计、事件都带 `execution_id`；问题在于下游把三态压成两态。
7. **并发与限流零件。** 租约、速率限制、32 个执行槽、请求超时都是正确的方向；问题在于幂等原子性和超时取消。
8. **测试意识。** 现有测试覆盖了失败注入、kill -9 原子性、并发、发布/回滚、幂等、历史窗口等场景。缺口在于"零样本 SLO""并发同键""超时后重试""重启后回滚""canary 隔离"没有被测试固定。

## 六、修复路线：先把回路接通，再谈自动

### 阶段 0：让传感器说真话（建议优先，1 到 2 天）

- 所有指标加时间窗和最小样本；零样本返回 `no_data`，SLO 总体不要绿。
- 工作台/运行页显示样本量、采样时刻、窗口；"实时"改成"截至某时刻"。
- 响应和 UI 暴露 `status`，unknown 显示为"结果未知"，不是成功。
- 后置条件失败必须改变状态，至少进入红色待处理。
- outbox 没有消费者时保持 pending 或标记 `no_consumer`，不能显示"已投递"。
- 对账只在有差异时发事件，事件 payload 带 finding 数量。

### 阶段 1：把执行器做成可信的（建议优先，3 到 5 天）

- 幂等键原子占位，放在租约内；unknown 保留执行记录和 `execution_id`；同一键在旧执行未确认前拒绝新的执行。
- 超时线程增加 fencing token 或取消检查，禁止放弃后继续写世界。
- 增加 unknown 解析器：查询对象状态、重放安全查询、人工确认，再决定重试或补偿。
- 能力契约 UI 与后端对齐；`effects`/`compensate` 要么执行，要么从契约中移除，不能只校验不执行。
- 发布/部署/回滚把 payload 绑定到 release/deployment；重启自愈以指针为准；canary 使用隔离运行时。
- 金丝雀健康门基于 canary 自己的流量窗口；增加自动回滚或至少"失败即阻止提升并开 todo"。

### 阶段 2：加一个真正的时钟（建议优先，3 到 5 天）

- 增加最小调度器和 lease，周期执行 outbox dispatch、SLO 采样、objective 评估、controller observe。
- 所有周期任务可配置、可观测、可暂停；失败有退避、重试上限、死信。
- 控制器增加多动作和停止条件：连续不收敛就升级 todo/告警，不能无限重跑。
- 目标改用窗口指标，todo 携带证据和验收条件，resolve 前重新评估。
- 投影同步改为后台任务，记录 last_check 与 last_change，增加行数限制和背压。

### 阶段 3：把身份、模型和 Agent 纳入治理（建议后续）

- 真实身份、默认拒绝匿名 admin、token 映射真实 actor、角色接读可见性。
- 模型按工作空间固定版本，密钥服务端加密，变更审计，执行记录模型版本。
- Agent 目标加成功谓词、完整 trace、时间/成本预算、独立验收。
- 观测层结构化渲染嵌套属性，统一时区，详情与变更流对齐采样时刻。

## 七、验收标准：怎样证明回路真的闭了

下面这些不是当前测量结果，而是修复后应该能稳定通过的验收测试。建议把它们写成自动化测试，避免再次出现"零件存在但回路不通"。

| # | 场景 | 期望 |
|---|---|---|
| 1 | 空工作空间读取 SLO | `success_rate.samples = 0` 且状态为 `no_data`，总体不是绿色 |
| 2 | 能力超时 | 响应 `status = unknown`，UI 显示"结果未知"，不显示成功；提供重试或查证入口 |
| 3 | 后置条件失败 | 执行状态不是成功，UI 红色，至少开 todo 或事件；不能只把 `verification` 放进 payload |
| 4 | 同键并发 100 次 | 世界只改变一次，execution 只有一条，所有响应都是同一次结果 |
| 5 | 超时后同键重试 | 旧执行不能在新执行之后继续写；最终效果恰好一次，或进入人工解析 |
| 6 | 回滚后重启进程 | 运行时指纹等于部署指针的 release 指纹，没有 `schema.fingerprint_mismatch` |
| 7 | canary 部署 | 当前读路径仍使用 current schema；canary 只影响 canary 流量；提升前有 canary 窗口指标 |
| 8 | 注入投影外合法对象 | 对账不报假阳性；控制器不重复重跑；连续不收敛时升级 |
| 9 | 注入缺失对象 | 控制器执行后复测通过，误差归零；若不能归零，给出明确原因并升级 |
| 10 | outbox 无消费者 | 事件保持 pending 或标记 `no_consumer`；UI 不显示"已投递" |
| 11 | 订阅者失败 | 重试有退避和上限，最终进入死信；attempts 和 last_error 可见 |
| 12 | 目标越线 | 不依赖打开页面也能产生 todo；todo 包含证据、动作、验收条件；resolve 前重新评估 |
| 13 | viewer 执行写能力 | 被拒绝，审计记录真实 actor；默认部署没有隐式 admin |

## 附录 B：审计限制

1. 本报告没有做生产压测、没有测端到端时延、没有接真实 LLM 做模型行为评估。所有"时滞/饱和/稳定性"判断都是基于代码路径和局部探针的工程推断，不是实测数据。
2. 没有完整审计 CLI、MCP、legacy `web/index.html` 和所有 API 端点。页面功能与共用用例已覆盖，边缘接口可能还有未列出的回路问题。
3. 没有做浏览器端 E2E 复核。前端结论来自源码、构建后的页面行为和此前已有的 smoke/axe 检查，不包含本轮新的交互录像。
4. 部分问题在"本地单用户演示"语境下是可接受的，例如默认 admin、手动同步、模型全局配置。报告把它们标为 P1/P2，而不是一律要求生产化，但在任何多用户或生产部署前必须处理。
5. 附录 A.2 的 `EXTRA` 对象是通过 gateway 直接写入的合法对象，不是脏数据；这正说明对账器没有考虑"非本投影来源"的对象。如果产品设计规定"一个对象类型只能由一个投影拥有"，则应显式建模这条约束，而不是默认成立。

## 附录 C：一句话总结

**v0.2 的控制回路已经有骨架、有传感器、有执行器、有审计，但还没有"判定"：它能在人看着的时候表演闭环，却不能在人不看的时候维持闭环；更危险的是，它会在不该绿的时候显示绿色。下一步不是加更多智能，而是让每一个"成功/达标/已投递/已隔离/已修复"都必须由独立观测和复测来兑现。**
