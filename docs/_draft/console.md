# 控制台：状态展示器，还是控制回路的人机接口？

> 视角：钱学森《工程控制论》的反馈回路（参考输入 → 比较 → 执行 → 被控对象 → 测量 → 反馈）。
> 对象：`frontend/src`（React 控制台）+ `src/onto_platform/interfaces/api.py` 对应路由。
> 方法：只读源码与文档，不启服务、不改码。行号取自写作时工作树（`frontend/src/api.ts`、`views/Ontology.tsx` 当时有未提交改动）。
> 本文只做控制论诊断；已由 `frontend-audit.md` / `frontend-react-review.md` / `frontend-layout-plan.md` 记录的缺陷不重复举证，只在第 3 节说明"它们之后剩下的控制语义缺口"。

## 0. 结论

**当前控制台是"状态展示器"（display），还不是"控制回路的人机接口"（HMI）。**

判定依据：人机接口必须闭合四件事——**看得见状态、比得出偏差、发得出动作、验得回效果**。逐项核对：

| 回路要素 | 控制论符号 | 本系统对应物 | 控制台是否承担 |
|---|---|---|---|
| 参考输入（目标/设定值） | r | **不存在实体**；唯一近似是 `AppAgent.goal` 自然语言（`frontend/src/api.ts:63`） | ✗ 不能设定 |
| 比较器 | r−y | 人脑，界面不提供目标值 | ✗ 不算偏差 |
| 执行器 → 被控对象 | u → y | 能力 invoke / 投影 run / 发布（`api.ts:228-233`） | ◐ 能发，不能预演/回滚 |
| 测量（传感） | y | `state/find|get`、`changes`、`audit`（`api.ts:199-203`） | ◐ 有值，无采样时刻 |
| 反馈确认 | y 回读 | 仅 toast + 后端自报 `changes`；`api.get` 只用于详情抽屉（`views/StateBrowser.tsx:82`） | ✗ 不校验 |

一句话总结：**能"看定义、点动作"，不能"看偏差、验效果、复原"。** 它优化的是"建模流水线的可视化"，而不是"运行中业务世界的调节"。

## 1. 控制台在控制回路中的位置

### 1.1 人机接口的三层职能（显示 / 设定 / 确认）

| 职能 | 现状实现 | 证据 | 控制论评价 |
|---|---|---|---|
| **显示** | 各页 `useLoad` 一次性拉取定义与状态 | `ui.tsx:12-29`；`views/Workbench.tsx:36-55`；`views/Data.tsx:14-21` | 只有"快照"，无采样时刻、无失效标记 |
| | 顶栏健康灯 20s 轮询 | `store.tsx:159-164`（`ping`）、`:220`（`setInterval(ping, 20000)`） | 唯一周期观测**只探活**（`/api/health`），不描述被控对象 |
| | 变更流水 2.5s 轮询（需手动勾选） | `views/StateBrowser.tsx:178`（默认 `false`）、`:198-202` | 唯一的"过程量"通道，默认关闭 |
| | 服务端重检查需手动点击 | `App.tsx:201-205` | 观测可控但无"上次检查时刻" |
| **设定** | 表单即设定：对象/关系/术语/映射/能力参数/应用视图 | `views/Ontology.tsx:156-211`；`views/Capability.tsx:112-183`；`views/Application.tsx:370-510` | 设定的是**结构（schema）**，不是**运行目标（setpoint）** |
| | 执行参数在能力抽屉里手填 | `views/Capability.tsx:245-258` | 这是唯一"给被控对象下设定值"的入口，却无历史值/上次值/推荐值 |
| **确认** | 写后 toast（成功 4s、错误 9s、最多 3 条） | `store.tsx:152-157` | 反馈是**瞬时事件**，不是**持久状态** |
| | 执行结果区仅存在于抽屉内，关闭即销毁 | `views/Capability.tsx:191`（组件局部 `result`）、`:222-227`（`Drawer` + footer） | 结果不可回溯 → 操作者"记得自己做过"，系统不记得 |
| | 校验问题只进 toast | `views/Ontology.tsx:69-74` | 失败清单 4s 后消失，无法逐条修 |

### 1.2 采样频率与新鲜度

| 通道 | 频率 / 触发 | 失效时界面表现 | 是否标注数据时刻 |
|---|---|---|---|
| `/api/health` | 20s 定时 + 手动 | 顶栏点变灰、文案"服务不可达"（`App.tsx:203-204`） | 否（只有版本号） |
| 运行时/定义（ontology、runtime、capabilities、applications、datasources、projections） | **仅挂载 / 换工作空间 / 显式 reload**（`ui.tsx:19-27`，deps 为 `[wid]`） | 页面保留旧数据，**无任何"过期"提示** | 否 |
| 对象实例查询 | 提交表单时 | `results.error` 从不渲染（`StateBrowser.tsx:60-62` 只分 loading/empty/data） | 否 |
| 变更流 `/changes?after=` | 2.5s（opt-in） | 无（错误被 `useAction` 吞成 toast） | 否（表格列只有 序号/来源/改动，`StateBrowser.tsx:220`，尽管事件带 `ts`（`api.ts:70`）） |
| 审计 | 打开页签 / 手动"读取最近操作" | 无 | **是**（`Settings.tsx:154`，唯一显示时刻的地方） |

**全局事实：整个前端没有任何时间戳/`Date.now()`/`fetchedAt` 逻辑**（`frontend/src` 全目录检索 `Date.now|new Date|toLocale|updatedAt|asOf` 零命中；仅表格渲染后端自带 `ts` 字段）。
控制论解释：测量值必须附带**采样时刻**，否则操作者无法判断反馈回路是否还通、数据是 3 秒前还是 3 小时前；这是"可观测性"的最低门槛。
后果：多操作者、跨页签、长会话三种场景下，"界面显示"与"世界状态"可能任意偏离而无人知情——**系统失去可观测性，任何后续判断都不成立**。

## 2. 逐项诊断

### 2.1 采样与新鲜度

**S1｜所有主页面是一次性快照，没有"数据截止时间"**
- 现象：定义区/计数区只在挂载、换工作空间或点按钮时刷新；界面从不说明数据何时取回。
- 证据：`ui.tsx:19-27`（`useEffect` 只依赖 `[...deps, nonce]`）；`views/Capability.tsx:32`、`views/Data.tsx:14-21`、`views/Application.tsx:21-29`、`views/Settings.tsx:92`。
- 控制论：把"采样"做成了"事件驱动的一次性读取"，等于没有周期性测量；反馈通道的可用性无从评估。
- 后果：操作者把 10 分钟前的"已发布"当现状；对本人刚做的改动，另一处界面仍显示旧值，产生"系统没反应"的误判，进而重复动作。

**S2｜健康探活只证明"进程活着"，不证明"回路通"**
- 现象：顶栏灯 = `/api/health` 是否 200；`health` 载荷只有 版本/存储/provider/console。
- 证据：`store.tsx:159-164`；`App.tsx:201-206`；后端 `interfaces/api.py:148-158`。
- 控制论：这是**执行器/传感器都通**才成立的闭环假设，而探活只测了 HTTP 入口。运行时沙箱加载失败、内核异常、投影积压，灯仍然绿。
- 后果：绿色的"v0.1.0"给了虚假的安全感——观察者以为在观测，其实只观测了网关。

**S3｜工作空间切换存在刷新竞态（推断）**
- 现象：`refreshRuntime` 无取消/校验令牌；连续切 A→B 时，A 的响应可能后到并覆盖 B 的计数。
- 证据：`store.tsx:181-216` 全程无 `wid` 归属校验；调用点 `store.tsx:231`。
- 控制论：测量回路与被控对象之间缺少"作用域标记"，反馈可能被贴到错误的对象上（feedback misassignment）。
- 后果：侧栏完成度/对象类型下拉显示的是上一个世界的数字，且**没有任何机制会发现**（推断：无二次校验）。

**S4｜跨操作者不可见（推断）**
- 现象：无 SSE/WebSocket/广播；`EventSource|WebSocket` 在 `frontend/src` 零命中，服务端亦无推送路由（`interfaces/api.py:141-391` 全为拉取）。
- 控制论：多操作者共用同一被控对象时，各自的"测量"独立过期，控制回路由"一人一回路"退化为"多人开环"。
- 后果：两人同时对同一对象下动作，谁都不知道对方已改过——冲突只能事后从 `changes` 里翻出来（而默认不显示时刻）。

**S5｜变更流水有 `ts` 却不展示**
- 现象：`ChangeEvent` 带 `ts`（`api.ts:70`），变更表只渲染 序号/来源/改动 三列。
- 证据：`StateBrowser.tsx:220`（表头）、`:222-239`。
- 控制论：过程量只有"序"没有"时"，无法计算变化率、无法判断停滞（desync detection 的常见依据是"多久没来新事件"）。
- 后果：实时跟随开启时，操作者无法分辨"没有变化"与"回路卡住"。

### 2.2 回路闭合（写操作之后会发生什么）

**L1｜15s 客户端超时 vs 长任务：动作可能已生效，界面却报"超时"**
- 现象：`TIMEOUT = 15000` 统一用于所有请求；只有 AI 快速建模单独放宽到 90s（`api.ts:114-115, 219`）。而 `/agent`、`/invoke`、`/projections/{id}/run` 都沿用 15s（`api.ts:228, 233, 259`）。
- 证据：`api.ts:117-137`（AbortController + `friendly` 超时文案 `:132`）；服务端为 `ThreadingHTTPServer`（`interfaces/api.py:416`），且 agent 每步都能 `invoke_capability` 真实改状态（`application/agent_runner.py:151-152`）；投影同步逐表 fetch+apply（`application/data_usecases.py:124-146`）。
- 控制论：这是**执行与反馈在时间尺度上不匹配**。客户端 abort 只断开 HTTP，不取消服务端线程——于是"控制量已输出、反馈被截断"，回路被打成开环。
- 后果（推断）：真实 LLM 下一步常 >15s，操作者看到"请求超时：服务超过 15 秒没响应"→ 判定失败→ 重试→ 同一业务动作被执行两次；而 `changes` 里确实有两条记录，界面却只留下一条红色 toast。**这是当前最危险的控制语义错误：把"未知结果"渲染成"失败"。**

**L2｜没有任何"动作后回读"**
- 现象：能力执行后只贴出后端返回的 `changes`（后端自报），并 `candidates.reload()` 刷新下拉框；不读目标对象的新值。投影同步只 toast 计数；发布只 toast + 刷新列表。
- 证据：`views/Capability.tsx:216-219`；`views/Data.tsx:23-29`；`views/Application.tsx:101-107`。
- 控制论：`api.get` 在整个前端只用于详情抽屉（`StateBrowser.tsx:82`）。缺少"执行→再测量"这一步，反馈是**声明（assertion）而非观测（observation）**。
- 后果：后端若"报成功但没写"（no-op、被后续逻辑覆盖、写到了别处），控制台无法发现；这正是闭合回路要消灭的失败模式。

**L3｜零变更的执行不产生任何可观测痕迹**
- 现象：执行成功但状态未变（例如充值金额已相等）时，网关不记录变更。
- 证据：`infrastructure/runtime/kernel_gateway.py:255-256`（仅在 `changes` 非空时 `_record`）、`:355-357`（delta 同）。
- 控制论：反馈通道把"执行了但偏差为 0"与"根本没执行"合并成同一个观测（空）。**这是缺失观测的经典陷阱**：不可区分即不可控。
- 后果：操作者无法区分"我点了没反应"和"点了，系统说无事可做"；排查只能翻审计（`capability_usecases.py:120-124` 写入了 ok/error），而审计与变更流是两个互不相连的页面。

**L4｜失败不进入过程流，只在审计的 JSON 里**
- 现象：invoke 失败会被审计记录（`ok:false` + `error`），但 `changes` 里没有对应事件；控制台没有任何"失败列表/失败率"。
- 证据：`application/capability_usecases.py:120-124`；审计页仅表格展示 `detail` JSON（`views/Settings.tsx:150-159`）。
- 后果：控制论上"扰动"不可见——回路只记录成功输出，等于把误差项丢掉，系统无法自我纠偏。

**L5｜执行编号不可回查**
- 现象：抽屉里显示 `执行编号`，但审计详情不含 `execution_id`，也无按编号查询的路由。
- 证据：`views/Capability.tsx:265`；`capability_usecases.py:120-124`（detail 只有 target/ok/error/changes）；`api.py:203-263` 无执行详情路由。
- 后果：事后核对只能靠"时间相近 + 对象相同"猜测，追溯链在关键一环断掉。

**L6｜toast 消失即遗忘；结果区随抽屉销毁**
- 现象：成功提示 4s、错误 9s、最多 3 条（`store.tsx:152-157`）；执行结果 `result` 是 `RunDrawer` 局部 state，关抽屉即丢（`views/Capability.tsx:191, 222-227`）。
- 控制论：反馈必须是**可保持的状态**，否则人必须实时在场；缺"操作日志面板"意味着人机接口只能做瞬时提示，不能做"上次动作 → 当前状态"的对比。
- 后果：连做 3 次动作后无法复述每次改了什么（推断：实际用户会打开另一个窗口记笔记或截图）。

**L7｜防重复提交只防"连点"，不防"重试"**
- 现象：`useAction.busy` 只在同一请求在途时忽略点击（`store.tsx:298-305`）；请求结束即解除，无幂等键、无"上次提交"指纹、无二次确认。
- 证据：`store.tsx:294-307`；`api.ts:209-260` 全部 POST 无 `Idempotency-Key`；后端 `invoke`（`capability_usecases.py:115-131`）无幂等去重。
- 控制论：无记忆的执行器在"超时/重试"下必然重复施加控制量（积分饱和的离散版本）。
- 后果：叠加 L1，重试风险被放大；业务上等价于"重复扣款"。

**L8｜动作不可逆、不可预演、不可补偿**
- 现象：能力执行直接改状态；发布后本体不可变；无 dry-run、无撤销、无回滚。
- 证据：`frontend/src` 与后端全仓检索 `dry_run|rollback|undo|revert|compensat` 零命中；不可变文案见 `api.ts:97-98`（`friendly` 对 `published ontology is immutable`）。
- 控制论：没有反向作用通道（无负反馈的执行层），也没有"先仿真再施加"（预测控制），系统只能正向推进。
- 后果：误动作只能靠"再执行一次相反动作"手工补偿——而控制台不提供"当前值是多少"的对比视图，补偿量靠人算（推断：这是操作失误的第二大来源）。

### 2.3 观测盲区（暴露了什么 / 缺什么）

**O1｜暴露的都是"计数与文本"，缺"时间与质量"**

| 已暴露 | 证据 | 缺失 | 为什么关键 |
|---|---|---|---|
| 对象类型/关系/术语数、能力/应用已发布数 | `store.tsx:190-214`；`Workbench.tsx:58-85` | 请求延迟、错误率、超时率 | 无法判断回路快慢与稳定性 |
| 投影"新增/更新 N 个对象、M 条关系" | `views/Data.tsx:25-28` | 投影**运行历史**（每次耗时、成功/失败、写入量趋势、上次同步时刻） | 无法发现"同步变慢/空转" |
| 变更流水（最多 200 条） | `StateBrowser.tsx:191` | 积压量（`seq` 差）、消费延迟 | 无法判断是否落后于世界 |
| 审计（最多 500 条，无分页） | `views/Settings.tsx:132-137, 142` | 按动作/对象/结果筛选、失败聚合 | 排障靠肉眼扫表 |
| 健康：版本/存储/provider | `views/Settings.tsx:101-112` | 运行时是否可用、内核异常数、LLM 调用成本/耗时/失败率 | "系统自检"名不副实 |
| Agent 步数 + 推理链 | `ui.tsx:237-258`；`Assistant.tsx:149-155` | token/费用/耗时、每步延迟、"它改了什么" | 无法评估自动化动作的代价与副作用 |

**O2｜"系统自检"里有两行是硬编码的"正常"**
- 现象：`版本` 与 `定义存储` 两行的结果恒为 `yes(true)`；`运行时状态存储` 只判断 `!= "memory"`。
- 证据：`views/Settings.tsx:97`（`yes`）、`:105-107`。
- 控制论：这是**伪造的测量**——把常量贴在仪表盘上，操作者会把它当测点读。
- 后果：比"没有仪表"更坏：它让人相信已经检查过。

**O3｜"自检模型连通性"并不连模型**
- 现象：按钮只调 `/api/health` 读 `llm_configured` 字段，没有一次真实补全调用。
- 证据：`LlmPicker.tsx:47-56`（`:50` 仅 `api.health()`）。
- 控制论：连通性断言必须以"最小闭环试探"验证（发一个 1-token 请求看响应），否则测的是配置项而非通道。
- 后果：密钥错误、base_url 不通、模型名不存在时按钮仍报"模型服务就绪"，故障被推迟到真正执行业务动作时才爆。

**O4｜变更事件不带来源实体，无法与审计对齐**
- 现象：投影写入的变更 `source="projection"`，不携带 projection id；invoke 的变更带 `function` 但不变更流 UI 只当标签显示。
- 证据：`kernel_gateway.py:256`（`source="invoke", function=...`）、`:356`（`source=source`）；`api.ts:70`（`ChangeEvent.function?`）。
- 后果："哪次同步改的"必须靠时间戳人工对——而变更表连 `ts` 都不显示（S5）。

**O5｜错误只有一句中文，没有类别**
- 现象：`ApiError` 保留 `status`/`type`，但全前端无一处读取（检索 `.status` 零命中）；`friendly()` 把错误压成一句业务话术。
- 证据：`api.ts:82-92`（类）、`:93-112`（`friendly`）；`store.tsx:302`（toast 只取 `message`）。
- 控制论：误差信号被"翻译"成叙事，丢失可分类、可聚合、可告警的维度。
- 后果：操作者无法区分"我填错了(4xx)"、"服务坏了(5xx)"、"网络断了(0)"，也就无法选择正确的纠正动作。

**O6｜"看得到"与"说得清"错位：应用视图只能表达"是什么"**
- 现象：视图只渲染对象属性表/卡片（`Application.tsx:250-261`），查询结果是固定过滤条件的对象集合（`api.ts:62`）；没有"阈值/目标/达成率"字段。
- 证据：`api.ts:61-63`（`AppQuery{object_type, filters, expand}`、`AppView{kind, properties}`）；后端全仓检索 `kpi|metric|threshold|setpoint|target_value` 零命中。
- 控制论：应用层是"面向业务人员的测量界面"，却只能测量**当前值**，不能测量**相对目标的偏差**——业务人员仍须自己做除法。
- 后果：所谓"应用"退化为"更好看的表查询"，没有承担 HMI 的读数职能。

### 2.4 轮询稳定性

**R1｜轮询失败会造成 toast 风暴（推断）**
- 现象：`pull` 走 `useAction`，任何异常都被 catch 成 toast；2.5s 一拍，最多 3 条同屏，每条 9s。
- 证据：`StateBrowser.tsx:183-194`（`pull`）→ `store.tsx:302`（catch→toast）→ `store.tsx:152-157`（错误 9s）。
- 控制论：把"采样失败"当成"事件异常"上报，噪声淹没信号。
- 后果：服务重启的 30 秒里，屏幕被十几条重复错误刷满，真正的关键提示被挤掉。

**R2｜游标越界无自愈：重启后可能永久"无新变更"**
- 现象：`seq` 存在组件 ref 里，只增不减，只有换工作空间才归零（`StateBrowser.tsx:180, 197`）。变更日志仅在 `runtime_store=sqlite` 时落盘（`provider.py:27-32`）；memory 运行时重启后 `_seq` 回到 0，而客户端仍持旧高位。
- 证据：`kernel_gateway.py:397-399, 415-427`；`api.py:258-260`（`after` 直接透传）。
- 控制论：这是**反馈通道静默失效**——最危险的失效模式：不报错、不给数，界面显示"暂无变更"，操作者以为世界静止。
- 后果（推断）：重启后操作者继续下动作，完全看不到结果，直到刷新页面；而"刷新页面"这个正确做法没有任何提示。

**R3｜`after=0` 全量拉取：观测成本随历史线性增长**
- 现象：详情抽屉每开一次对象就拉**整份**变更日志，再在浏览器里字符串匹配过滤。
- 证据：`StateBrowser.tsx:91-94`；服务端无 `limit`/`since` 参数（`api.py:258-260`），`observe_changes` 全表扫描复制（`kernel_gateway.py:397-399`）。
- 后果：日志到 10 万条时，打开对象详情要传几十 MB、主线程逐条 `JSON.stringify` 比较——观测本身成为系统负担。

**R4｜变更日志无上限、无压缩、无轮转**
- 现象：进程内 `_changes` 列表只 append；落盘 append-only JSONL，无轮转、无截断。
- 证据：`kernel_gateway.py:401-413`（写入）、`:397-399`（读取）；前端只截留 200 条显示（`StateBrowser.tsx:191`），服务端不限。
- 控制论：传感器缓冲区无界 → 长期运行后内存与查询成本单调上升，回路响应变慢直至不可用。
- 后果：项目号称"每次改变都留痕"，实际是"运行越久越慢"，而控制台不暴露队列深度，用户只会觉得"平台卡了"。

**R5｜并发保护只在"同一组件同一动作"层面**
- 现象：`useAction.busy` 是组件级 ref；`Store.refreshRuntime` 多路并发 `Promise.all`（`store.tsx:192-196`）；工作台一屏打 11 个请求（`Workbench.tsx:38-46` + `store.tsx:185-196`）。
- 证据：`store.tsx:294-307`；`Workbench.tsx:36-55`。
- 控制论：回路里没有"总请求预算/背压"，一次交互的采样成本与页面复杂度成正比。
- 后果：慢网下多个请求各 15s 超时，界面长时间停在半加载态（推断），操作者倾向于重复点击，进一步加重并发。

### 2.5 信息架构与控制语义

**I1｜五步主流程是"建模流水线"，不是"控制环"**
- 现象：工作台的五步依次是 建空间 → 定义本体 → 发布 → 接数据 → 能力/应用；每步 `done` 由"计数>0"判定。
- 证据：`Workbench.tsx:58-85`（`steps`）、`:92-100`；`store.tsx:203-208`（`suggestions` 也是按计数递进）。
- 控制论：这是**开环的构建顺序**（commissioning checklist），它回答"平台搭好了没有"，不回答"业务目标达成得怎样"。闭环需要的是 设定 → 执行 → 测量 → 比较 → 修正 的循环，而这里循环在"发布"之后就结束了。
- 后果：控制台的心智模型停留在上线那一刻；上线之后（也就是真正需要控制的时候）没有任何视图承接。

**I2｜"目标"不是一等公民**
- 现象：`goal` 只以字符串出现在应用智能体里（`AppAgent.goal`，`api.ts:63`），仅用于给 LLM 的提示词（`Application.tsx:484`；`Assistant.tsx:132`）；没有"目标值 / 阈值 / 期望状态"之类的可计算实体。
- 证据：`api.ts:61-63`；`views/Application.tsx:469-488`；后端零 `metric/threshold/target` 字段。
- 控制论：没有参考输入 r，就没有误差 e=r−y，也就没有"偏差"这个概念可显示。**整个控制台因此只能显示"是什么"，不能显示"差多少"。**
- 后果：任何"系统有问题吗"的判断都被推回给人：人自己去表里找异常行。这是控制台最根本的能力上限。

**I3｜不能表达"目标值 vs 实际值"**
- 现象：对象表平铺属性（`ui.tsx:175-209`），卡片视图平铺字段（`Application.tsx:273-292`）；没有"当前值 / 目标值 / 偏差 / 趋势"的呈现原语。
- 证据：同上；`ui.tsx` 无 gauge/delta/spark 组件。
- 后果：即使数据里存在 `balance` 与"应充金额"这类可比较量，界面也只能并列显示，比较动作留在人脑——回路里唯一的"比较器"是人。

**I4｜导航按"平台结构"分词，不按"控制任务"分词**
- 现象：主导航为 工作台 / 本体 / 数据 / 能力 / 应用 / 对象实例 / AI 助手 / 设置（`App.tsx:16-35`），全部是实体名词。
- 控制论：HMI 的导航通常按"任务/回路"组织（监控 → 越限 → 处置 → 复盘）。当前结构迫使操作者在"我该做什么"与"去哪个页签"之间做一次翻译。
- 后果：跨页的闭环动作（执行 → 看变更 → 看审计 → 回对象）需要 4 次导航，且每次导航都**重置本地状态**（结果区/抽屉销毁），闭环在交互上被打断。

**I5｜"最后同步时间"缺席使"是否需要动作"无法判断**
- 现象：数据页有"立即同步"按钮，但列表不显示上次同步时刻、上次结果、对象总量趋势。
- 证据：`views/Data.tsx:23-29`（只有 toast）、`:59-88`（表格列只有 名称/覆盖范围/按钮）。
- 控制论：控制律的第一步是"何时该动作"的判据；缺上次时刻与上次效果，动作只能靠人拍脑袋（定时轮询式人工动作）。
- 后果：要么频繁空跑同步，要么长期不同步——两者都让"数据新鲜度"这个关键状态量失控。

| **P1-5** | 变更事件不带来源实体 | 变更流与审计无法对齐 | `kernel_gateway.py:256, 356`；`api.ts:70` |

| **P1-7** | 错误只留一句中文，`status/type` 无人读 | 误差不可分类、不可聚合 | `api.ts:82-112`；`store.tsx:302` |

| **P2-2** | 结果区/抽屉关闭即销毁，执行编号不可回查 | 反馈不可保持、不可追溯 | `Capability.tsx:191, 222-227, 265` |
| **P2-3** | 工作台五步是"上线清单"而非控制环 | 上线之后没有视图承接 | `Workbench.tsx:58-85` |
| **P2-4** | 导航按实体分词，闭环动作需 4 次跳转且状态重置 | 交互层打断回路 | `App.tsx:16-35`；`Capability.tsx:191` |
| **P2-5** | 校验问题只进 toast | 失败清单无法逐条处理 | `Ontology.tsx:69-74` |

**若只做三件事**：(1) 给每个数据区加"数据时刻 + 最后同步时刻"，并把超时改为"未知结果"而非"失败"（P0-1/P0-2）；(2) 写操作后强制 `get()` 回读并在结果区并排显示"动作前/动作后"（P0-3）；(3) 在应用视图里引入"目标值/偏差"列，把参考输入变成实体，让"差多少"可被测量（P1-4）。
前两项让回路**闭合**，第三项让偏差**可计算**——这是从"状态展示器"变成"人机接口"的最小改造集。
